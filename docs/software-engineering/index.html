A job description asks for three things: systems thinking that survives contact with production, Go fluency good enough to read, review and write real code, and hands-on comfort with the cloud those systems actually run on. This page walks all three from beginner to advanced — mostly in pictures — and then puts every concept on the same map.

Orientation

What each level actually means

The three levels here are not "how much you have read". They are three different relationships with the same idea: you can name it, you can operate it, or you can own the tradeoff it makes. Every topic below is split the same way, so the ladder is comparable across concepts.

Pillar A

Deep backend foundations

Six mechanisms that show up in every backend, regardless of language. Each one exists to trade a resource you have for a resource you do not: CPU for latency, memory for reads, durability for throughput, correctness for availability.

Deep dive: The Machine Room →

Foundations · 01

Concurrency

Concurrency is a way of structuring work so parts can progress independently. Parallelism is executing them at the same instant. You can have concurrency on one core; you get parallelism only with more cores.

L1 · Beginner

Know the vocabulary and the hazard

  • Process vs thread — separate memory vs shared memory, and why sharing is what creates the problem.
  • Race condition — result depends on timing. Critical section — the code that must not interleave.
  • Mutex to serialise access; atomics for single-word counters.
  • Context switch costs; blocking on I/O is what makes concurrency pay off.
  • CPU-bound vs I/O-bound — the first wants cores, the second wants overlap.
L2 · Intermediate

Coordinate safely at scale

  • Deadlock and the four conditions; break it with a global lock ordering.
  • Lock granularity — coarse locks are correct and slow; fine locks are fast and easy to get wrong. Sharded locks as the middle.
  • Memory visibility — without a happens-before edge, another thread may never see your write.
  • Bounded concurrency: worker pools, semaphores, and why unbounded goroutines/threads is a production incident.
  • Backpressure — a full queue must slow the producer, not silently grow.
  • Cancellation propagated through the whole call tree.
L3 · Advanced

Reason about the scaling ceiling

  • Amdahl & the Universal Scalability Law — contention flattens the curve, coherency (cross-core chatter) bends it back down. More cores can be slower.
  • False sharing — two hot variables on one cache line silently serialise.
  • Lock-free via CAS, and knowing when it is not worth it: uncontended mutexes are already cheap.
  • Single-writer principle — partition state by key so no lock is needed at all. Usually beats clever locking.
  • Structured concurrency — no goroutine outlives the scope that spawned it; leaks become impossible by construction.
  • Latency under contention is a distribution: watch p99, not the mean.
Foundations · 02

Event-driven architecture

A command asks for something to happen and waits. An event announces something already happened and does not care who listens. Swapping one for the other changes who is coupled to whom, and who is awake when things break.

L1 · Beginner

Events, publishers, subscribers

  • An event is a fact in the past tense: OrderPlaced, not PlaceOrder. It cannot be rejected.
  • Pub/sub vs point-to-point; the publisher does not know its subscribers.
  • Sync gives you an answer; async gives you decoupling. That is the whole trade.
  • Asynchronous means the caller returns before the work is done — so the UI must be designed for "in progress".
L2 · Intermediate

Contracts, ordering, and the dual-write trap

  • Choreography vs orchestration — events reacting to events, vs one coordinator driving steps. Orchestration is easier to debug; choreography is easier to extend.
  • Three payload styles: notification (id only), event-carried state transfer (full snapshot), event sourcing (the log is the truth).
  • Idempotent consumers — assume every event arrives twice. Dedupe on an event id.
  • Ordering is per partition key, never global. Key by aggregate id.
  • Dual write: writing the DB and publishing separately can lose or invent events → fix with the transactional outbox or CDC.
L3 · Advanced

Truth, time, and recovery

  • Event sourcing + CQRS — rebuild any read model by replaying; the cost is versioning every event forever.
  • Schema evolution: additive-only fields, registries, and a compatibility policy you enforce in CI.
  • Sagas — distributed transactions as steps plus compensations; there is no rollback, only a corrective event.
  • Effectively-once = at-least-once delivery + idempotent effects. "Exactly once" end-to-end is marketing.
  • Eventual consistency in the product: read-your-writes, stale reads, and what the user is told meanwhile.
  • Replay safety — can you re-run last week's log without re-charging a card?
Foundations · 03

Caching

A cache buys latency and load relief with memory and staleness. Every cache is a bet that the same answer will be asked for again before it stops being true — and a new failure mode for the moment the bet is wrong.

L1 · Beginner

What, where, how long

  • Why: cut latency and cut load on something expensive.
  • Layers: browser → CDN → in-process → distributed (Redis/Memcached) → DB buffer pool.
  • Hit ratio, TTL, eviction (LRU, LFU) and what happens when memory fills.
  • Cache only what is expensive and re-read. Everything else is a memory leak with extra steps.
L2 · Intermediate

Patterns and key design

  • Cache-aside, read-through, write-through, write-behind — and which one loses data on a crash.
  • Key design: namespace, entity, version. Bumping a version prefix invalidates a whole class instantly.
  • Negative caching for "not found", or one bad id becomes a DB scan generator.
  • Local (fast, per-instance, inconsistent) vs distributed (shared, consistent-ish, a network hop away).
  • Measure hit ratio and the latency of a miss — a 99% hit ratio with a 2s miss is still a bad p99.
L3 · Advanced

The cache as a liability

  • Stampede / dogpile → single-flight coalescing, TTL jitter, probabilistic early recompute.
  • Cold start — a deploy or Redis failover exposes the origin to unfiltered traffic. Warm, or shed load.
  • Hot keys — one celebrity id saturating one shard; fix with key splitting or a local L1 in front.
  • Consistent hashing so adding a node moves 1/N of keys, not all of them.
  • Write–invalidate races; fix with delete-after-commit, short TTLs as a safety net, or versioned CAS writes.
  • Decide explicitly: is stale data wrong here, or merely old? Prices and permissions differ from avatars.
Foundations · 04

Indexing

An index is a second, ordered copy of some columns that turns "look at everything" into "navigate to it". You pay on every write and in storage, forever, to make certain reads cheap.

L1 · Beginner

Lookup instead of scan

  • Index = ordered structure mapping a value → row location. B+tree is the default.
  • Primary key vs secondary index; unique vs non-unique.
  • The cost: every INSERT/UPDATE maintains every index. Indexes are not free reads — they are bought with writes.
  • Index the columns you filter and join on, not every column.
L2 · Intermediate

Read the plan, design the key

  • Leftmost prefix and column ordering: equality columns first, the range column last.
  • Selectivity — an index on a boolean rarely helps; the planner will ignore it and be right.
  • Covering index / index-only scan — put the returned columns in the index and skip the table entirely.
  • Read EXPLAIN ANALYZE: estimated vs actual rows is where bad plans confess.
  • Structure per job: B-tree (range), hash (equality), inverted (search), GiST/geo, LSM (write-heavy).
L3 · Advanced

Write amplification and plan stability

  • B-tree vs LSM — in-place updates and read-optimised, vs sequential writes with compaction and read amplification. Bloom filters recover point reads.
  • Clustered (row lives in the index, InnoDB) vs heap (Postgres) — changes the cost of every secondary lookup.
  • Partial and expression indexes — index the 2% of rows a hot query touches.
  • Bloat, vacuum, and write cliffs — index maintenance is an operational concern, not a one-time DDL.
  • Cardinality misestimates flip plans overnight under stale statistics; that is the 3am "the query got slow with no deploy".
  • At scale the partition/shard key outranks every index: it decides which machine even has to answer.
Foundations · 05

Messaging queues

A queue converts a synchronous dependency into a buffer with a time dimension. Producers stop caring whether consumers are up, fast, or numerous — and in exchange you now own a backlog, a retry policy, and a poison message somewhere.

L1 · Beginner

Producer, broker, consumer

  • Why: decouple, buffer spikes, retry safely, do slow work off the request path.
  • Queue (one consumer wins) vs topic (everyone gets a copy).
  • Ack — the broker keeps a message until the consumer confirms; no ack means redelivery.
  • Producing is fast; the work still has to happen. A queue moves latency, it does not delete it.
L2 · Intermediate

Semantics you can defend

  • At-most-once / at-least-once / effectively-once. Nearly everything real is at-least-once, so consumers must be idempotent.
  • Consumer groups and partitions: parallelism is capped by partition count.
  • Visibility timeout / ack deadline — too short and you double-process, too long and failures stall.
  • DLQ plus a plan for draining it. A DLQ nobody reads is a bug tracker nobody reads.
  • Lag is the health metric; alert on it before latency SLOs break.
L3 · Advanced

Topology and failure economics

  • Log-based (Kafka/Pulsar: retained, replayable, ordered per partition) vs broker-based (SQS/Rabbit: per-message ack, easy fan-out of work, no replay). Pick by whether you need history.
  • Hot partitions from a skewed key; rebalancing storms when consumers flap.
  • Poison messages blocking an ordered partition — ordering guarantees and skip-on-failure are in direct conflict.
  • Backpressure and flow control: an unbounded queue converts a throughput problem into an unbounded latency problem.
  • Replay as an operational tool — and the idempotency that makes it safe.
  • Queue depth as a control signal for autoscaling, not just a dashboard line.
Foundations · 06

Fault tolerance

Everything downstream will be slow before it is down, and down before you notice. Fault tolerance is the set of decisions you make in advance about what to do with the time you are not going to get an answer in.

L1 · Beginner

Assume failure

  • Networks drop, disks fill, processes are killed mid-write. Failure is normal traffic.
  • Always set a timeout. An unset client timeout is an unbounded outage waiting for a slow day.
  • Redundancy: more than one instance, health checks, restart on failure.
  • Graceful degradation — return the page without the recommendations rather than no page.
L2 · Intermediate

Patterns with knobs

  • Exponential backoff + jitter, capped attempts. Jitter is what stops synchronised retries.
  • Idempotency keys so a retry cannot charge twice.
  • Circuit breaker (closed/open/half-open) and bulkheads so one slow dependency cannot consume every worker.
  • Rate limiting and load shedding — rejecting 5% cleanly beats collapsing for 100%.
  • Deadline propagation — the whole call tree shares one budget, decremented at each hop.
L3 · Advanced

Systemic failure

  • Metastable failure — the trigger passes but retries and cold caches keep the system down. Recovery needs load shedding, not more capacity.
  • Blast radius: failure domains, cells, shuffle sharding, so one bad tenant cannot reach everyone.
  • Gray failure — healthy to the health check, broken for users. Probe what users do.
  • Hedged requests to cut tail latency, paid for in extra load.
  • CAP / PACELC as a design statement: during a partition, do you refuse writes or accept divergence? Say which, on purpose.
  • SLOs and error budgets turn "reliable" into a number that decides whether you ship or harden.
Pillar B

Pragmatic Go

Go is a small language with four ideas that carry almost everything: goroutines, channels, interfaces, and errors as values. The bar here is fluency for reading and reviewing — being able to look at a diff and say "that goroutine leaks", "that interface is nil but not nil", "that error swallows context".

Deep dive: Reading Go →

Go · 01

Goroutines

A goroutine is a function scheduled by the Go runtime rather than the OS: a few kilobytes of stack, started with one keyword. Cheap enough that "one per request" is idiomatic — which is exactly why leaking them is the most common Go production bug.

// The leak: nobody ever receives, so this goroutine blocks forever.
// Its memory, its stack, and everything it closes over stay alive.
func leak() {
    ch := make(chan int)          // unbuffered
    go func() { ch <- expensive() }()  // blocks on send, forever
    return                        // caller walked away
}

// The fix: an exit path the goroutine can actually take.
func noLeak(ctx context.Context) (int, error) {
    ch := make(chan int, 1)       // buffered: send never blocks
    go func() { ch <- expensive() }()
    select {
    case v := <-ch:
        return v, nil
    case <-ctx.Done():            // caller gave up; we still unblock
        return 0, ctx.Err()
    }
}
L1 · Beginner

Start one, wait for it

  • go f() starts a goroutine; the caller does not wait.
  • sync.WaitGroup to wait for a known set. Add before go, defer wg.Done() inside.
  • When main returns, every goroutine dies mid-sentence. Shut down on purpose.
  • Run tests with -race. It finds real bugs you cannot reason your way to.
L2 · Intermediate

Lifetimes and limits

  • context.Context is the cancellation and deadline channel of every real Go service. First parameter, always.
  • Bounded worker pools — N workers over one job channel, or a buffered channel as a semaphore. Unbounded fan-out is how you OOM.
  • errgroup.Group — wait for a group, propagate the first error, cancel the rest.
  • Leak review checklist: every go has a stop condition; every send has a receiver or a ctx.Done().
  • Loop-variable capture is per-iteration since Go 1.22 — know which version the codebase is on.
L3 · Advanced

Runtime behaviour

  • Work stealing, preemption, and the netpoller — why blocking I/O scales but a tight CPU loop used to starve everything.
  • GOMAXPROCS in containers — unset, Go can see host cores and oversubscribe a small CPU quota (fixed by newer runtimes / automaxprocs).
  • Diagnosis: pprof goroutine profiles, goleak in tests, the runtime trace for scheduler latency.
  • Structured concurrency — the caller owns the scope; nothing outlives it.
  • sync.Pool and allocation pressure; GC and goroutine count are related costs.
Go · 02

Channels

A channel is a typed, synchronised handoff. Unbuffered channels are a rendezvous: the send does not complete until someone receives. Buffered channels are a bounded queue — and that bound is the backpressure from the foundations section, expressed in one integer.

// Bounded fan-out: 8 workers, backpressure built in, cancellable.
func process(ctx context.Context, jobs <-chan Job) error {
    g, ctx := errgroup.WithContext(ctx)
    for i := 0; i < 8; i++ {          // fixed concurrency, not one per job
        g.Go(func() error {
            for {
                select {
                case j, ok := <-jobs:
                    if !ok {           // channel closed: clean exit
                        return nil
                    }
                    if err := handle(ctx, j); err != nil {
                        return err     // cancels ctx for the whole group
                    }
                case <-ctx.Done():     // someone else failed, or caller gave up
                    return ctx.Err()
                }
            }
        })
    }
    return g.Wait()                    // first error, after all workers stop
}
L1 · Beginner

Send, receive, close

  • ch <- v sends, v := <-ch receives; both block until the other side is ready.
  • make(chan T) vs make(chan T, n).
  • close(ch) then for v := range ch to drain; sending on a closed channel panics.
  • Directional types in signatures — <-chan T and chan<- T document intent and are checked by the compiler.
L2 · Intermediate

Compose them

  • select with ctx.Done() is the shape of nearly every production loop.
  • default: makes a non-blocking try — useful for drop-on-full metrics, dangerous as a busy loop.
  • Pipelines, fan-out/fan-in, and closing a downstream stage only after every upstream sender has finished.
  • Buffered channel of capacity N as a semaphore around an expensive resource.
  • time.After in a hot loop allocates a timer per iteration; prefer time.NewTimer and stop it.
L3 · Advanced

Know when not to

  • "Share memory by communicating" is a default, not a law. For a hot counter or a shared map, sync.Mutex or sync/atomic is simpler and faster — a channel op costs far more than an uncontended lock.
  • Unbuffered send/receive establishes a happens-before edge; that is the memory-model reason channels are safe.
  • Deadlock shapes: circular pipelines, sending to yourself, and waiting on a channel nobody will close.
  • Every channel needs a documented owner: who sends, who closes, who drains on cancellation.
  • Draining before returning matters — abandoning a producer that is mid-send leaks it.
Go · 03

Interfaces

Go interfaces are satisfied implicitly: a type implements one by having the methods, with no declaration anywhere. That inverts the usual dependency direction — the consumer declares what it needs, and packages it never heard of already satisfy it.

L1 · Beginner

Behaviour, not hierarchy

  • No implements keyword — matching method sets is enough.
  • io.Reader / io.Writer: one method each, and half the standard library composes through them.
  • Pointer vs value receivers decide the method set: methods on *T are not in T's set. This is the usual "does not implement" compile error.
  • The empty interface any means "no information" — a smell in most signatures.
L2 · Intermediate

Seams and idiom

  • Accept interfaces, return structs — callers stay flexible, you keep freedom to add methods.
  • Typed-nil trap — a nil *T assigned to an interface is non-nil.
  • Type assertion v, ok := x.(T) and type switches for handling a closed set of cases.
  • Embedding for composition and decorators (a logging or caching wrapper that satisfies the same interface).
  • Compile-time check: var _ Store = (*Repo)(nil).
L3 · Advanced

Cost and restraint

  • Dynamic dispatch blocks inlining; boxing a value into an interface can force a heap allocation. Read -gcflags=-m before optimising.
  • Interface pollution — interfaces invented up-front, with one implementation, for a mock nobody needed. Wait for the second implementation.
  • Generics vs interfaces: generics for one algorithm over many types with no dispatch cost; interfaces for many behaviours behind one call site.
  • Adding a method is a breaking change for every external implementer — interfaces are API surface.
  • Reflection (encoding/json, ORMs) is convenient and measurably slow on hot paths.
Go · 04

Error handling

Errors in Go are ordinary values returned alongside results. There is no invisible unwinding path: every failure is a branch you can see in the diff — which is verbose, and is also why Go code is unusually easy to review for correctness.

// Layer boundary: add context going up, decide only at the top.
func (s *Service) Invoice(ctx context.Context, id string) (*Inv, error) {
    inv, err := s.repo.Get(ctx, id)
    if err != nil {
        // %w preserves the chain; the id is context only this layer has.
        return nil, fmt.Errorf("invoice %s: %w", id, err)
    }
    return inv, nil
}

// The one place that translates errors into a response.
func (h *Handler) Get(w http.ResponseWriter, r *http.Request) {
    inv, err := h.svc.Invoice(r.Context(), chi.URLParam(r, "id"))
    switch {
    case err == nil:
        writeJSON(w, 200, inv)
    case errors.Is(err, sql.ErrNoRows):
        http.Error(w, "not found", 404)          // expected, not an incident
    case errors.Is(err, context.DeadlineExceeded):
        http.Error(w, "timeout", 504)            // retryable, upstream slow
    default:
        h.log.Error("get invoice", "err", err)   // logged once, here
        http.Error(w, "internal", 500)
    }
}
L1 · Beginner

Errors are values

  • if err != nil immediately after the call; handle before continuing.
  • errors.New and fmt.Errorf; sentinel errors like ErrNotFound as package-level vars.
  • No exceptions. panic is for programmer bugs and unrecoverable startup failures, not for control flow.
  • defer for cleanup — and remember it runs at function exit, not scope exit.
L2 · Intermediate

Wrap, inspect, decide once

  • %w to wrap; errors.Is for identity, errors.As for type and fields.
  • Custom error types carrying structured data (field name, retry-after, status).
  • Do not log and return — pick one. Handling means the error stops here.
  • recover() only at a boundary (HTTP middleware, a worker loop) so one bad request cannot kill the process.
  • Add context that the caller cannot reconstruct; skip context it already has.
L3 · Advanced

Errors as an API

  • Taxonomy: retryable / terminal / programmer bug. It drives the retry, breaker and DLQ decisions from Pillar A.
  • context.Canceled (caller left — often not an error worth paging on) vs DeadlineExceeded (you were too slow — it is).
  • Structured errors carrying a stable code, mapped once to HTTP/gRPC status at the edge.
  • Which errors you return is public API — changing a sentinel breaks callers as surely as changing a signature.
  • Errors as telemetry: a bounded code dimension on metrics and spans, never the raw message (unbounded cardinality).
  • In concurrency: errgroup returns the first error — decide deliberately whether the others matter.
Pillar C

Cloud & infrastructure

AWS and Kubernetes are not new concepts — they are the same six foundations sold as products and expressed as YAML. A queue is SQS. A copy is a read replica. A boundary is a security group, a limit, or an availability zone. What is genuinely new is that the boundaries are now configuration, which means they can be wrong in a pull request.

Deep dive: From Account to Pod →

Cloud · 01

The AWS mental model: accounts, regions, zones

Before any service, learn the geography — because that geography is the blast radius from the fault-tolerance section, drawn on a map. Almost every AWS availability decision is really a question about which of these boxes you are willing to lose.

L1 · Beginner

The map and the vocabulary

  • Account → region → AZ; an AZ is one or more real datacentres, a region is a set of them.
  • The core nouns: EC2 (a machine), S3 (objects), RDS (managed SQL), IAM (who may do what), CloudWatch (metrics and logs).
  • Shared responsibility: AWS runs the hardware and the service; you own configuration, identity, and your data.
  • Everything is an API. The console is one client — the CLI and SDK are the same calls.
L2 · Intermediate

Build it reproducibly

  • Infrastructure as code (Terraform / CDK / CloudFormation). Console changes are undocumented, unreviewable, and unrepeatable.
  • Multi-AZ by default for load balancers, node groups and databases.
  • Roles, not access keys — instance profiles and short-lived STS credentials over anything long-lived in an env var.
  • Tags drive cost allocation and ownership; untagged infra becomes nobody's.
  • Alarms on symptoms (latency, error rate, queue age), not just CPU.
L3 · Advanced

Boundaries, limits and money

  • Multi-account org with SCPs — the strongest blast-radius control AWS offers. Prod separate from everything.
  • Control plane vs data plane: during a big regional event, launching new capacity often fails while running capacity keeps serving. Design recovery that does not need the control plane.
  • Service quotas are a fault mode — hitting a limit looks exactly like an outage. Track and raise them before launch.
  • Cost is architecture: cross-AZ traffic, NAT gateway data processing and egress quietly dominate bills; VPC endpoints and AZ-aware routing are design choices.
  • RTO/RPO stated as numbers, and a restore you have actually rehearsed.
Cloud · 02

Networking and identity: the two things you can get badly wrong

The VPC decides what can reach what; IAM decides who may ask. Nearly every cloud incident that is not a capacity problem is one of these two misconfigured — usually in the permissive direction.

L1 · Beginner

Wires and doors

  • VPC, subnet, route table; public = has a route to the internet gateway.
  • Security group = stateful allow-list attached to a resource; there is no "deny" rule.
  • Load balancer in front, instances behind, health checks deciding who gets traffic.
  • IAM user / role / policy: a policy is JSON granting actions on resources.
L2 · Intermediate

Layouts that hold up

  • Public / private / isolated subnet tiers; databases never in a public subnet.
  • SG vs NACL — stateful per-resource vs stateless per-subnet.
  • NAT gateway for outbound, VPC endpoints to keep S3/DynamoDB traffic private and off the NAT meter.
  • ALB vs NLB (HTTP-aware and flexible vs L4, fast, static IPs); target group health checks are your readiness signal.
  • Roles assumed via STS, secrets in Secrets Manager or SSM — never in an image or a repo.
L3 · Advanced

Least privilege that survives contact

  • Policy evaluation order and why explicit deny plus SCPs are the only real guardrails.
  • IRSA / Pod Identity — per-pod AWS roles in EKS instead of one over-powered node role that every workload inherits.
  • Conditions (source VPC endpoint, MFA, tag matching) turn a coarse policy into a precise one.
  • Identity vs resource policies, cross-account trust, and confused-deputy protection.
  • Least privilege is a process: start broad in dev, tighten from CloudTrail's record of what was actually called, and use Access Analyzer to catch public exposure.
Cloud · 03

Managed services are the foundations, rented

Every service below is one of the six foundations with an SLA attached. Choosing well means knowing which concept you are buying — and which part of the concept you still own, because managed never means "no longer your problem".

Foundation AWS service What it genuinely removes What is still yours
Messaging queue SQS (standard / FIFO) Durability, scaling, redelivery, DLQ plumbing. Idempotent consumers; a visibility timeout longer than your slowest handler; draining the DLQ.
Event log Kinesis / MSK Retention, replay, ordered partitions. The partition key — and therefore your ordering guarantee and your hot-shard risk.
Event routing SNS / EventBridge Fan-out, filtering, cross-account delivery. Schema evolution and knowing who your subscribers are.
Caching ElastiCache / CloudFront Running Redis, failover, edge presence. Invalidation, key design, stampede protection, what a cold cache does to the origin.
Indexing & storage RDS / Aurora Backups, patching, Multi-AZ failover, replicas. Schema, indexes, query plans, connection limits — and 60–120s of rejected writes during failover.
Indexing at scale DynamoDB Horizontal scale with predictable single-digit-ms reads. Access patterns up front; the partition key is the index and the hot-key limit; GSIs cost writes.
Durability S3 Effectively unlimited, eleven nines of durability, versioning. Lifecycle rules, request cost at high QPS, and never making a bucket public by accident.
Fault tolerance ALB + Auto Scaling / EKS Health-checked routing, capacity replacement, multi-AZ spread. Meaningful health checks, scale-up latency, and every quota you are one traffic spike from.
L1 · Beginner

Know what each one is for

  • Files → S3. Relational data → RDS. Key-value at scale → DynamoDB. Work to do later → SQS. Hot reads → ElastiCache.
  • Compute ladder: Lambda (per request) → ECS/Fargate (containers, no nodes) → EKS (Kubernetes) → EC2 (machines).
  • Managed = AWS runs it, you configure it and you are still on call for how you use it.
L2 · Intermediate

Choose with reasons

  • RDS vs DynamoDB: flexible queries and joins, or known access patterns and horizontal scale. Picking Dynamo without knowing your queries is the classic regret.
  • SQS standard vs FIFO — throughput and at-least-once, vs ordering per group at much lower throughput.
  • SNS vs EventBridge vs Kinesis: fan-out, routed integration, or a replayable ordered stream.
  • Lambda vs a container: bursty and event-shaped, vs steady traffic, long connections, or big dependencies.
  • Autoscaling on the metric that reflects the work — queue depth or lag, not just CPU.
L3 · Advanced

The fine print that pages you

  • DynamoDB partition keys reproduce every hot-key and skew problem from Pillar A, with a hard per-partition throughput ceiling.
  • Lambda: cold starts, per-account concurrency, and one runaway function starving every other function in the account.
  • RDS connection limits vs a fleet of pods each holding a pool — a proxy or a pool budget is not optional.
  • Failover is not free: writes are rejected during it, so clients need retry with backoff and the app needs to survive a minute of read-only.
  • Lock-in and exit cost as an explicit, priced decision rather than a slogan.
  • Every managed service has a quota; quota exhaustion presents as an outage with a healthy dashboard.
Cloud · 04

Kubernetes: one idea, repeated everywhere

Kubernetes is a database of desired state plus a crowd of controllers that continuously try to make reality match it. Every object, every feature, and every surprising behaviour follows from that one sentence.

L1 · Beginner

The objects you touch daily

  • Pod (unit of running), Deployment (manages pods), Service (stable address), Ingress (external entry), Namespace (grouping).
  • ConfigMap and Secret for configuration; environment differences belong here, not in the image.
  • Declarative YAML plus kubectl apply; get, describe, logs, and get events are the debugging loop.
  • Containers log to stdout; the platform collects them.
L2 · Intermediate

Model your workload correctly

  • Labels and selectors as the wiring; a typo here is a silent routing bug, not an error.
  • Deployment vs StatefulSet vs DaemonSet vs Job — stateless replicas, stable identity and storage, one per node, run-to-completion.
  • Rollback is instant because the previous ReplicaSet still exists.
  • Namespaces + RBAC + ResourceQuota as the multi-team boundary.
  • On EKS: IRSA for AWS permissions per service account, and the AWS load balancer controller turning Ingress into a real ALB.
L3 · Advanced

Extend it, and know its edges

  • CRDs and operators — the same reconcile loop over your own types; the correct place for domain-specific automation.
  • Admission control (validating and mutating webhooks, policy engines) to enforce standards at write time rather than in review.
  • etcd is the system of record: its size, latency and backups are the cluster's real limits.
  • Data plane survives the control plane — design deploys and recovery so they do not require an API server that may itself be degraded.
  • Networking depth: CNI, kube-proxy vs eBPF, NetworkPolicy as the in-cluster equivalent of security groups (default-open until you write one).
Cloud · 05

Health, rollouts and shutdown

Probes are how your process tells the cluster what it can do right now, and the rolling update is entirely gated on them. Getting the three probes wrong is the most common way a healthy application becomes an outage on a busy afternoon.

Cloud · 06

Resources, scheduling and scaling

Requests are a promise the scheduler makes to your pod; limits are a promise your pod makes to the node. CPU and memory break that promise in completely different ways, and knowing which is which is most of Kubernetes performance debugging.

L1 · Beginner

Ask for what you need

  • Requests = reserved for scheduling. Limits = the ceiling.
  • Always set both for memory; set CPU requests at minimum.
  • kubectl top, and reading OOMKilled / CrashLoopBackOff in describe.
  • More replicas is horizontal scaling; a bigger pod is vertical. Prefer horizontal for stateless work.
L2 · Intermediate

Place and scale deliberately

  • CPU throttling vs OOMKill — two entirely different symptoms; check throttling metrics before blaming the code.
  • QoS classes decide eviction order under node pressure.
  • topologySpreadConstraints across AZs and nodes, so three replicas are not three pods on one machine in one AZ.
  • PodDisruptionBudget so node upgrades and scale-downs cannot drain your service to zero.
  • HPA on a custom or external metric; Cluster Autoscaler / Karpenter for nodes.
L3 · Advanced

Density, tails and money

  • Should you set CPU limits at all? A real trade: limits give predictable neighbours, and cause p99 throttling even on an idle node. Decide per workload, with data.
  • Go on Kubernetes: without GOMAXPROCS awareness the runtime sizes itself to the node's cores, not your CPU quota — instant throttling under load.
  • Scaling latency budget end to end; combine headroom, pre-scaling and load shedding rather than trusting the autoscaler alone.
  • Spot capacity with interruption handling, plus PDBs and spread — large savings, only if the workload is genuinely disposable.
  • Bin packing vs blast radius: denser nodes are cheaper and make each node failure hurt more.
Synthesis

One level up: it is all the same four moves

Studied separately, these look like sixteen topics. Studied together, they are four moves applied to different resources — Go's features are the in-process version, and AWS and Kubernetes are the rented version. That collapse is what "deep foundations" means in practice: you meet an unfamiliar system and already know which four questions to ask.

Everything at once: one request through one service

Here is a single order-placement path with every concept on this page marked where it actually appears, and the infrastructure it lands on written underneath. If you can narrate this diagram out loud — including what happens when each box is slow, when each box is dead, and which AZ each one lives in — you are answering the job description.

The four questions to ask about any box on any diagram

1. Where is the queue, and is it bounded?  2. What is the contract, and who breaks if it changes?  3. What happens when this is slow — who waits, and for how long?  4. What happens when this is dead — do we degrade, queue, or fail?  Most senior interviews and most postmortems are these four questions in a trench coat.

If you only take three things into the interview

Backpressure — every buffer must be bounded, and a full buffer must slow the producer rather than silently grow. Idempotency — it is what makes retries, queues, replays, outboxes and every at-least-once managed service safe, and it is a design decision, not a library. Blast radius — goroutine, pod, node, AZ, region, account: name the boundary you are willing to lose, and check that no single component quietly spans all of them.

How to use this page. Pick one row of the self-check table per week. Read the L2 column and build the smallest thing that exercises it — a worker pool with a bounded channel, a cache-aside layer with a stampede test, an outbox with a deliberate crash between commit and publish. The L3 column is what you will be able to say afterwards, from having watched it break.
