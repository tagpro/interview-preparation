Part four

Compute: Lambda and ECS

Two ways to run your code, with different units of scaling: Lambda scales the number of concurrent invocations, ECS scales the number of long-lived processes. Almost every difference in cost, latency and operational feel follows from that.

AWS · 00

Lambda: the execution environment is the whole model

A Lambda function is not invoked — an execution environment is created, initialised, then used for many invocations, frozen between them, and eventually destroyed. Cold starts, connection reuse, background threads and half the surprises all live in that lifecycle.

Reserved concurrencyBoth a floor and a ceiling for one function: it is guaranteed that much, and can never exceed it. The blast-radius control — set it on anything that talks to a database.
Provisioned concurrencyEnvironments kept initialised and warm, billed by the hour. The only real fix for cold-start-sensitive user-facing paths, and it can be scheduled or autoscaled.
SnapStartSnapshots the environment after init and restores from it — large cold-start wins for Java, Python and .NET. Your init must not bake in anything unique, such as a random seed or an open socket.
Scaling rateA function can add on the order of 1,000 concurrent executions every 10 seconds, up to the account limit. A genuine spike is throttled at the edge of that ramp, not at the account cap.

The handler shape that gets everything right

Clients built at module scope, per-invocation deadlines derived from the remaining time, and partial batch failure reporting so one poison message does not replay the other nine.

// main.go — Go runs on provided.al2023 as a custom runtime; the binary is the
// runtime. Everything above main() happens once, during INIT, with full CPU.
var (
    cfg = mustConfig()                          // credential chain resolved once
    ddb = dynamodb.NewFromConfig(cfg)           // pool survives across invocations
    log = slog.New(slog.NewJSONHandler(os.Stdout, nil))
)

func handle(ctx context.Context, ev events.SQSEvent) (events.SQSEventResponse, error) {
    // Leave headroom: finish, flush and return before Lambda kills us.
    if dl, ok := ctx.Deadline(); ok {
        var cancel context.CancelFunc
        ctx, cancel = context.WithDeadline(ctx, dl.Add(-500*time.Millisecond))
        defer cancel()
    }

    // Partial batch response: without this, ONE bad message redelivers all ten,
    // which is how a single poison record becomes a permanent replay loop.
    var failures []events.SQSBatchItemFailure

    for _, m := range ev.Records {
        if err := process(ctx, m); err != nil {
            log.Error("record failed", "message_id", m.MessageId, "err", err)
            failures = append(failures, events.SQSBatchItemFailure{
                ItemIdentifier: m.MessageId,
            })
        }
    }
    // Return nil error: the batch itself succeeded. Only the listed ids return
    // to the queue. Requires ReportBatchItemFailures on the event source mapping.
    return events.SQSEventResponse{BatchItemFailures: failures}, nil
}

func main() { lambda.Start(handle) }
# handler.py — everything at module scope runs once, during INIT, with full
# CPU. Imports and client construction belong here, not in the handler.
import json, os, time
import boto3
from aws_lambda_powertools import Logger, Metrics, Tracer
from aws_lambda_powertools.utilities.batch import (
    BatchProcessor, EventType, process_partial_response,
)

logger, tracer, metrics = Logger(), Tracer(), Metrics()
DDB = boto3.client("dynamodb")          # connection pool survives invocations
TABLE = os.environ["TABLE_NAME"]

processor = BatchProcessor(event_type=EventType.SQS)


@tracer.capture_method
def record_handler(record):
    body = json.loads(record.body)
    DDB.put_item(
        TableName=TABLE,
        Item={"pk": {"S": body["id"]}, "payload": {"S": record.body}},
        ConditionExpression="attribute_not_exists(pk)",   # at-least-once delivery
    )


@logger.inject_lambda_context
@tracer.capture_lambda_handler
@metrics.log_metrics                    # flushes EMF metrics BEFORE the freeze
def handler(event, context):
    # Partial batch response: without this, ONE bad message redelivers all ten,
    # which is how a single poison record becomes a permanent replay loop.
    # Requires ReportBatchItemFailures on the event source mapping.
    return process_partial_response(
        event=event, record_handler=record_handler,
        processor=processor, context=context,
    )

Tune memory with data, not instinct

Duration typically falls faster than price rises, up to the point where the function stops being CPU-bound. Sweep 512 MB to 3 GB against a real payload and plot cost per invocation — the minimum is often at three or four times the memory somebody guessed, and it is faster as well as cheaper.

Arm64 unless something stops you

Graviton pricing is roughly 20% lower per GB-second and the same code is usually a little faster. The only reasons to stay on x86 are a native dependency with no aarch64 wheel or binary, and a container image you have not rebuilt.

ECS and Fargate: the deployment is the interesting part

A task definition is easy. What decides whether ECS is calm is the deployment configuration — the percentages, the circuit breaker, the health check grace period and the shutdown sequence, all of which have defaults that will eventually hurt.

Piece of the task definitionWhat it controlsThe detail
taskRoleArnThe IAM role your code assumesDelivered over the container credentials endpoint. This is the role your SDK picks up.
executionRoleArnThe role ECS itself usesPulls the image from ECR, writes the log stream, and reads the secrets you inject. Confusing these two is the classic first-deploy failure.
networkMode: awsvpcOne ENI, one private IP, per taskThe task gets its own security group. It also consumes a subnet address, and ENI attachment adds several seconds to task start.
secretsEnvironment variables from Secrets Manager or SSMResolved at task start by the execution role, so a rotated secret needs a new task — not a restart of your process.
Container healthCheckWhether ECS considers the container healthySeparate from the load balancer’s check. Use both: the container check catches a wedged process with no traffic on it.
stopTimeoutSIGTERM to SIGKILLDefault 30s, maximum 120s on Fargate. If your drain is longer than this, the drain does not happen.
cpu / memoryFargate’s billable sizeOnly certain combinations are valid, and the whole task is billed on the total — a fat sidecar costs the same as fat application.

Shut down properly, or drop requests forever

// The four-stage shutdown ECS expects. Nothing here is Go-specific except the
// syntax — the sequence is what matters.
srv := &http.Server{Addr: ":8080", Handler: mux}

go func() {
    if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
        log.Error("listen", "err", err)
        os.Exit(1)
    }
}()

sig := make(chan os.Signal, 1)
signal.Notify(sig, syscall.SIGTERM, syscall.SIGINT)
<-sig

// 1. Fail readiness first, so the load balancer stops sending new requests
//    even before ECS deregisters us. A few seconds of overlap is deliberate.
ready.Store(false)
time.Sleep(5 * time.Second)

// 2. Stop accepting, finish what is in flight. Shutdown does exactly this.
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    log.Warn("graceful shutdown timed out", "err", err)   // stopTimeout must exceed 25s
}

// 3. Then, and only then, release everything downstream.
pool.Close()
_ = tracerProvider.Shutdown(ctx)

# draining, but the readiness flip in front of it is yours to write.
import signal, asyncio, contextlib, uvicorn

READY = True


@app.get("/readyz")
async def readyz():
    # 1. Fail readiness first, so the load balancer stops sending new requests
    #    even before ECS deregisters us. A few seconds of overlap is deliberate.
    return Response(status_code=200 if READY else 503)


# Run uvicorn programmatically, so the signal handler can hand the signal
# back to it. The graceful timeout must be SHORTER than stopTimeout.
server = uvicorn.Server(uvicorn.Config(
    app, host="0.0.0.0", port=8080,
    timeout_keep_alive=75,             # above the ALB idle timeout
    timeout_graceful_shutdown=20,      # below stopTimeout, which we set to 60
))


@contextlib.asynccontextmanager
async def lifespan(app):
    loop = asyncio.get_running_loop()

    def _term():
        global READY
        READY = False
        # Installing this handler REPLACED uvicorn’s own, so we have to pass
        # the signal on — otherwise nothing drains and ECS just SIGKILLs us.
        loop.call_later(5.0, server.handle_exit, signal.SIGTERM, None)

    loop.add_signal_handler(signal.SIGTERM, _term)
    yield
    # 2. By the time teardown runs, uvicorn has stopped accepting and has
    #    already waited out the in-flight requests.

Autoscale on the right signal

Target tracking on ALBRequestCountPerTarget beats CPU for a web service: it reacts to arriving work rather than to the symptom of work. Keep a scale-in cooldown longer than the scale-out one, and remember that scaling is bounded by how fast a task can start — image pull plus ENI attach plus your own init.

Fargate Spot is real capacity with a real catch

Around 70% cheaper, and reclaimed with a two-minute SIGTERM warning. Perfect for queue consumers that checkpoint, wrong for anything holding a long request. Mix capacity providers: a base of on-demand tasks with the elastic portion on Spot.

Choosing between them, with arithmetic

The Lambda-versus-containers argument is usually settled by taste. It should be settled by two numbers: your requests per second and your p50 duration, which together tell you exactly where the crossover sits.

// Work out the crossover instead of arguing about it. Prices are illustrative
// US-East-1 list rates — substitute your own before quoting anyone.
const (
    lambdaPerGBSecond = 0.0000166667
    lambdaPerRequest  = 0.0000002
    fargateVCPUHour   = 0.04048       // x86; Graviton and Spot are cheaper
    fargateGBHour     = 0.004445
)

// One Lambda invocation: memory in GB, duration rounded up to the millisecond.
func lambdaMonthly(reqsPerMonth float64, memGB, durSec float64) float64 {
    return reqsPerMonth*(lambdaPerRequest+memGB*durSec*lambdaPerGBSecond)
}

// A Fargate task charges whether or not a request arrives.
func fargateMonthly(tasks, vcpu, memGB float64) float64 {
    return tasks * 730 * (vcpu*fargateVCPUHour + memGB*fargateGBHour)
}

// 40 ms at 512 MB, against two 0.5 vCPU / 1 GB tasks:
//   5M requests/month   Lambda $2.67   Fargate $36.04   → Lambda, easily
//   500M requests/month Lambda $267    Fargate $36.04   → containers, easily
// The crossover is near 68M requests — but only if the tasks can actually
// serve them. Capacity check first: reqs/sec x duration must fit in
// tasks x concurrency_per_task, or you are comparing against a fantasy.
fmt.Printf("%.2f vs %.2f\n",
    lambdaMonthly(5e6, 0.5, 0.04), fargateMonthly(2, 0.5, 1))
# Work out the crossover instead of arguing about it. Prices are illustrative
# US-East-1 list rates — substitute your own before quoting anyone.
LAMBDA_GB_SECOND = 0.0000166667
LAMBDA_REQUEST = 0.0000002
FARGATE_VCPU_HOUR = 0.04048        # x86; Graviton and Spot are cheaper
FARGATE_GB_HOUR = 0.004445


def lambda_monthly(reqs: float, mem_gb: float, dur_s: float) -> float:
    # One invocation: memory in GB, duration rounded up to the millisecond.
    return reqs * (LAMBDA_REQUEST + mem_gb * dur_s * LAMBDA_GB_SECOND)


def fargate_monthly(tasks: float, vcpu: float, mem_gb: float) -> float:
    # A Fargate task charges whether or not a request arrives.
    return tasks * 730 * (vcpu * FARGATE_VCPU_HOUR + mem_gb * FARGATE_GB_HOUR)

If this is trueChoose
Traffic is spiky, occasional, or zero most of the timeLambda — nothing else bills at zero
A request can take longer than fifteen minutesFargate or EC2; Lambda cannot, at any price
You need a persistent connection pool, or a warm in-process cacheFargate or EC2. Lambda can hold one per environment, and you do not control how many there are
