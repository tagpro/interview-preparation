Part eight

What the standard library already gives you

Nearly every structure on this page is already implemented, tested against adversarial inputs and tuned for the hardware, in the runtime you are using. The valuable knowledge is not how to write them — it is knowing which one you are reaching for, what it costs, and which of them your language gets conspicuously wrong.

// Iterators (1.23) let you write algorithms that compose without
// materialising intermediate slices.
func Filter[T any](s iter.Seq[T], keep func(T) bool) iter.Seq[T] {
    return func(yield func(T) bool) {
        for v := range s {
            if keep(v) && !yield(v) {
                return                           // the consumer stopped early
            }
        }
    }
}

map.computeIfAbsent(key, k -> new ArrayList<>()).add(v);   // group
map.compute(key, (k, v) -> v == null ? init : update(v));

The mistakes each language invites

Every runtime has a small set of data-structure errors that its own design makes easy. They are not exotic; they are the ones that reach production, survive review, and are eventually found by a profiler or an incident. Here they are, per language, with the fix.

LanguageThe mistakeWhat it costs, and the fix
GoSub-slicing a large buffer and keeping the small resultThe whole backing array stays reachable. A 10-byte slice of a 100 MB read holds 100 MB. Fix: slices.Clone.
Goappend to a slice a caller also holdsWhether the write is visible depends on spare capacity, so the bug is intermittent. Fix: three-index slicing xs[a:b:b], or document that append is the caller’s job.
GoAssuming a map ever releases memoryMaps never shrink. Fix: rebuild into a fresh map when the live set is a small fraction of the peak.
Pythonin on a list inside a loopSilent O(n²). Fix: build a set once, before the loop.
Pythonlist.pop(0) or insert(0, ...) as a queueSilent O(n²). Fix: collections.deque.
PythonString concatenation in a loopQuadratic copying. Fix: collect into a list and "".join(parts).
PythonA mutable default argument, or [[0]*n]*mShared state across calls or rows. Fix: None plus a check, and a comprehension for the grid.
JavahashCode and equals disagreeing, or a mutable keyEntries become unreachable and un-removable — a leak plus a correctness bug. Fix: use a record.
JavaIterating a PriorityQueue and expecting sorted orderIt is heap order, which looks sorted for small inputs and is not. Fix: repeated poll(), or sort a copy.
JavaA comparator built from subtractiona - b overflows for large or negative values, and Timsort throws “violates its general contract”. Fix: Comparator.comparingInt.
JavaLinkedList, Vector, Stack, HashtableAll four are worse versions of something else. Fix: ArrayList, ArrayDeque, HashMap.
All threeSorting to get the top tenO(n log n) where O(n log k) would do, and it buffers everything. Fix: a bounded heap.
All threeRecursing to a depth the input controlsStack exhaustion, which is a crash rather than an exception. Fix: an explicit stack, or a hard depth limit.
 
// pitfalls.go — the three that cause real incidents, and their fixes.

// 1. The slice that pins a hundred megabytes.
func ExtractIDBad(r io.Reader) []byte {
    data, _ := io.ReadAll(r)                     // 100 MB
    return data[10:42]                           // 32 bytes; the 100 MB stays alive
}

func ExtractID(r io.Reader) []byte {
    data, _ := io.ReadAll(r)
    return slices.Clone(data[10:42])             // 32 bytes, and only 32
}

// 2. The loop variable that used to be shared. Fixed in Go 1.22 -- each
// iteration now gets its own variable -- but the same shape still bites
// when you take the address of a range value over a slice of structs.
for _, item := range items {
    out = append(out, &item)                     // 1.22+: fine. Before: all same
}

// 3. Growing a map forever. A map that peaked at 10 million keys keeps
// its buckets after every key is deleted.
if len(cache) < cap(keys)/4 {                    // live set is a quarter of peak
    fresh := make(map[string]Entry, len(cache))
    maps.Copy(fresh, cache)
    cache = fresh                                // the old buckets become garbage
}

# 1. Membership on a list. This is O(n*m) and reads as if it were O(n).
missing = [x for x in candidates if x not in known_list]     # slow
known = set(known_list)                                      # once, O(m)

# 2. A list used as a queue.
while queue:
    item = queue.pop(0)                          # O(n) each: shifts everything

# 3. String building.
out = ""
for row in rows:
    out += render(row)                           # O(n^2) copying
out = "".join(render(row) for row in rows)       # O(n)

# 4. The mutable default: evaluated ONCE, at definition time, and then
# shared by every call that does not pass one.
def add(item, bucket=[]):                        # wrong
    bucket.append(item)
    return bucket

def add(item, bucket=None):                      # right
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

# 5. Mutating a list while iterating it. The iterator holds an index,
# so a removal makes it skip the next element -- silently.
for x in list(xs):                               # iterate a copy, or
    if drop(x):
        xs.remove(x)
xs = [x for x in xs if not drop(x)]              # better: one pass, no removal
// Pitfalls.java — the ones that survive code review.

// 1. A mutable key. After the set() the entry is unreachable AND
// un-removable: it hashes to a different bin than the one it is in.
Map<Point, String> map = new HashMap<>();
Point p = new Point(1, 2);
map.put(p, "a");
p.setX(9);                                       // the entry is now lost forever
map.get(p);                                      // null
map.remove(p);                                   // does nothing; the memory stays
// Fix: record Point(int x, int y) {} -- immutable, equals and hashCode free

// 2. Comparator by subtraction. Fine until the values are large.
Comparator<Item> broken = (a, b) -> a.id() - b.id();
Comparator<Item> fixed = Comparator.comparingInt(Item::id);

// 3. Removing while iterating. Fail-fast, so at least it throws.
for (String s : list) if (drop(s)) list.remove(s);   // ConcurrentModification
list.removeIf(this::drop);                           // one pass, correct

// 4. Boxing in a hot loop. Every ++ unboxes, adds, and boxes again --
// an allocation per iteration above the Integer cache of 127.
Map<String, Integer> counts = new HashMap<>();
counts.merge(key, 1, Integer::sum);              // still boxes, but once per call
// For a fixed key space, int[] indexed by an enum ordinal boxes never.

// 5. Arrays.asList is a fixed-size VIEW over the array, not a copy.

The order to think in

When something is slow, work down this list rather than reaching for the clever structure first. One: is there an accidental quadratic — a membership test, a removal, or a string concatenation inside a loop? That is the majority of real cases and the fix is usually one line. Two: is the work being repeated — would a cache, a prefix sum or a memo remove it? Three: is the data laid out badly — boxed values, pointer chasing, a map where an array would do? Four, and only then: is a different algorithm needed? Most performance work never gets past step one, and the engineers who look fastest are usually the ones who recognise it there.
