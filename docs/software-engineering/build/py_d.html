Part seven

The toolchain everyone assumes you have

None of what follows is in the language. It is the set of defaults the Python community converged on after twenty years of doing it badly — and it is what a reviewer will silently assume is already in place before they read a line of your code.

Python · 00

Environments, resolution, and lockfiles

A dependency range says what is allowed. A lockfile says what you actually got. Projects that ship only the first one discover the difference when CI and a laptop resolve the same range to different versions on different days.

# pyproject.toml — one file for metadata, dependencies and tool config
[project]
name = "payments"
requires-python = ">=3.13"
dependencies = ["httpx>=0.27,<0.29", "pydantic>=2.7", "sqlalchemy>=2.0"]

[dependency-groups]           # PEP 735: dev deps that are not shipped
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

# uv lock          → writes uv.lock, commit it
# uv sync --frozen → installs exactly the lock, fails if it is stale
# uv run pytest    → runs inside the project env, no activation needed

L1 · Beginner

Never install into the system Python

  • Virtual environment — a directory with its own site-packages; activating it just puts its bin/ first on PATH.
  • One env per project, never shared. Deleting .venv and recreating it should always be safe — if it is not, something is undeclared.
  • pyproject.toml is the single manifest: metadata, dependencies and tool configuration in one file.
  • .venv/ goes in .gitignore; the lockfile does not. PEP 751’s pylock.toml is the standard lockfile format — uv and pip can export and consume it, so the lock is no longer tool-proprietary.
  • Learn python -m pip, not bare pip — the -m form guarantees you are installing into the interpreter you think you are.
L2 · Intermediate

Commit the lockfile, install from it

  • Ranges in the manifest, exact versions in the lock. Loosen the range when you want an upgrade; regenerate the lock deliberately, in its own commit.
  • --frozen in CI and Docker — installs must fail rather than silently re-resolve when the lock is stale.
  • Extras and groups — test and lint dependencies live in a dev group so they never reach the production image.
  • Applications lock; libraries do not. A library publishes ranges, because pinning inside a library makes it uninstallable alongside anything else.
  • Pin the Python version too — requires-python plus a .python-version file.
L3 · Advanced

Understand what the resolver is doing

  • Resolution is a SAT problem over the whole graph. Backtracking resolvers can take minutes on a conflict, and the error names the pair that is unsatisfiable — read it rather than deleting pins at random.
  • Wheels vs sdists — a wheel is a prebuilt zip; falling back to an sdist means compiling on the target machine and needing a toolchain in your image.
  • Platform tags (manylinux, musllinux, macosx_arm64) decide which wheel you get. Alpine images miss manylinux wheels and rebuild from source — a common reason a Docker build is fifteen minutes.
  • Hash-pinned installs (--require-hashes) make a compromised index unable to substitute an artefact.
  • Multi-stage images — resolve and build in one stage, copy only site-packages into a slim runtime stage.

One formatter, one linter, three gates

Formatting stopped being a discussion when black shipped with no options. Linting stopped being five tools when ruff reimplemented them in one binary. What is left to decide is where the checks run — and the answer is all three places, with identical configuration.

# pyproject.toml — the whole quality config, in the file you already have
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM", "RUF", "ASYNC", "S"]
#  E/F pycodestyle+pyflakes · I imports · UP pyupgrade
#  B bugbear · SIM simplify · ASYNC async traps · S security
ignore = ["E501"]             # the formatter owns line length

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S101"]          # assert is the point of a test

The one rule set worth turning on deliberately

flake8-bugbear (B) is the highest-value group by a distance: it is the one that catches the mutable default argument, the loop variable captured by a closure, and except clauses that swallow everything. Those are the three bugs earlier in this page, found automatically, for free.

L1 · Beginner

Stop formatting by hand

  • Formatter — rewrites layout deterministically. ruff format is black-compatible; the output is not a matter of taste, and that is the feature.
  • Linter — finds likely mistakes: unused imports, undefined names, shadowed builtins, comparisons that are always true.
  • PEP 8 is the style baseline — but you should never be applying it manually.
  • Turn on format-on-save the day you start. Every formatting comment in a review is a wasted one.
  • ruff check --fix applies the safe fixes; read the diff before committing it.
L2 · Intermediate

Make the gate automatic

  • pre-commit — a hook manager with pinned tool versions in .pre-commit-config.yaml. pre-commit autoupdate bumps them in a reviewable commit.
  • Pin the linter version. An unpinned linter turns a new release into a red build on an unrelated PR.
  • Adopt on a large codebase by reformatting everything in one commit, then adding that SHA to .git-blame-ignore-revs so blame still works.
  • Select rules explicitly. select a named set rather than everything — a wall of warnings nobody triages is the same as no linter.
  • noqa needs a code and a reason: # noqa: S105 - test fixture, not a real key.
L3 · Advanced

Know what a linter cannot see

  • Lint is syntactic, types are semantic. Ruff will not tell you a function returns None on one branch; a type checker will. They are different gates, both needed.
  • Custom rules — when a bug class recurs, encode it: an AST check in CI, or a flake8 plugin. A rule that fires automatically beats a convention nobody remembers.
  • Security lint (bandit, ruff’s S rules) flags subprocess(shell=True), weak hashes and hard-coded secrets. High false-positive rate; still worth the triage.
  • Complexity budgets (C901, PLR0912) are blunt but real — they surface the function that needs splitting before a reviewer has to say it.
  • Formatter migrations change diffs, not behaviour. Do them alone, never inside a feature branch.
Python · 00

Type checking as a gate, not a hope

Annotations do nothing at run time. They are worth writing anyway — but only once something actually checks them, in CI, on every commit. The hard part is not the syntax; it is adopting a checker on a codebase that has none without stopping the world.

# pyproject.toml — strict everywhere, with named, temporary exceptions
[tool.mypy]
python_version = "3.13"
strict = true
warn_unreachable = true
warn_unused_ignores = true    # deletes the ignores you no longer need

[[tool.mypy.overrides]]       # the legacy corner, listed explicitly
module = ["payments.legacy.*"]
disallow_untyped_defs = false

[[tool.mypy.overrides]]       # a dependency that ships no stubs
module = ["some_untyped_lib.*"]
ignore_missing_imports = true
L1 · Beginner

Annotate the boundaries first

  • Function signatures pay for themselves. Parameters and return type on every public function; local variables almost never need one.
  • Install the checker as a dev dependency and run it locally — mypy . or pyright. Your editor is already running one, quietly.
  • None is a type. str | None is the single most useful annotation in the language, because it forces the caller to handle the missing case.
  • Do not annotate for the sake of it: x: int = 0 tells nobody anything.
  • Third-party stubs live in types-requests-style packages; install them when the checker asks.
L2 · Intermediate

Ratchet, and never go backwards

  • Per-module overrides keep the legacy corner listed by name, so the exceptions are visible and shrinking rather than a blanket ignore.
  • warn_unused_ignores turns stale suppressions into errors — the ratchet that stops the exception list growing quietly.
  • Protocol over inheritance for typing duck-typed arguments — the direct analogue of a Go interface, satisfied structurally.
  • Type the data at the edge — Pydantic at the boundary, plain dataclasses inside. The checker is only as good as the point where untyped data becomes typed.
  • Run the checker in CI on the whole tree, not just changed files — a change in one module breaks types in another.
L3 · Advanced

Where the type system gets interesting

  • TypeVar, ParamSpec, Concatenate — how a decorator keeps its wrapped function’s signature instead of collapsing it to (*args, **kwargs).
  • overload for functions whose return type depends on argument types, and Literal for the flags that select between them.
  • Narrowing — isinstance, assert, and TypeGuard/TypeIs teach the checker facts it cannot infer; match statements narrow too.
  • Variance bites in real code: list[Dog] is not a list[Animal], because you could append a Cat. Accept Sequence when you only read.
  • Any is contagious — it silences errors downstream of itself. --disallow-any-explicit and object plus narrowing are the honest alternatives.

Layout, naming, and version numbers

Two directory layouts are common and one of them lets your tests import a copy of the code that will never be installed. The naming conventions are trivial to learn and instantly visible in review, which is exactly why they are worth getting right.

Version numbers

SemVer (2.4.1) is the ecosystem default; CalVer (2026.8.1) is common for applications and tools where dates mean more than compatibility promises. Python’s own rules live in PEP 440, which also defines pre-releases (1.0.0rc1), post-releases and the ~= compatible-release operator. Keep one source of truth — usually version in pyproject.toml, read at run time via importlib.metadata.version().

The PEPs actually worth knowing

8 style · 20 the Zen · 257 docstrings · 440 versions · 484 type hints · 517/518/621 builds and pyproject.toml · 561 shipping types · 3107/526 annotation syntax. You do not read PEPs for fun; you read the one that explains why a tool is behaving the way it is.

L1 · Beginner

Follow the conventions without thinking

  • snake_case for anything callable or storable, PascalCase for classes, SCREAMING_SNAKE for module-level constants.
  • Four spaces. Never tabs; the formatter enforces it anyway.
  • One leading underscore means “not part of the API”. Nothing enforces it — Python has no private — and that is fine.
  • Never name a file after a standard library module. A local random.py or types.py shadows the real one and produces a genuinely baffling error.
  • Docstrings on public functions; PEP 257 for the shape, Google or NumPy style for the body.
L2 · Intermediate

Adopt the src layout

  • src/ makes the installed package the only importable one, so pip install -e . plus pytest tests the real artefact.
  • Editable installs (-e) put a path hook in site-packages; your edits are live, but the import path is still the installed one.
  • Keep tests/ outside the package unless you intend to ship them.
  • Layer by responsibility, not by type. payments/charge/ beats models/, views/, utils/ — a utils package is where cohesion goes to die.
  • Build the wheel and inspect it (unzip -l dist/*.whl) before your first release. What is missing is always a data file.
L3 · Advanced

Publishing and the import graph

  • __all__ defines the star-import surface and signals intent to tooling; py.typed (PEP 561) is what makes your annotations visible to a consumer’s checker.
  • Namespace packages let several distributions contribute to one import path — powerful for plugin ecosystems, confusing everywhere else.
  • Entry points in pyproject.toml give you console scripts and plugin discovery without an import-everything scan.
  • Trusted publishing to PyPI via OIDC removes the long-lived API token from CI entirely — the same identity-federation idea as IRSA on EKS.
  • Import cycles are an architecture smell. Enforce the layering mechanically with import-linter rather than by review.
