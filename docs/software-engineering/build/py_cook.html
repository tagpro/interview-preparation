Parsing an untrusted payload with Pydantic

The job: turn a JSON body you did not write into an object your code can trust. Pydantic does it in one call, and the important part is what it means afterwards — nothing downstream ever has to ask whether qty is a number.

# models.py — the contract, written once
from decimal import Decimal
from typing import Annotated, Literal, Self
from pydantic import BaseModel, ConfigDict, EmailStr, Field, field_validator, model_validator

Money = Annotated[Decimal, Field(gt=0, max_digits=12, decimal_places=2)]
Sku   = Annotated[str, Field(pattern=r"^[A-Z]{3}-\d{4}$")]

class LineItem(BaseModel):
    sku: Sku
    qty: Annotated[int, Field(ge=1, le=100)]
    price: Money

class CreateOrder(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)   # unknown key = error

    email: EmailStr
    currency: Literal["GBP", "EUR", "USD"]
    items: Annotated[list[LineItem], Field(min_length=1, max_length=50)]
    note: str | None = None
# two kinds of rule: one field, or the whole object
    @field_validator("note")
    @classmethod
    def strip_and_bound(cls, v: str | None) -> str | None:
        return v.strip()[:500] if v else None

    @model_validator(mode="after")                # runs once, after coercion
    def within_unattended_limit(self) -> Self:
        if sum(i.qty * i.price for i in self.items) > Decimal("10000"):
            raise ValueError("order exceeds the unattended limit")
        return self
# using it — the only three calls you need day to day
try:
    order = CreateOrder.model_validate(request_json)   # dict  -> object
except ValidationError as e:
    return 422, {"errors": e.errors(include_url=False)}

order.items[0].price * order.items[0].qty     # Decimal arithmetic, exact
payload = order.model_dump(mode="json")       # object -> JSON-safe dict
CreateOrder.model_json_schema()               # the OpenAPI schema, free

The same class does your configuration

pydantic-settings is the same machinery pointed at the environment, which is why the config topic earlier could promise “fails at start-up, not at 3am”: class Settings(BaseSettings): database_url: PostgresDsn; timeout_s: float = 2.0; api_key: SecretStr — then settings = Settings() at import raises immediately if API_KEY is missing or TIMEOUT_S is not a number. SecretStr also keeps the value out of every log line and traceback that repr the object.

L1 · Beginner

What the code does

  • BaseModel turns annotations into run-time checks — the one place in Python where a type hint has teeth.
  • Field carries the constraints: gt, ge, le, min_length, pattern. They land in the JSON schema too.
  • model_validate takes a dict and returns an instance or raises; model_dump goes back the other way.
  • Annotated[Decimal, Field(...)] names a reusable rule — Money is now one word you can put on any field.
  • ValidationError.errors() is a list of dicts, not a string. Return it as the response body.
L2 · Intermediate

Why it is written this way

  • extra="forbid" makes a typo in the client an error instead of a silently ignored field — the default is to drop unknown keys, which hides bugs for months.
  • frozen=True makes the parsed request immutable, so no later code can “fix up” the input and leave the log disagreeing with what happened.
  • Decimal for money, never float — and pydantic will coerce the string "12.50" straight to Decimal without going through binary floating point.
  • field_validator for one field, model_validator(mode="after") for a rule that needs several; mode="after" means every value is already the right type.
  • Separate the request model from the database model. They change for different reasons, and merging them is how internal columns end up in your public API.
L3 · Advanced

What bites in production

  • Validation is not free. v2’s core is Rust and fast, but validating the same object at four internal layers is four times the cost for no extra safety. Parse once, at the edge.
  • model_construct skips validation for data you already trust — useful on a hot path out of the database, dangerous anywhere near a socket.
  • Union order matters. Prefer a discriminated union (Field(discriminator="kind")) over a bare A | B: it picks by tag rather than by trying each in turn, and the errors name one branch instead of all of them.
  • ValidationError messages can leak input. Return type and loc to the caller; keep input for your logs, and never let a SecretStr reach either.
  • Generated schemas are a contract. If clients consume your OpenAPI, adding extra="forbid" or tightening a pattern is a breaking change — version it like one.

One endpoint, end to end

The job: accept an order, write it once, and return an answer the caller can retry safely. Four layers, each owning exactly one thing — and the transaction boundary drawn so a raised exception cannot leave half an order behind.

# deps.py — one session and one transaction per request
async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:      # closes, returns to the pool
        async with session.begin():            # COMMIT on clean exit,
            yield session                      # ROLLBACK on any exception
# routes.py — HTTP shapes in, HTTP shapes out, nothing else
router = APIRouter(prefix="/orders", tags=["orders"])

class OrderCreated(BaseModel):        # response contract ≠ request contract
    id: UUID
    status: Literal["accepted"]
    total: Decimal

@router.post("", status_code=201, response_model=OrderCreated)
async def create_order(
    body: CreateOrder,                                  # validated already
    idem_key: Annotated[str, Header(alias="Idempotency-Key")],
    session: Annotated[AsyncSession, Depends(get_session)],
) -> OrderCreated:
    try:
        order = await orders.place(session, body, idem_key)   # INSERT inside session.begin_nested()
    except orders.DuplicateKey as e:
        order = await orders.get(session, e.existing_id)  # same answer
    except orders.OutOfStock as e:
        raise HTTPException(409, str(e)) from e           # keeps the cause
    return OrderCreated(id=order.id, status="accepted", total=order.total)
L1 · Beginner

What the code does

  • The type hints are the wiring. body: CreateOrder means “parse the JSON body into this”; Header(...) means “read this header”.
  • Depends(get_session) runs the dependency, hands you what it yields, and resumes it after the response.
  • The savepoint is load-bearing. A unique-key violation aborts a plain Postgres transaction — every later statement fails with InFailedSQLTransaction. Because place() wraps its INSERT in session.begin_nested(), only the savepoint rolls back, and the orders.get on the next line still runs inside a healthy transaction.
  • response_model filters the response through a second model, so an internal field cannot leak by accident.
  • raise HTTPException(409, ...) is how you choose a status code deliberately.
  • from e keeps the original traceback attached — the chained cause you saw in the exceptions topic.
L2 · Intermediate

Why it is written this way

  • The route knows HTTP; the domain does not. orders.place raises OutOfStock, never HTTPException — so the same function works from a worker, a CLI and a test.
  • Yield-style dependencies own the resource. The async with pair means the transaction cannot outlive the request, no matter how the handler exits.
  • Request and response models are separate classes even when they look alike today; they diverge the first time you add an internal field.
  • Idempotency is a database constraint, not an if. A unique index on the key is the only version that survives two concurrent retries.
  • A duplicate is not an error. Returning the original answer is what makes a client retry safe, which is what makes at-least-once delivery workable.
L3 · Advanced

What bites in production

  • One blocking call poisons the loop. A synchronous driver, time.sleep or a CPU-heavy hash inside an async def stalls every other request on that worker — asyncio.to_thread or a sync def endpoint instead.
  • The client can vanish mid-request. A disconnect cancels the task and raises CancelledError inside your handler; the rollback is correct, but any external side effect already sent is not undone.
  • Long transactions hold locks. Do not call another service inside session.begin() — a two-second HTTP timeout becomes a two-second row lock.
  • The dependency’s COMMIT runs after the response is sent — FastAPI resumes yield dependencies once the body is out the door. If the caller must be able to trust the 201, commit explicitly in the handler before returning, and keep the dependency as the rollback-on-error backstop.
  • Pool sizing is a total, not a per-worker setting. Eight workers × a pool of 20 is 160 connections; Postgres’s default max_connections is 100.
  • Validation errors are a 422 by default, which many clients treat as unretryable — deliberate, and worth documenting rather than discovering.

Calling another service without hanging

The job: call an internal API, survive its bad minutes, and never become the reason your own workers are all stuck. Two numbers decide everything — the per-attempt timeout and the total budget the caller is willing to wait.

# client.py — one client for the process, not one per call
TIMEOUT = httpx.Timeout(connect=1.0, read=2.0, write=2.0, pool=1.0)
LIMITS  = httpx.Limits(max_connections=100, max_keepalive_connections=20)

client = httpx.AsyncClient(base_url="https://ledger.internal",
                           timeout=TIMEOUT, limits=LIMITS)
# a fresh AsyncClient per call throws away the connection pool and the
# TLS session, and turns a 2 ms call into a 40 ms one

class Retryable(Exception): ...      # 5xx, timeouts: worth another try
class Permanent(Exception): ...      # 4xx: retrying cannot help

@retry(stop=stop_after_attempt(3),
       wait=wait_exponential_jitter(initial=0.1, max=1.0),   # jitter matters
       retry=retry_if_exception_type((httpx.TransportError, Retryable)),
       reraise=True)
async def post_entry(entry: LedgerEntry, idem_key: str) -> LedgerRef:
    r = await client.post("/entries", json=entry.model_dump(mode="json"),
                          headers={"Idempotency-Key": idem_key})
    if r.status_code >= 500:
        raise Retryable(f"ledger {r.status_code}")
    if r.status_code >= 400:
        raise Permanent(r.text[:200])
    return LedgerRef.model_validate(r.json())   # their JSON is untrusted too
L1 · Beginner

What the code does

  • Every call has a timeout. httpx defaults to five seconds; requests defaults to waiting forever, which is the difference that matters.
  • One client, reused — it holds the connection pool. Create it at start-up, close it at shutdown.
  • Retry only what a retry can fix: connection errors and 5xx. A 400 will be a 400 again.
  • Back off between attempts, and add jitter so a thousand clients do not all retry on the same tick.
  • Validate their response too — another service’s JSON is exactly as untrusted as a browser’s.
L2 · Intermediate

Why it is written this way

  • Two exception types, not status-code checks at the call site. Retryable and Permanent put the policy in one place and make the retry decorator declarative.
  • The idempotency key is generated by the caller and reused across all attempts — that is what makes a retry safe rather than a second charge.
  • Timeouts are named separately so you can allow a slow response while still failing fast on a dead host.
  • Cap the total attempts against the caller’s deadline, not against a number that felt right. Three × 600 ms does not fit in a 2s budget.
  • max_connections is your bound on the downstream, and it is the only thing standing between a slow dependency and every worker you own.
L3 · Advanced

What bites in production

  • Retries are a load multiplier. A struggling service that you hit three times instead of once gets 3× the traffic exactly when it can least take it — the metastable failure from the foundations page.
  • A circuit breaker is the missing piece. After N consecutive failures, fail immediately for a cooldown instead of queueing more work against a service that is down.
  • Retrying a non-idempotent POST duplicates work unless the server enforces the key. “We send a key” and “they honour it” are different claims — check which one is true.
  • Propagate the deadline, not just a timeout: pass the remaining budget downstream so the whole chain gives up together, the way a Go context does.
  • Connection pools and forked workers — a client created before fork shares sockets across processes. Build it in the worker’s own start-up hook.

Fan-out with a bound on it

The job: enrich two hundred records by calling a service for each. The naive version issues two hundred simultaneous requests, and the thing that breaks is not your process — it is theirs.

# bounded fan-out, partial failure allowed
async def enrich_all(ids: list[str], *, limit: int = 20) -> list[Result | BaseException]:
    sem = asyncio.Semaphore(limit)

    async def one(oid: str) -> Result:
        async with sem:                        # the bound, not the loop
            async with asyncio.timeout(2.0):   # per item, not per batch
                return await enrich(oid)

    return await asyncio.gather(*(one(i) for i in ids), return_exceptions=True)
    # return_exceptions=True: one bad id does not lose the other 199 results
# all-or-nothing instead: 3.11+ TaskGroup cancels siblings on first failure
async def must_all_succeed(ids: list[str]) -> dict[str, Result]:
    async with asyncio.TaskGroup() as tg:
        tasks = {i: tg.create_task(enrich(i)) for i in ids}
    return {i: t.result() for i, t in tasks.items()}

# the exit raises ExceptionGroup — handle by type, not by position:
try:
    results = await must_all_succeed(ids)
except* TimeoutError as eg:
    log.warning("slow upstream", count=len(eg.exceptions))
except* ValidationError as eg:
    log.error("bad payload", count=len(eg.exceptions))
L1 · Beginner

What the code does

  • gather starts everything at once and waits for all of it. The list you pass decides how much runs concurrently.
  • Semaphore(20) hands out twenty permits; the twenty-first async with waits until one is returned.
  • return_exceptions=True puts failures in the result list instead of losing the successes.
  • asyncio.timeout is a context manager, so it bounds a block rather than a single call.
  • TaskGroup is the newer, stricter option: if one child fails the rest are cancelled.
L2 · Intermediate

Why it is written this way

  • The timeout is inside the semaphore, so the two seconds measure the actual call — not two seconds of queueing behind other tasks.
  • Choose the failure mode deliberately. gather(return_exceptions=True) for “do as much as you can”; TaskGroup for “all of it or none”.
  • except* handles an ExceptionGroup, which is what a TaskGroup raises when several children fail at once.
  • The limit should be derived, not guessed: their capacity divided by the number of instances of you.
  • Order out matches order in. gather preserves position, so you can zip results back to inputs; as_completed does not.
L3 · Advanced

What bites in production

  • Cancellation is cooperative. A cancelled task resumes with CancelledError at its next await — if it is blocked in C code it will not stop at all.
  • Never swallow CancelledError. except Exception will not catch it — it inherits from BaseException, deliberately. What breaks shutdown is except BaseException or a bare except: that catches it and carries on.
  • Fire-and-forget tasks get garbage collected. create_task without keeping a reference can have the task vanish mid-flight; hold it in a set and discard on completion.
  • Two hundred coroutines is memory too — each holds its own frame and its own response buffer. Bounded concurrency bounds peak memory as well.
  • The real limit is often theirs, expressed as 429. Read the Retry-After header rather than guessing your own backoff.

A file that does not fit in memory

The job: load an 8 GB compressed export into the database. The version that works and the version that gets OOM-killed differ by one word — list — and the generator topic earlier is the reason.

# each stage is lazy; nothing is read until the for loop pulls
def rows(path: str) -> Iterator[dict[str, str]]:
    with gzip.open(path, "rt", newline="") as fh:      # decompresses as it reads
        yield from csv.DictReader(fh)

def valid(raw: Iterable[dict[str, str]]) -> Iterator[Order]:
    for i, r in enumerate(raw, start=2):               # line 1 is the header
        try:
            yield Order.model_validate(r)              # pydantic, at the edge again
        except ValidationError as e:
            log.warning("skipped row", line=i, errors=e.error_count())
# the driver: one transaction per batch, so a failure loses 1000 rows, not 8 GB
from itertools import batched            # 3.12+; recipe in the docs before that

totals: Counter[str] = Counter()
for n, batch in enumerate(batched(valid(rows("orders.csv.gz")), 1000), start=1):
    with session.begin():
        session.execute(insert(OrderRow), [o.model_dump() for o in batch])
    totals.update(o.currency for o in batch)
    if n % 100 == 0:
        log.info("progress", batches=n, rows=n * 1000, totals=dict(totals))
L1 · Beginner

What the code does

  • yield makes the function lazy — calling rows(path) reads nothing; the for loop at the end pulls one row at a time through the whole chain.
  • yield from forwards every item of an inner iterable without a loop.
  • with gzip.open(...) decompresses on the fly; the file is never on disk uncompressed and never fully in memory.
  • batched turns a stream of items into a stream of tuples of n.
  • Counter.update accumulates counts without building an intermediate list.
L2 · Intermediate

Why it is written this way

  • Each stage does one thing, so each can be tested with a three-item list instead of an 8 GB file.
  • Bad rows are skipped with the line number, not silently dropped and not fatal — an import that dies on row 4 million is an import you run four times.
  • One transaction per batch bounds both the lock duration and how much work a crash costs.
  • Batch inserts, not row inserts. A thousand single INSERTs is a thousand round trips; the batch is one.
  • Log progress by batch count. A silent job that runs for an hour is indistinguishable from a hung one.
L3 · Advanced

What bites in production

  • A generator holds its resources open. The with inside rows only closes when the generator is exhausted or garbage collected — break out early and the file handle lingers.
  • Restartability beats speed. Record the last committed batch so a rerun resumes rather than starting again; with a unique key the insert can be an upsert and the whole job idempotent.
  • The database is usually the bottleneck, not the parse. Measure before reaching for multiprocessing — then COPY beats every Python-side optimisation by an order of magnitude.
  • Generators and exceptions interact badly under concurrency: a generator is not thread-safe, and sharing one across workers corrupts its state silently.
  • Watch fragmentation, not just peak. A long-running loop can hold flat RSS while the allocator never returns freed arenas to the OS.
