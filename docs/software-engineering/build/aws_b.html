Part two

Relational: RDS and Aurora

RDS is your database with the operations attached. Aurora is a different storage engine wearing the same wire protocol. The distinction decides your failover time, your bill, and how much of your recovery plan is a button versus a weekend.

AWS · 00

RDS: every knob, and which ones cost you an outage

An RDS instance is a normal Postgres or MySQL server plus six configuration surfaces — compute, storage, parameters, backups, availability and maintenance. Changing three of them is instant; changing the other three restarts your database.

Storage · gp33,000 IOPS and 125 MB/s baseline included, both independently provisionable. The default for almost everything, and it removed gp2’s burst-credit cliff.
Storage · io2Up to 256,000 IOPS with a five-nines durability claim. You want it when a sustained write workload is IOPS-bound, and you will feel the price.
AutoscalingGrows storage when free space drops below 10%. Set a maximum — without one a runaway write can grow you into a very large bill.
T-classBurstable CPU credits. Fine for dev, dangerous in production: when credits run out the instance is throttled to baseline and everything queues at once.

A pre-deploy guard for the database

Three RDS facts should block a release: pending maintenance that will reboot you mid-deploy, a certificate authority about to expire, and storage close to the autoscaling ceiling. All three are one API call each.

// preflight fails the pipeline if the database is about to move under us.
func preflight(ctx context.Context, c *rds.Client, id string) error {
    d, err := c.DescribeDBInstances(ctx, &rds.DescribeDBInstancesInput{
        DBInstanceIdentifier: aws.String(id),
    })
    if err != nil {
        return err
    }
    in := d.DBInstances[0]

    // 1. a modification already queued for the next window (class, storage, params)
    if p := in.PendingModifiedValues; p != nil && p.DBInstanceClass != nil {
        return fmt.Errorf("pending class change to %s", aws.ToString(p.DBInstanceClass))
    }

    // 2. static parameters saved but not yet live — the reboot is still owed
    for _, g := range in.DBParameterGroups {
        if aws.ToString(g.ParameterApplyStatus) == "pending-reboot" {
            return fmt.Errorf("parameter group %s awaits a reboot",
                aws.ToString(g.DBParameterGroupName))
        }
    }

    // 3. maintenance AWS will apply for us, whether or not we are deploying
    m, err := c.DescribePendingMaintenanceActions(ctx,
        &rds.DescribePendingMaintenanceActionsInput{
            ResourceIdentifier: in.DBInstanceArn,
        })
    if err != nil {
        return err
    }
    for _, r := range m.PendingMaintenanceActions {
        for _, a := range r.PendingMaintenanceActionDetails {
            log.Warn("pending maintenance",
                "action", aws.ToString(a.Action),                 // system-update, ca-certificate-rotation…
                "auto_applied_after", a.AutoAppliedAfterDate)
        }
    }
    log.Info("db ok", "ca", aws.ToString(in.CACertificateIdentifier),
        "engine", aws.ToString(in.EngineVersion),
        "multi_az", aws.ToBool(in.MultiAZ))
    return nil
}

    for group in inst["DBParameterGroups"]:
        if group["ParameterApplyStatus"] == "pending-reboot":
            raise Blocked(f"{group['DBParameterGroupName']} awaits a reboot")

    # 3. maintenance AWS will apply for us, whether or not we are deploying
    actions = RDS.describe_pending_maintenance_actions(
        ResourceIdentifier=inst["DBInstanceArn"]
    )["PendingMaintenanceActions"]
    for res in actions:
        for a in res["PendingMaintenanceActionDetails"]:
            log.warning(
                "pending maintenance",
                extra={"action": a["Action"],            # ca-certificate-rotation…
                       "after": a.get("AutoAppliedAfterDate")},
            )

    log.info("db ok", extra={"ca": inst["CACertificateIdentifier"],
                             "engine": inst["EngineVersion"],
                             "multi_az": inst["MultiAZ"]})

The recovery you should have rehearsed

“Someone dropped a table at 14:07” is not a backup restore — it is a point-in-time restore into a new instance, from which you copy the one table back. Practise it once and the real thing is forty minutes instead of a day.

// Restore to one second before the mistake. This never touches production:
// it creates a second instance you then read from.
target := "orders-prod-recovery-1407"
_, err := c.RestoreDBInstanceToPointInTime(ctx, &rds.RestoreDBInstanceToPointInTimeInput{
    SourceDBInstanceIdentifier: aws.String("orders-prod"),
    TargetDBInstanceIdentifier: aws.String(target),
    RestoreTime:                aws.Time(dropTime.Add(-1 * time.Second)),
    DBSubnetGroupName:          aws.String("private"),        // same VPC, no public IP
    VpcSecurityGroupIds:        []string{"sg-db"},
    DBInstanceClass:            aws.String("db.r7g.xlarge"),  // size for the copy job
    MultiAZ:                    aws.Bool(false),              // it is temporary
    DeletionProtection:         aws.Bool(false),
})
if err != nil {
    return err
}

// Restores take tens of minutes on a large volume; the waiter has a cap so a

Blue/Green is the upgrade path

RDS Blue/Green clones the instance, keeps it in sync by logical replication, lets you upgrade and test the green copy, then switches over in about a minute with the endpoint names swapped. It is the only sane way to do a major version upgrade on a database you care about.

Performance Insights or nothing

CloudWatch tells you CPU is 90%. Performance Insights tells you which SQL, waiting on what, measured as average active sessions against your vCPU count. Seven days of retention is free. Turn it on before you need it — it cannot show you yesterday.

Aurora: the log is the database

Aurora keeps the Postgres or MySQL front end and replaces everything below the buffer pool. Instances ship redo log records to a distributed storage fleet; storage materialises pages. Every property people like about Aurora falls out of that one decision.

Serverless v2Capacity in ACUs, roughly 2 GiB of memory each, scaling in place without dropping connections. It can scale to zero, at the price of a resume delay on the next connection.
CloningCopy-on-write on the storage volume: a full-size test cluster in minutes, paying only for pages that then diverge. The best staging trick AWS sells.
Global DatabaseStorage-level replication to another region, typically under a second behind, with managed planned switchover and unplanned promotion in minutes.
I/O-OptimizedA flat compute-and-storage price with no per-request I/O charge. Worth switching to once I/O passes roughly a quarter of the cluster bill.
BehaviourRDS PostgresAurora Postgres
Write pathPages + WAL to an EBS volume, checkpoints, full-page writesRedo records only, to six storage nodes. No checkpoint, no full-page writes.
Failover60–120s instance, under 35s for a Multi-AZ clusterTypically 10–30s — nothing is copied, only promoted
ReplicasUp to 15, asynchronous, each with its own storage copy15, reading the same volume, lag in milliseconds
Storage growthProvisioned; you pay for allocated spaceAutomatic in 10 GiB steps to 128 TiB; you pay for used
Restore a copyFull restore from snapshot, minutes to hoursClone in minutes, copy-on-write
Cost shapeInstance + provisioned storage + provisioned IOPSInstance + used storage + per million I/Os, unless I/O-Optimized
ExtensionsWide support, close to community PostgresSlightly behind, and some extensions never arrive

The Data API: SQL over HTTPS, no pool at all

Aurora — provisioned and Serverless v2 alike — exposes an HTTP endpoint that runs statements with IAM auth and credentials from Secrets Manager. There is no connection to manage, which makes it the right answer for Lambda — and the wrong answer for a chatty request path, because every statement is a signed HTTPS round trip.

// Data API: no driver, no pool, no VPC attachment. Each call is signed HTTPS.
rd := rdsdata.NewFromConfig(cfg)

const clusterARN = "arn:aws:rds:eu-west-1:1234:cluster:orders"
const secretARN = "arn:aws:secretsmanager:eu-west-1:1234:secret:orders-db"

Rehearse the failover, in a script

A failover you have never triggered deliberately is a failover you do not know the cost of. Run this against staging monthly with traffic flowing, and watch your own error rate rather than the console.

start := time.Now()

    }

Aurora DSQL is a different product with a familiar name

Aurora DSQL is a serverless, distributed, active-active SQL database with a Postgres-compatible wire protocol and optimistic concurrency control. It is not “Aurora, but more so”: there are no instances to size, no failover, and no long-lived transactions holding locks — conflicting writes are rejected at commit and your code must retry them. Reach for it for multi-region write workloads, not as a drop-in for an existing Aurora cluster.

Connecting to it without falling over

Three application-side decisions determine whether a database incident is thirty seconds or thirty minutes: how many connections you open, how you authenticate, and what your pool does when the server on the other end changes identity.

// pgxpool, sized deliberately, with IAM auth and a failover-aware health check.
cfgp, err := pgxpool.ParseConfig(

        "user=orders_app dbname=orders sslmode=verify-full " +
        "sslrootcert=/etc/ssl/certs/rds-global-bundle.pem")
if err != nil {
    return err
}

// Sizing: (max_connections * 0.8) / number of tasks, then leave headroom for a
// deploy running twice the tasks. Bigger is not better — it just queues later.
cfgp.MaxConns = 10
cfgp.MinConns = 2
cfgp.MaxConnLifetime = 30 * time.Minute      // forces rebalancing after a failover
cfgp.MaxConnIdleTime = 5 * time.Minute
cfgp.HealthCheckPeriod = 30 * time.Second

// IAM auth: the password is a signed, 15-minute token, generated per connection.
// No secret to rotate, and every connection is attributable in CloudTrail.
cfgp.BeforeConnect = func(ctx context.Context, c *pgx.ConnConfig) error {
    tok, err := auth.BuildAuthToken(ctx, c.Host+":5432", "eu-west-1",
        c.User, cfg.Credentials)
    if err != nil {
        return err
    }
    c.Password = tok
    return nil
}

// The four lines that turn a 30-minute outage into a 30-second one: refuse to
// hand out a connection to an instance that is no longer the writer.
cfgp.BeforeAcquire = func(ctx context.Context, c *pgx.Conn) bool {
    var inRecovery bool
    if err := c.QueryRow(ctx, "SELECT pg_is_in_recovery()").Scan(&inRecovery); err != nil {
        return false                          // broken: destroy it
    }
    return !inRecovery                        // demoted: destroy it, reconnect via DNS
}

DecisionChooseReasoning
Where the pool livesIn the process, small — plus RDS Proxy if you have Lambda or many tasksLambda cannot pool across invocations; hundreds of short-lived environments each opening one connection is exactly what Proxy exists for.
Password or IAMIAM for services, Secrets Manager for anything that cannot use itIAM tokens last 15 minutes and leave a CloudTrail entry per connection. There is nothing to leak and nothing to rotate.
Reads on the reader endpointA second, explicitly-named pool — never automatic routingReplica lag is real. “Read your own writes” breaks silently and only under load, which is the worst way to find out.
Retry on failoverRetry the transaction, not the statement, and only if it is idempotentA retried INSERT after a lost commit is a duplicate order. Use a unique key or a conditional write to make it safe.
TLSverify-full with the regional CA bundle, pinned in the imagerequire encrypts but does not authenticate the server. The bundle expires — RDS certificate rotation is an announced, dated event.

The rule that survives every architecture

Connections are the scarcest resource in the system and the least elastic. Everything else in this part — Proxy, IAM auth, pool sizing, reader endpoints, Serverless v2 — is a way of spending fewer of them or recovering faster when they all break at once. If you only take one number away: work out tasks × pool_max at peak during a deploy, and compare it with your instance’s real limit before you ship.
