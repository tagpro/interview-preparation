Part two

The linear structures

Four structures carry the overwhelming majority of production code: the growable array, the linked list, the stack-or-queue, and the hash table. Everything later in this page is built out of them. What matters is not their interfaces — those you know — but what each one is doing to memory when you use it, and the one operation each is quietly bad at.

The growable array, and why appending is free

A Go slice, a Python list and a Java ArrayList are the same idea: a fixed block of memory, a length, and a capacity. Appending past the capacity allocates a bigger block and copies. The reason that is not a disaster — the reason append is O(1) rather than O(n) — is one of the most useful arguments in the subject.

OperationCostThe reason, and the trap
IndexO(1)One multiply and one add. Nothing else in this page is this cheap.
AppendO(1) amortisedThe individual append that reallocates is O(n). If you have a tail-latency budget, preallocate.
Insert or delete at the frontO(n)Every later element shifts. In a loop this is the classic accidental O(n²) — use a deque, or append and reverse at the end.
Delete in the middle, order keptO(n)Same shift. If order does not matter, swap the last element into the hole: O(1).
Search, unsortedO(n)But with the best constant of any O(n) in existence, so it beats a hash set well past the size you would guess.
Search, sortedO(log n)Binary search. Keeping an array sorted costs O(n) per insert, which is only worth it when reads dominate heavily.
Grow past capacityO(n), rarelyGo doubles under 256 elements then grows by roughly 1.25×; Java’s ArrayList uses 1.5×; CPython uses about 1.125× plus a constant. All multiplicative, all amortised O(1).

for i := range 1024 {                            // for the next 1024 appends
    xs = append(xs, i)

The remove-in-a-loop quadratic

Deleting k elements one at a time from an array-backed list costs O(nk), because each delete shifts the tail. Deleting them in a single filtering pass costs O(n). Go has slices.DeleteFunc, Python has a comprehension, Java has removeIf; all three do the same thing, which is to write the survivors forwards over the original in one sweep. Whenever you find yourself removing inside a loop, you are choosing an algorithm, and it is the worse one.

Linked lists: rarely the answer, always the exam question

A linked list buys O(1) insertion and removal at a position you already hold, and pays with a pointer per element, an allocation per element, and a cache miss per hop. That trade almost never wins in application code. It wins decisively in three specific places, and those are worth knowing precisely.

Where it winsIntrusive lists in allocators and kernels. The node is part of the object, so there is no extra allocation, and O(1) unlink from a pointer you already have is exactly the operation needed.
Where it winsLRU caches. A hash map to nodes plus a doubly linked list gives O(1) lookup and O(1) move-to-front. No array can do the second one.
Where it winsLock-free queues. A single atomic pointer swap publishes a node. Growable arrays cannot be resized without coordination.
Where it losesEverywhere else. Iteration, search, sorting, memory use and cache behaviour are all worse, and “O(1) insert” is a lie if finding the position is O(n).
// list.go — the two techniques worth memorising, both of them pointer
// discipline rather than cleverness.

type Node struct {
    Val  int
    Next *Node
}

// 1. Reverse in place. Three pointers, one pass, no allocation.
func Reverse(head *Node) *Node {
    var prev *Node
    for cur := head; cur != nil; {
        next := cur.Next                         // remember before clobbering
        cur.Next = prev                          // flip
        prev, cur = cur, next                    // advance both
    }
    return prev                                  // prev is the old tail
}

// 2. Floyd's cycle detection. Fast moves two, slow moves one; if there
// is a loop they must meet inside it, in O(n) time and O(1) space.
// Restarting one pointer at the head then advancing both one step at a
// time lands them on the entry to the cycle -- that part is not obvious,
// and it falls out of the arithmetic of where they met.
func CycleStart(head *Node) *Node {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow, fast = slow.Next, fast.Next.Next
        if slow == fast {                        // a cycle exists
            for p := head; p != slow; p, slow = p.Next, slow.Next {
            }
            return slow                          // the node the loop enters at
        }
    }
    return nil
}

// A dummy head node removes every "is this the first element" branch
// from insert and delete. Use one; the code halves in size.
# linked.py — you will almost never write one of these in Python, but
# the two techniques generalise to every sequence you cannot index.
from dataclasses import dataclass
from typing import Optional

@dataclass
class Node:
    val: int
    next: Optional["Node"] = None

def reverse(head: Optional[Node]) -> Optional[Node]:
    prev = None
    while head is not None:
        head.next, prev, head = prev, head, head.next   # one line, one pass
    return prev

def cycle_start(head: Optional[Node]) -> Optional[Node]:
    slow = fast = head
    while fast is not None and fast.next is not None:
        slow, fast = slow.next, fast.next.next
        if slow is fast:                         # identity, not equality
            slow = head
            while slow is not fast:
                slow, fast = slow.next, fast.next
            return slow
    return None

// Lists2.java — LinkedHashMap gives you the LRU cache in six lines,
// because it maintains exactly the hash-map-plus-linked-list structure
// you would otherwise build by hand.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int cap;

    LruCache(int cap) {
        super(16, 0.75f, /* accessOrder = */ true);   // the whole trick
        this.cap = cap;
    }

    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > cap;                     // evict on the way out of put()
    }
}

// accessOrder=true moves an entry to the end of the list on every get,
// which is the O(1) move-to-front an array cannot do. With it false
// (the default) you get insertion order, which is what you want when
// the map is really an ordered record rather than a cache.

// java.util.LinkedList exists and you should almost never use it. It is

Stacks, queues, deques and the ring buffer underneath

A stack is last-in-first-out, a queue is first-in-first-out, and a deque is both. All three are interfaces, not structures: the good implementations of all of them are arrays. What makes a queue an array rather than a list is one idea — move the head index instead of moving the elements.

// deque.go — Go has no deque type. A slice is a fine stack; for a queue
// with bounded memory, write the ring buffer, it is thirty lines.

// Stack: a slice, and that is the whole implementation.
stack = append(stack, v)                         // push
v, stack = stack[len(stack)-1], stack[:len(stack)-1]  // pop

// Queue: the naive version leaks. `q = q[1:]` advances the pointer but
// keeps the whole backing array alive, so a long-running queue grows
// without bound even at constant depth.
type Ring[T any] struct {
    buf        []T
    head, tail int
    n          int
}

func NewRing[T any](cap int) *Ring[T] { return &Ring[T]{buf: make([]T, cap)} }

func (r *Ring[T]) Push(v T) bool {
    if r.n == len(r.buf) {
        return false                             // full: caller decides — block,
    }                                            // drop, or grow
    r.buf[r.tail] = v
    r.tail = (r.tail + 1) % len(r.buf)
    r.n++
    return true
}

func (r *Ring[T]) Pop() (T, bool) {
    var zero T
    if r.n == 0 {
        return zero, false
    }
    v := r.buf[r.head]
    r.buf[r.head] = zero                         // release the reference, or the
    r.head = (r.head + 1) % len(r.buf)           // GC keeps the popped object
    r.n--
    return v, true
}

// already done: make(chan T, 1024).
# deque.py — collections.deque is O(1) at both ends and written in C.
from collections import deque

stack = []                                       # a list IS the right stack
stack.append(v); v = stack.pop()                 # both O(1) amortised

q = deque()                                      # the right queue
q.append(v); v = q.popleft()                     # both O(1)

# maxlen turns it into a ring buffer that silently drops from the far
# end -- exactly what you want for "the last 1000 log lines".
recent = deque(maxlen=1000)

def window_max(nums: list[int], k: int) -> list[int]:
    """Maximum of every window of size k, in O(n) total.

    The deque holds *indices* whose values are strictly decreasing, so
    the front is always the current maximum. Each index enters once and
    leaves once, which is where the linear bound comes from.
    """
    dq: deque[int] = deque()
    out = []
    for i, v in enumerate(nums):
        while dq and dq[0] <= i - k:             # front fell out of the window
            dq.popleft()
        while dq and nums[dq[-1]] <= v:          # everything smaller is dead:
            dq.pop()                             # v is newer AND bigger
        dq.append(i)
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out

# A heap would also work and would be O(n log k). The deque is O(n),
# because it never reconsiders an element it has thrown away.
// Deques.java — ArrayDeque is the one to reach for: a growable ring
// buffer, no synchronisation, faster than LinkedList and than Stack.

Deque<Integer> stack = new ArrayDeque<>();
stack.push(v);                                   // addFirst
int top = stack.pop();                           // removeFirst, throws if empty

Deque<Task> queue = new ArrayDeque<>();
queue.offer(t);                                  // addLast, false if capacity-bound
Task next = queue.poll();                        // removeFirst, null if empty

// Learn the pairs: add/remove/element throw on failure, offer/poll/peek
// return a sentinel. Mixing them is how a queue ends up throwing
// NoSuchElementException in production at 3 a.m.

int[] windowMax(int[] nums, int k) {             // O(n), monotonic deque
    int[] out = new int[nums.length - k + 1];
    Deque<Integer> dq = new ArrayDeque<>();      // holds indices, values decreasing
    for (int i = 0; i < nums.length; i++) {
        while (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();
        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) dq.pollLast();
        dq.addLast(i);
        if (i >= k - 1) out[i - k + 1] = nums[dq.peekFirst()];
    }
    return out;
}

Hash tables: O(1) with three asterisks

A hash table turns a key into an array index and looks there. That is the entire idea, and it is genuinely close to O(1) — conditional on the hash spreading keys evenly, on the load factor staying low, and on nobody choosing your keys adversarially. Each of those three conditions has failed in production somewhere, expensively.

The asteriskWhat goes wrongWhat the runtimes do about it
The hash must spreadA weak hash clusters keys into a few buckets and lookups degrade to O(n)Go uses a seeded hash with hardware AES where available; Python uses SipHash for strings and bytes; Java relies on your hashCode and only spreads its high bits into the low ones.
The load factor must stay lowA nearly full table collides constantly whatever the hashResize at a threshold — Java at 0.75, Go at 6.5 entries per bucket group, Python at 2/3 — then rehash everything, which is the one O(n) insert.
Keys must not be chosen by an attackerHash flooding: a few thousand colliding keys turn one request into seconds of CPUPer-process random seeds in Go and Python. Java has no seed, which is why HashMap treeifies instead.
Keys must be immutableMutating a key after insertion changes its hash; the entry becomes unreachable and un-removableNothing. Python enforces hashability but not immutability of custom objects; Go rejects unhashable types at compile time; Java trusts you.
Iteration order is not insertion orderCode that accidentally depends on order breaks on a resize, a rebuild or a new versionGo randomises iteration deliberately, to break that dependency early. Python dicts have kept insertion order since 3.7 and it is now guaranteed. Java’s HashMap makes no promise; LinkedHashMap does.

“It is O(1)” is a claim about the hash, not about the table

Every guarantee in this section is inherited from the assumption that keys spread evenly across buckets. When you write hashCode by hand, use every field that equals uses and no field that it does not — the two must agree or the map breaks outright. When your key is a composite of a low-cardinality tenant and a high-cardinality id, make sure the id reaches the low bits of the hash. And when the keys arrive from outside your system, know which of your runtimes seeds its hash: Go and Python do, Java does not.
