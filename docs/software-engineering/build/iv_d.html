Part four

Data: modelling it, indexing it, keeping it correct

Databases are the densest source of interview questions per minute of preparation, because almost every backend role touches them and almost every candidate’s knowledge stops at the ORM. Four things get asked: can you model a domain, can you make a query fast and say why, do you understand what a transaction promises, and do you know what breaks when one machine is no longer enough.

Topic · xx

Relational modelling and the SQL you must be able to write

The schema question is a design question in miniature: entities, relationships, cardinality, and where the truth lives. The SQL question is a fluency test — you will be asked to write it, not to describe it.

Entities and relationshipsOne-to-one, one-to-many, many-to-many with a join table. Draw it before you name a column.
KeysPrimary, natural vs surrogate, composite, foreign. Whether the key is meaningful is a real design decision.
Normal forms1NF to 3NF in practice: one fact in one place. Then when to denormalise, and what you owe in return.
ConstraintsNOT NULL, UNIQUE, CHECK, foreign keys, defaults. The database is the last place an invariant can actually be enforced.
JoinsInner, left, right, full, cross, self, semi and anti. Know what each does to row counts and to NULLs.
AggregationGROUP BY, HAVING, and why a column not in the grouping is an error rather than an average.
Window functionsROW_NUMBER, RANK, LAG, running totals. The most common “senior” SQL question there is.
Subqueries and CTEsCorrelated vs not, EXISTS vs IN vs JOIN, recursive CTEs for trees and graphs.
NULL semanticsThree-valued logic. NULL = NULL is not true, and NOT IN with a NULL returns nothing.
Set operationsUNION vs UNION ALL and the sort the first one silently pays for.
Data typesNumeric vs decimal for money, timestamp with and without time zone, UUID vs bigint keys, JSON columns.
Soft deletes and historyTombstones, audit tables, temporal tables, event sourcing — and what each costs a query.
Schema migrationExpand–migrate–contract, backfills, adding a column with a default on a big table, online DDL.
ORMsWhat they generate, the N+1 query, lazy loading, and when to drop to raw SQL.

The one query that shows up most often is “top N per group”, and the good answer uses a window function rather than a correlated subquery. Being able to write it without hesitating is worth more than knowing three ways to do it slowly.

-- top_per_group.sql — the most-asked "senior SQL" shape.
-- "The three most recent orders for every customer, with the running total."
WITH ranked AS (
    SELECT
        o.customer_id,
        o.id,
        o.placed_at,
        o.amount_cents,
        ROW_NUMBER() OVER (PARTITION BY o.customer_id
                           ORDER BY o.placed_at DESC)        AS rn,
        SUM(o.amount_cents) OVER (PARTITION BY o.customer_id
                                  ORDER BY o.placed_at)      AS running_cents
    FROM orders o
    WHERE o.placed_at >= now() - interval '90 days'
)
SELECT customer_id, id, placed_at, amount_cents, running_cents
FROM ranked
WHERE rn <= 3                       -- filter AFTER the window has been computed
ORDER BY customer_id, placed_at DESC;

-- Two things an interviewer listens for:
--   * why the rn filter cannot go in the WHERE of the inner query
--     (window functions run after WHERE, so rn does not exist yet), and
--   * that this reads the 90-day slice once, where a correlated subquery
--     would re-scan per customer.

Indexes, and the two shapes storage engines come in

“Add an index” is not an answer. Which index, on which columns, in which order, and what it costs on write — that is the answer.

Then the part candidates get wrong: column order in a composite index. An index on (a, b) serves a lookup on a and on a plus b, but not one on b alone — it is a sorted list keyed left to right, exactly like a phone book sorted by surname then first name. Equality columns come first, the range column last, and anything after a range column cannot be used for seeking.

-- index_order.sql — the phone-book rule, made concrete.
CREATE INDEX idx_events_tenant_type_time
    ON events (tenant_id, event_type, created_at DESC);

-- Uses the index fully: equality, equality, then a range on the last column.
SELECT * FROM events
 WHERE tenant_id = $1 AND event_type = 'login' AND created_at > now() - interval '1 day'
 ORDER BY created_at DESC LIMIT 50;

-- Uses only the first column, then filters the rest by hand.
SELECT * FROM events WHERE tenant_id = $1 AND created_at > $2;

-- Cannot use it at all: the leading column is missing.
SELECT * FROM events WHERE event_type = 'login';

-- A covering index answers from the index alone -- no heap fetch at all:
CREATE INDEX idx_events_cover ON events (tenant_id, created_at DESC) INCLUDE (event_type, payload_id);
B-tree indexThe default. Equality, ranges, prefix matches, and ORDER BY without a sort.
Hash indexEquality only, no ordering. Rarely the right answer, occasionally the exact one.
Composite indexLeftmost-prefix rule, equality before range, and the sort it can save you.
Covering indexAll the columns the query needs, so the table is never touched. The biggest single win available.
Partial / filtered indexIndex only the rows you query — the pending ones, the non-deleted ones. Smaller and faster.
Unique indexAn index and a constraint at once, and the only sound way to enforce “at most one” under concurrency.
Full-text and trigramWhy LIKE '%foo%' cannot use a normal index, and what does.
Geospatial, GIN, GiSTIndexes over arrays, JSON documents and shapes.
Clustered vs secondaryInnoDB stores the row in the primary key’s tree; a secondary index costs a second lookup.
Selectivity and cardinalityAn index on a boolean is usually useless. The planner needs statistics to know that.
The query planEXPLAIN ANALYZE, seq scan vs index scan, nested loop vs hash vs merge join, estimated vs actual rows.
The cost of an indexEvery write updates every index. Unused indexes are a tax with no benefit — find and drop them.

Transactions, isolation and the anomalies each level allows

Everyone can expand ACID. The question that separates people is which anomalies your default isolation level still permits — because it is never none, and the default is rarely serialisable.

ACIDAtomicity, consistency, isolation, durability — and which of the four your setup actually delivers.
MVCCReaders never block writers because each sees a snapshot. The cost is old versions, and vacuum or compaction to remove them.
LockingShared and exclusive, row and table, gap and next-key, optimistic vs pessimistic.
DeadlockThe database detects and kills one side. Your code must be prepared to retry — that retry is often the missing piece.
SELECT FOR UPDATEThe explicit way to serialise a read-modify-write, and the queue it creates.
Optimistic concurrencyA version column and a conditional update. Scales better and needs a retry loop.
Write-ahead logDurability, crash recovery, checkpoints — and the log everything else is built from: replication, change capture, point-in-time restore.
Long transactionsHold locks, block vacuum, bloat the table. Never open one around a network call.
Distributed transactionsTwo-phase commit and why it is avoided; sagas with compensating actions instead.
IdempotencyThe application-level answer to “did that write actually happen?” when the connection dropped.
Outbox patternThe standard fix for the dual write: change the row and enqueue the event in one transaction.
Isolation in your ORMWhich level the framework opens by default, and whether it retries serialisation failures for you. Usually not.

When one machine is not enough

Replication, partitioning and everything they break. This is the bridge between the database questions and the system-design round, and interviewers use it exactly that way.

Vertical vs horizontalA bigger box is the correct first answer far more often than candidates admit. Say when it stops working.
Read replicasCheap read scale, and replication lag: your own write not visible to your own next read.
Read-your-writesSticky routing, reading from the primary after a write, or a causality token. Name one.
Synchronous vs asynchronous replicationDurability against latency. Semi-synchronous as the middle ground.
FailoverAutomatic or manual, split brain, fencing, and what the client library does during the gap.
PartitioningBy range, by hash, by list. Range gives you scans and hot spots; hash gives you spread and no scans.
ShardingChoosing a shard key you can live with for five years. Cross-shard joins and transactions are the price.
Consistent hashingAdding a node moves 1/n of the keys instead of all of them. Virtual nodes even out the distribution.
Hot keys and hot partitionsThe celebrity problem. Salting, splitting, or a cache in front — all with their own cost.
RebalancingMoving data while serving traffic. Usually the hardest part of a sharding answer.
Connection poolingA database has a hard connection ceiling; a thousand pods with ten connections each will find it.
Backups and restoreSnapshots, point-in-time recovery, RPO and RTO, and the restore you have actually rehearsed.
Multi-regionActive–passive, active–active, conflict resolution, and the speed of light as a hard floor.
Change data captureReading the replication log to feed caches, search indexes and warehouses without dual writes.

The other stores, and when each is the right answer

“Which database would you use?” is a trap only if you answer with a product. Answer with an access pattern and the product follows.

FamilyUse it whenWhat it costs you
RelationalThe data has relationships, you need transactions, and queries will change.Scaling writes past one machine; schema changes on huge tables.
Key–valueYou always know the key, and the value is opaque.No queries you did not plan for; no joins at all.
Wide columnEnormous write volume, queries fixed at design time.The partition key is forever, and modelling is per query.
DocumentAggregates read and written whole; a schema that varies by tenant.Duplication, and consistency across documents is yours to keep.
Search indexText relevance, facets, fuzzy matching, aggregations over free text.Eventual consistency with the source of truth, and reindexing.
CacheReads dominate, and staleness is acceptable and bounded.Invalidation, stampedes, and a cold start that can take the system down.
Time seriesAppend-only measurements, queried by range and rolled up.Cardinality explodes if a label is user-controlled.
GraphThe query is about paths and neighbourhoods, not rows.An operational niche; most graph questions are answered fine by SQL.
Object storeLarge immutable blobs, cheap and durable, served by URL.Latency, listing costs, and no partial updates.
Columnar warehouseAnalytics over billions of rows, few columns at a time.Not for a request path; loads in batches, answers in seconds.
Log / streamOrdered, replayable events consumed by many independent readers.Retention, partition ordering only, and consumer lag as a new thing to watch.
EmbeddedSingle process, no network hop, local state.It is not shared, and it dies with the process unless you plan otherwise.
