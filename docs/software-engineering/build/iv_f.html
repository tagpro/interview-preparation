Part six

Design in the small

The other design round: no traffic estimates, no datacentres, just a domain and forty-five minutes to turn it into types. It rewards different things from the system round — naming, boundaries, and the discipline to leave things out — and it is where object-oriented principles stop being trivia and start being usable.

Topic · xx

From three sentences to a set of types

The exercise has a mechanical opening: extract the nouns, extract the verbs, decide which nouns are types and which are fields, then show one interaction end to end.

Concurrency belongs in the design, not after it. “Two cars arrive at the same instant” is asked in almost every one of these rounds, and the answer is not a synchronized keyword sprinkled on a method: it is a single atomic claim on a spot, with the search allowed to be racy because a failed claim just retries.

// ParkingLot.java — the interesting three lines of a low-level design round.
public final class ParkingLot {
    private final SpotRepository spots;      // interface: in memory now, a table later
    private final PricingPolicy pricing;     // interface: hourly now, dynamic later
    private final Clock clock;               // injected, so the tests do not sleep

    public Ticket park(Vehicle vehicle) {
        for (Spot candidate : spots.freeSpotsFor(vehicle.size())) {
            // The search may be stale; the claim must not be. One atomic
            // compare-and-set decides the winner, and the loser simply
            // takes the next candidate -- no lock spans the search.
            if (candidate.claim(vehicle)) {
                return new Ticket(candidate.id(), vehicle.plate(), clock.instant());
            }
        }
        throw new LotFullException(vehicle.size());
    }
}

Design patterns, filed by the problem they solve

Learn them as answers to questions, not as a list of twenty-three names. In an interview you will use six of them, and you should be able to name the trade-off of each.

Strategy“The rule varies.” An interface plus one implementation per rule. The single most useful pattern in these rounds.
Factory / abstract factory“Construction is a decision.” Keeps new out of the code that uses the thing.
Builder“Too many constructor arguments, some optional.” Also the standard way to build an immutable object.
Singleton“Exactly one.” Ask whether you mean one instance or one lifetime — injection usually answers it better.
Prototype“Copy this configured object.” Rare, but the deep-versus-shallow copy question is not.
Adapter“Their interface, my shape.” The boundary object that keeps a third-party type out of your domain.
Facade“One door to a subsystem.” What a service class usually is.
Decorator“Add behaviour without subclassing.” Retries, caching, metrics, logging — all decorators over one interface.
Proxy“Stand in for it.” Lazy loading, access control, remote calls.
Composite“A thing and a group of things behave the same.” File systems, menus, permissions trees.
Bridge“Two dimensions of variation.” Stops the class count multiplying.
Flyweight“Millions of nearly identical objects.” Share the immutable part; interning strings is the everyday case.
Observer“Tell whoever cares.” Events, listeners, and the memory leak from never unsubscribing.
Command“Make the action an object.” Undo, queues, retries, audit logs.
State“Behaviour depends on a mode.” The honest alternative to a growing enum and a switch.
Template method“Same skeleton, different steps.” Easy to overuse; strategy is usually the better shape.
Chain of responsibility“Try each handler in turn.” Middleware, filters, interceptors.
Iterator“Walk it without exposing it.” A common coding-round exercise in its own right.
Mediator“Stop objects wiring themselves to each other.” Chat rooms, air traffic control, forms.
Memento“Snapshot and restore.” Undo without exposing internals.
Visitor“New operation over a fixed set of types.” Compilers, ASTs — and the reason sealed hierarchies exist.
Interpreter“A tiny language.” Rules engines and expression evaluation.
Repository and unit of workNot in the original book, asked more often than half of it.

The low-level design catalogue

A shorter list than the system-design one, and each entry has a known trap. Interviewers reuse the traps far more than they reuse the problems.

Elevator systemModelling the car without the scheduler. The interesting object is the dispatcher.

Topic · xx

API design

Asked on its own, and as a sub-question of both design rounds. The whole subject is: what is the resource, what can go wrong, and how does the client find out.

RESTResources and nouns, correct verbs, correct status codes, and the difference between 400, 401, 403, 404, 409 and 422.
IdempotencyPUT and DELETE are idempotent by definition; POST is made so with a client key. Say which yours is.
PaginationOffset is simple and wrong at scale; cursor pagination is stable under insertion. Know both.
Filtering and sortingWhitelist the fields. An open sort parameter is an unindexed query waiting to happen.
ErrorsA stable machine-readable code, a human message, and a request ID. Never a stack trace.
VersioningURL, header or content type — and the harder half: how a field is deprecated and removed.
CompatibilityAdditive changes only; never repurpose a field. What breaks a client is rarely what you expected.
Rate limitsCommunicated in headers, with a retry hint. A limit the client cannot see is a limit it will hammer.
gRPCSchema-first, streaming, deadlines that propagate. Costs browser reach and human debuggability.
GraphQLThe client picks the shape. Costs you query cost control, caching and the N+1 problem moving server-side.
WebhooksSigned, retried, idempotent, replayable. The receiver must assume duplicates and out-of-order delivery.
Long-running work202 plus a status resource, or a callback. Do not hold a connection open for four minutes.
Bulk operationsPartial success is the design problem. Per-item results, not one status code for a hundred items.
AuthenticationWhere the token goes, how it is scoped, and what a leaked one can do — see part ten.

Part seven

Languages and runtimes

Two rounds’ worth of questions hide here: the ones asked of any language, which test whether you understand the machine underneath the syntax, and the ones asked of yours, which test whether you have read the manual or only the tutorial.

Topic · xx

The five questions asked of every language

Whatever you claim on your CV, expect these five. They are the same five for Java, Python, Go, C++, TypeScript and Rust; only the answers change.

MemoryStack versus heap, what a reference is, how memory is reclaimed, and what a leak looks like in a garbage-collected language.
ConcurrencyWhat a unit of concurrency costs, what is shared, and what the language guarantees about visibility.
ErrorsValues or exceptions, checked or not, and what happens to an error nobody handles.
The type systemStatic or dynamic, nominal or structural, generics and variance, and how much of it survives to runtime.
Build and dependenciesResolution, lock files, transitive conflicts, reproducible builds, and the artifact you actually deploy.
Equality and identityValue versus reference equality, and the hash contract every language has and every candidate forgets.
Mutability and copyingDeep versus shallow, defensive copies, and why a mutable default argument is a bug in more than one language.
The standard libraryWhich collection to reach for, and its complexity. Interviewers do ask what happens when a map resizes.
Performance toolsThe profiler, the allocation profile, and one story about using them on real code.
IdiomWhat reviewers in that language would object to. Writing Java in Python reads as inexperience even when it works.
