Part one

The machine you are installing

L1 · Beginner

Java is two artefacts: a compiler that turns source into bytecode once, and a virtual machine that turns bytecode into machine code every time you run. Everything people say about the platform — portable, verbose, slow to start, fast once warm — is a property of that split. Install the toolchain, run one file three different ways, and read the bytecode with your own eyes before part two adds the language on top.

Java · 00

Install a JDK and meet the JVM

Two commands install a full JDK. The interesting part is what you just installed: a compiler, a launcher, and a virtual machine that owns your program’s memory, garbage collection and threads for its whole life.

Why 21 and not the newest? Java ships a release every six months and stamps one as LTS (long-term support) every two years. The LTS line runs 8 → 11 → 17 → 21 → 25; the versions in between are real releases that stop getting updates six months later, which is why production skips them. Java 25 is the newest LTS (September 2025); 21 is what most production runs and what every line on this page is written against. Nothing here breaks on 25.

Now run something. Since Java 11 the launcher compiles a single source file in memory, so a beginner never needs to see javac on day one:

public class Hello {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : "world";
        System.out.println("Hello, " + name);
    }
}

Run it

Save as Hello.java and launch the file directly — no compile step, no project. Pass an argument to see args filled in.

$ java Hello.java Ada

For anything smaller than a file there is JShell, the REPL that ships with every JDK — the same role the python prompt played on the Python page. Statements do not need a class, a semicolon is optional at the prompt, and every result is bound to $1, $2… for reuse.

JDK, JRE, JVM — three words, one download

The JVM is the virtual machine in the figure. The JRE is the JVM plus the standard library — enough to run. The JDK is the JRE plus the tools: javac, jshell, javap, jar. You installed the JDK; production containers often carry a trimmed runtime built with jlink.

Java · 00

A Java file, dissected down to the bytecode

Every declaration in a Java file is load-bearing: the package is a directory, the public class is the file name, and public static void main(String[] args) is a signature the JVM looks up literally. Then javap shows you what the compiler actually wrote.

Here is the same program grown up: a package, an import, a constant. Read it top to bottom, because each line is a contract with either the compiler or the JVM:

// src/dev/ladder/hello/Greeter.java -- path and package MUST agree
package dev.ladder.hello;

import java.time.LocalTime;      // a compile-time name shorthand -- unlike Python's
                                 // import, it executes nothing at runtime
public class Greeter {

    private static final String FALLBACK = "world";   // a class-level constant

    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : FALLBACK;
        System.out.println("Hello, " + name + " at " + LocalTime.now());
    }
}

Dissect the one line that does something. System is a class in java.lang (the only package imported automatically); out is a static final field on it, of type PrintStream; println is an overloaded method on that stream. So System.out.println is not an incantation — it is field access followed by a method call, and by the end of part two you can read it that way.

Now compile explicitly and look at the result. javac -d out mirrors the package into a directory tree; java -cp out tells the launcher where that tree starts; javap -c disassembles what the compiler wrote.

Run it

Compile, run with an argument, then disassemble main. You are looking at the stack-machine instructions the interpreter executes and the JIT later compiles — every mystery on this page bottoms out here.

$ mkdir -p src/dev/ladder/hello out
$ javac -d out src/dev/ladder/hello/Greeter.java
$ java -cp out dev.ladder.hello.Greeter Ada

Where the ceremony is going

Java 25’s compact source files let a beginner write void main() { IO.println("hi"); } — no class, no static, no args — but every production codebase still looks like the file above, so this page keeps the full form.

Part one

Objects, values, and the type system

L1 · Beginner

Java draws a line Python never drew: a handful of primitive types live directly in the variable, and everything else is a reference into the heap. Hold that line in your head and the classic surprises — == lying about equality, a key vanishing from a HashMap, a boxed 127 behaving differently from a boxed 128 — become predictable consequences instead of folklore.

Java · 00

Primitives, references, and the two meanings of ==

A primitive variable holds the value itself; a reference variable holds a pointer into the heap. == compares whatever is in the slot — which is the value for primitives and the address for objects. That one sentence is the most common beginner bug in the language.

Eight primitive types exist; four carry almost all production code. They are not objects: no methods, no null, no heap allocation — the value sits in the variable, the way a C or Go value would.

TypeSizeLiteralNotes
int32-bit42The default for whole numbers; overflows silently at 231−1
long64-bit10_000_000_000LIDs, timestamps, money-in-cents; note the L
double64-bit0.1IEEE-754 — fine for science, never for money
boolean—trueOnly true/false; no truthy values, unlike Python

byte, short, float and char complete the set; you will meet them in I/O buffers and old APIs. Everything that is not one of the eight — String, arrays, every class you write — is a reference type: the variable holds a pointer, null means the pointer points at nothing, and copying the variable copies the arrow, never the object.

Collections cannot hold primitives, so Integer, Long and friends exist as boxed wrappers and the compiler autoboxes in both directions. The trap: the JVM caches boxes for −128..127, so == on small boxed values compares two pointers to the same cached box and returns true — then your test data grows past 127 and it silently returns false. Strings have the same shape: literals are pooled and shared, so == works right up until a string arrives from a file, a request, or new String(...). Prove all of it to yourself:

public class Surprises {
    public static void main(String[] args) {
        Integer a = 127, b = 127;             // both autoboxed from the cache
        Integer c = 128, d = 128;             // two fresh boxes on the heap
        System.out.println(a == b);           // true  -- same cached object
        System.out.println(c == d);           // false -- different objects, equal values
        System.out.println(c.equals(d));      // true  -- what you nearly always meant

        String s1 = "task";
        String s2 = "task";                   // same pooled literal as s1
        String s3 = new String("task");       // new forces a fresh object
        System.out.println(s1 == s2);         // true  -- pooling, an accident you cannot rely on
        System.out.println(s1 == s3);         // false -- different objects
        System.out.println(s1.equals(s3));    // true

        String t = s1.toUpperCase();          // Strings are immutable: this is a NEW string
        System.out.println(s1 + " " + t);     // task TASK -- s1 untouched

        int[] xs = {1, 2, 3};                 // arrays are fixed-size, forever
        System.out.println(xs.length);        // 3 -- a field, not a method
    }
}

Run it

One file, six lies and truths. If any line surprises you, re-read the figure: every result is “== compared what was in the slot”.

$ java Surprises.java
true
false
true
true
false
true
task TASK
3

The rule that survives this topic

Compare primitives with ==. Compare objects — every String, every Integer, everything you write — with .equals(), or with Objects.equals(a, b) when either side may be null. An == between two reference types is a code-review flag unless identity is genuinely the question.

Java · 00

Classes the long way, then records

Write one value class by hand — fields, constructor, accessors, equals, hashCode, toString — so you know exactly what a record generates when it replaces all thirty lines with one.

A Money type, the classical way. Note the shape: every field private final (set once, in the constructor, never again), accessors instead of public fields, and the three methods every value type owes the rest of the ecosystem:

import java.util.Objects;

public final class Money {                       // final class: cannot be subclassed
    private final long cents;                    // final field: assigned once, in the constructor
    private final String currency;

    public Money(long cents, String currency) {
        if (cents < 0) throw new IllegalArgumentException("negative amount");
        this.cents = cents;
        this.currency = Objects.requireNonNull(currency);
    }

    public long cents()       { return cents; }
    public String currency()  { return currency; }

    public Money plus(Money other) {             // no mutation: arithmetic returns a NEW Money
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(cents + other.cents, currency);
    }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;
        return cents == m.cents && currency.equals(m.currency);
    }

    @Override public int hashCode() { return Objects.hash(cents, currency); }

    @Override public String toString() { return cents + " " + currency; }
}

Thirty lines, and every one of them mechanical. Since Java 16 the language writes them for you:

public record Money(long cents, String currency) {}   // the same class, generated

A record declares its state in the header, and the compiler generates the final fields, the canonical constructor, accessors named after the components (cents(), not getCents()), and value-based equals, hashCode and toString. You add back only what is genuinely yours — validation goes in a compact constructor, domain logic is an ordinary method:

record Money(long cents, String currency) {
    Money {                                      // compact constructor: validate, then fields assign
        if (cents < 0) throw new IllegalArgumentException("negative amount");
    }
    Money plus(Money other) {
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(cents + other.cents, currency);
    }
}

public class MoneyDemo {
    static final Money FREE = new Money(0, "GBP");    // static: one per class, shared

    public static void main(String[] args) {
        Money a = new Money(12_50, "GBP");            // instance state: one per object
        Money b = new Money(4_99, "GBP");
        System.out.println(a.plus(b));
        System.out.println(a.equals(new Money(12_50, "GBP")));
        System.out.println(new Money(-1, "GBP"));     // validation fires
    }
}

Run it

Both classes sit in one file (only MoneyDemo is public), so the single-file launcher compiles them together. Value equality works with no equals written, and the compact constructor rejects the bad amount.

$ java MoneyDemo.java
Money[cents=1749, currency=GBP]
true
Exception in thread "main" java.lang.IllegalArgumentException: negative amount

static versus instance is the other axis worth fixing now: a static member belongs to the class (one FREE, shared; Math.max, Instant.now()), an instance member to each object (each Money has its own cents). main is static because when the JVM calls it, no object of your class exists yet. And final means “assigned once” for a field or variable, “no subclassing” for a class — it does not make the referenced object immutable.

Real money is BigDecimal or cents, never double

0.1 + 0.2 == 0.30000000000000004 in Java exactly as on the Python page. Hold money as long cents (as Money does) or use new BigDecimal("19.99") — constructed from a String, because new BigDecimal(0.1) faithfully preserves the binary error you were escaping.

Java · 00

Collections, generics, and the equals/hashCode contract

Arrays are fixed; real code uses List, Map and Set, parameterised with the type they hold. The compiler enforces the element type; the collection enforces a contract on you — and HashMap quietly loses data when you break it.

Three interfaces carry the standard library: List<T> (ordered, indexed, duplicates allowed — usually ArrayList), Map<K, V> (key to value — usually HashMap), and Set<T> (no duplicates — usually HashSet). The angle brackets are generics: List<Task> is a list that only accepts and only returns Task, checked at compile time, where Python’s list[Task] is a hint mypy checks and the runtime ignores. The diamond <> on the right-hand side asks the compiler to repeat the type parameter so you do not have to.

import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

record Task(String title, int priority, boolean done) {}

public class TaskListDemo {
    public static void main(String[] args) {
        List<Task> tasks = new ArrayList<>();          // diamond: compiler fills in <Task>
        tasks.add(new Task("write the Flyway migration", 1, false));
        tasks.add(new Task("wire the /tasks endpoint", 2, false));
        tasks.add(new Task("install a JDK", 1, true));

        tasks.sort(Comparator.comparing(Task::priority)   // sort by priority,
                             .thenComparing(Task::title)); // ties broken by title

        for (Task t : tasks) {                             // for-each: no index bookkeeping
            System.out.println((t.done() ? "[x] " : "[ ] ") + t.title());
        }

        Map<Integer, Long> perPriority = new HashMap<>();
        for (Task t : tasks) {
            perPriority.merge(t.priority(), 1L, Long::sum); // count per key, no if-absent dance
        }
        System.out.println(perPriority);

        Set<String> owners = new HashSet<>(List.of("ana", "ben", "ana"));
        System.out.println(owners.size());                 // deduplicated by equals/hashCode
    }
}

Run it

Sorting mutates the list in place; the map counts tasks per priority; the set swallows the duplicate. All three behaviours lean on Task’s record-generated equals and hashCode.

$ java TaskListDemo.java
[x] install a JDK
[ ] write the Flyway migration
[ ] wire the /tasks endpoint
{1=2, 2=1}
2

List.of(...), Map.of(...) and Set.of(...) build compact immutable literals — ideal for constants and test data, with one trap: they reject mutation at runtime, not compile time. The type system cannot see the difference between an ArrayList and an immutable list behind the same List interface:

List<String> tags = List.of("api", "db");   // immutable literal
tags.add("ui");                             // compiles fine...
// Exception in thread "main" java.lang.UnsupportedOperationException

List<String> mutable = new ArrayList<>(List.of("api", "db"));   // the copy that grows

Watch it happen. This key overrides both methods correctly — the bug is purely that it mutates after insertion:

import java.util.HashMap;
import java.util.Map;

class MutableKey {
    int n;
    MutableKey(int n) { this.n = n; }
    @Override public boolean equals(Object o) {
        return o instanceof MutableKey k && k.n == n;
    }
    @Override public int hashCode() { return Integer.hashCode(n); }
}

public class LostEntry {
    public static void main(String[] args) {
        Map<MutableKey, String> m = new HashMap<>();
        MutableKey k = new MutableKey(11);
        m.put(k, "hello");
        k.n = 14;                                       // the key moves AFTER insertion
        System.out.println(m.get(k));                   // null -- looked in the wrong bucket
        System.out.println(m.get(new MutableKey(11)));  // null -- right bucket, equals now fails
        System.out.println(m.size());                   // 1  -- the entry is still in there
    }
}

Run it

Both lookups miss while size() insists the entry exists. Fix is not code — it is policy: keys are immutable, ideally records.

$ java LostEntry.java
null
null
1
Part one

Contracts, hierarchy, and failure

L1 · Beginner

Interfaces are how Java code stays swappable, and sealed hierarchies are how modern Java makes the compiler check what Go delegates to a linter and Python to mypy. Then the part every service is judged on: what happens when things fail — which exceptions to catch, which to wrap, and which to let fly.

Java · 00

Interfaces, and sealed hierarchies the compiler checks

An interface is a contract with no state: methods a type promises to provide. Program to it and implementations become swappable. Seal it, and the compiler knows the full set of implementations — and starts proving your switch handles every one.

The classic half first. An interface declares what, a class declares how, and implements connects them. Two habits are non-negotiable from day one: declare variables as the interface type, and write @Override on every implementing method so the compiler catches the typo’d signature that would otherwise become a brand-new method:

import java.util.ArrayList;
import java.util.List;

record Task(String title, int priority, boolean done) {}

interface TaskStore {
    void add(Task task);
    List<Task> all();

    default boolean isEmpty() {                // a default method: behaviour ON the contract,
        return all().isEmpty();                // inherited by every implementation for free
    }
}

class InMemoryTaskStore implements TaskStore {
    private final List<Task> tasks = new ArrayList<>();   // composition: HAS a list,
                                                          // does not EXTEND ArrayList
    @Override public void add(Task task) { tasks.add(task); }
    @Override public List<Task> all()    { return List.copyOf(tasks); }
}

public class StoreDemo {
    public static void main(String[] args) {
        TaskStore store = new InMemoryTaskStore();   // the variable is the interface;
        store.add(new Task("learn interfaces", 1, false));   // swap in a JdbcTaskStore later
        System.out.println(store.isEmpty());         // and this line does not change
        List<String> xs = new ArrayList<>();         // the same habit, stdlib edition
        xs.add("program to the interface");
        System.out.println(xs);
    }
}

Run it

The main never mentions InMemoryTaskStore after the new. In part seven the same idea lets a Postgres-backed repository replace the in-memory store, and the calling code does not move.

$ java StoreDemo.java
false
[program to the interface]

InMemoryTaskStore has a list rather than being one — composition over inheritance. Java has single inheritance (extends, one superclass) and it is the most over-used feature in the language’s history: a deep extends chain welds subclasses to a parent’s implementation details, and any hierarchy more than two levels deep is a code-review flag. Interfaces impose no such coupling — a class can implement many — and default methods cover the “shared behaviour” excuse that used to justify base classes.

Now the modern half. By default an interface is open — anyone, anywhere, can implement it. A sealed interface names its complete set of implementations, and that closedness is what turns switch into a proof:

import java.util.List;

sealed interface Payment permits Card, Cash, Transfer {}
record Card(String last4, long cents)    implements Payment {}
record Cash(long cents)                  implements Payment {}
record Transfer(String iban, long cents) implements Payment {}

public class PaymentDemo {
    static String describe(Payment p) {
        return switch (p) {                       // switch as an EXPRESSION: it returns a value
            case Card c     -> "card *" + c.last4() + ", " + c.cents() + " cents";
            case Cash c     -> "cash, " + c.cents() + " cents";
            case Transfer t -> "transfer to " + t.iban();
        };                                        // no default: exhaustiveness is checked
    }

    public static void main(String[] args) {
        List<Payment> day = List.of(
            new Card("4242", 19_99), new Cash(5_00), new Transfer("DE89 3704", 120_00));
        for (Payment p : day) System.out.println(describe(p));
    }
}

Run it

Then do the experiment that matters: add record Voucher(long cents) implements Payment {} to the permits list and rerun — the compile error names the switch that is no longer complete.

$ java PaymentDemo.java
card *4242, 1999 cents
cash, 500 cents
transfer to DE89 3704
# after adding Voucher:
PaymentDemo.java: error: the switch expression does not cover all possible input values
Java · 00

Exceptions: the hierarchy, the resources, and Optional

Java splits failure into three families and treats one of them — checked exceptions — as part of a method’s type. Knowing which family you are holding tells you the correct reaction: fix, handle, wrap, or stand clear.

The reactions, family by family. Error means the JVM itself is in trouble — there is no catch block that un-runs-out memory. RuntimeException means your code is wrong: a NullPointerException is fixed by the null check you forgot, not by a catch. Checked exceptions — everything else under Exception — mark environmental failure that a correct program still meets: the file missing, the socket closed. The compiler makes you acknowledge those, and the idiomatic acknowledgement at a boundary is: handle it if you genuinely can, otherwise wrap it in your own unchecked exception with the cause attached and let it fly.

Resource cleanup has one modern answer. Anything AutoCloseable goes in the parentheses of try, and the JVM closes it — on success, on exception, in reverse order for multiple resources. The old try/finally dance, with its own bug where close() throws and eats the real exception, is legacy code you will read but should not write:

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.Optional;

class TaskStoreException extends RuntimeException {      // unchecked: extends RuntimeException
    TaskStoreException(String message, Throwable cause) { super(message, cause); }
}

public class ExceptionsDemo {

    static List<String> loadLines(Path file) {
        try (var reader = Files.newBufferedReader(file)) {   // try-with-resources: closed always,
            return reader.lines().toList();                  // even when an exception flies
        } catch (IOException e) {                            // the checked boundary...
            throw new TaskStoreException("could not read " + file, e);   // ...wrapped WITH cause
        }
    }

    static Optional<String> firstMatching(List<String> lines, String needle) {
        return lines.stream()                                // Optional: "maybe absent", in the
                    .filter(l -> l.contains(needle))         // return type where callers see it
                    .findFirst();
    }

    public static void main(String[] args) {
        List<String> lines = List.of("install jdk", "learn records");
        System.out.println(firstMatching(lines, "rec").orElse("no match"));
        System.out.println(firstMatching(lines, "zzz").orElse("no match"));
        loadLines(Path.of("missing.csv"));                   // watch the Caused by chain
    }
}

Run it

Two clean Optional results, then the wrapped failure. The stack trace is the payoff: your exception on top, the original NoSuchFileException preserved underneath as Caused by — both stacks, nothing lost.

$ java ExceptionsDemo.java
learn records
no match
Exception in thread "main" TaskStoreException: could not read missing.csv
        at ExceptionsDemo.loadLines(ExceptionsDemo.java:16)
        at ExceptionsDemo.main(ExceptionsDemo.java:30)
Caused by: java.nio.file.NoSuchFileException: missing.csv
        ...

Optional<T> deserves its own rules, because it is routinely misused. It exists to make “this might be absent” visible in a return type, so the caller is forced to decide — orElse, orElseThrow, map, ifPresent. That is the whole job. Never make it a field (serialisation and JPA both choke, and it solves nothing there), never a parameter (callers end up writing Optional.of(x) noise — overload instead), and never call bare .get() — that is the old NullPointerException wearing a fancier name.

Do

store.findByTitle("ship it").map(Task::title).orElse("—") — absence handled in one chain, at the call site, visibly.

Do not

opt.get() without isPresent(), Optional fields, Optional parameters, or catch (Exception e) {} — the empty catch block is the same bug as Python’s bare except: pass, and it will cost someone a weekend.
