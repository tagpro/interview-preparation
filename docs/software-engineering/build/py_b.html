Part three

Types and structure

Python will run almost anything you write. The tools in this part are how a team stops it running the wrong thing: annotations a checker reads, record types that say what a value is, and an import system whose rules decide what your process actually loaded.

Python · 00

Type hints: what they do and what they do not

An annotation is data attached to a function object. The interpreter stores it and moves on. Everything useful about hints happens in a second program — mypy or pyright — that you have to run yourself.

from typing import Literal, Protocol, TypedDict

class Row(TypedDict):          # the shape of JSON you do not own
    id: int
    status: Literal["open", "closed"]

class Store(Protocol):         # structural: no base class, no registration
    def get(self, key: str) -> Row | None: ...

def load(store: Store, key: str) -> Row | None:
    return store.get(key)      # any object with a matching get() type-checks

# PEP 695 (3.12+): generic syntax with no import, T scoped to the function
def first[T](xs: list[T]) -> T:
    return xs[0]

# the older spelling, still what most of the ecosystem reads and writes
from typing import TypeVar, cast
U = TypeVar("U")

def last(xs: list[U]) -> U:
    return xs[-1]

from __future__ import annotations   # hints stop being evaluated eagerly; the default on 3.14+ (PEP 649)

def handler(req: Request) -> Response: ...  # forward reference, unquoted -- lazy annotations resolve it

n = cast(int, config.get("timeout"))  # zero run-time effect -- a lie you are asserting is true
L1 · Beginner

Annotate the boundaries first

  • Parameters and returns — def get(uid: int) -> User: is where hints pay for themselves.
  • Containers — list[int], dict[str, int], tuple[str, ...]. Built-in generics since 3.9; no typing.List needed.
  • Maybe-missing — str | None is the honest type for anything that can be absent.
  • No enforcement — passing a str where int is annotated runs exactly as before. Nothing raises.
  • Your editor already uses them — completion and go-to-definition get better the moment you add them.
L2 · Intermediate

Say more than “object”

  • Optional[X] is X | None — and a default of None does not make a parameter optional in the type sense; annotate it.
  • Any is an escape hatch — it silently switches checking off for everything it touches. object is the safe “I do not know”.
  • TypedDict — types a dict you receive from JSON without turning it into a class.
  • Literal["asc", "desc"] — catches the typo in the string argument that would otherwise reach production.
  • Protocol — structural typing: anything with the right methods fits, no inheritance. Duck typing the checker can see.
  • Ramp the strictness — start with --ignore-missing-imports, add disallow_untyped_defs per package as each one is cleaned up.
L3 · Advanced

Generics, laziness and lies

  • PEP 695 — def first[T](xs: list[T]) -> T: in 3.12+; the older TypeVar spelling still fills every codebase you will read.
  • Variance in one sentence — a list[Dog] is not a list[Animal], because you could append a cat to it; immutable Sequence[Dog] is.
  • from __future__ import annotations — annotations become strings, so forward references work and import cost drops. On 3.14+ you rarely need it: PEP 649 defers annotation evaluation by default, and forward references simply work. Anything reading annotations at run time should go through annotationlib / get_type_hints.
  • typing.cast — zero run-time effect, pure assertion to the checker. A lie you own, so leave a comment saying why it is true.
  • Different job, different tool — a checker cannot know what came off a socket. Validate that with pydantic; check the rest statically.
Python · 00

Dataclasses, NamedTuple, TypedDict, Pydantic

Four ways to say “this is a user record”. They differ on exactly four things: whether it can be mutated, whether anything is checked at run time, what it costs per instance, and whether you had to install it.

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class User:
    id: int
    name: str
    tags: list[str] = field(default_factory=list)   # not tags: list = []

    def __post_init__(self) -> None:
        if self.id <= 0:                            # frozen: use object.__setattr__
            raise ValueError("id must be positive") # to normalise fields here

u = User(1, "ada")
u.name = "grace"        # FrozenInstanceError -- hashable, safe as a dict key

# NamedTuple — when tuple-ness IS the point: unpack it, hash it, index it
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float

p = Point(1.0, 2.0)
x, y = p                       # unpacks like any tuple
p[0]                           # 1.0 — still indexable
p._replace(x=9.0)              # returns a NEW Point; p itself never changes
{p: "origin-ish"}              # hashable out of the box, no frozen= needed
# TypedDict — for a JSON shape you do not own; a plain dict at run time
from typing import TypedDict

class UserPayload(TypedDict):
    id: int
    name: str
    tags: list[str]

def greet(u: UserPayload) -> str:
    return f"hello {u['name']}"    # dict access, not attribute access

raw: UserPayload = {"id": 1, "name": "ada", "tags": []}
raw["naem"] = "typo"               # mypy/pyright catch this; nothing does at run time
greet({"id": 1})                   # also only a type-checker error — TypedDict never runs
# BaseModel — the same record, but arriving from outside and needing to be believed
from pydantic import BaseModel, Field, ValidationError

class User(BaseModel):
    id: int = Field(gt=0)
    name: str
    tags: list[str] = []           # pydantic copies the default per instance — safe here

try:
    u = User.model_validate({"id": "1", "name": "ada"})  # "1" coerced to 1
except ValidationError as e:
    log.warning("bad user payload: %s", e.errors())

u.model_dump()                     # -> plain dict, JSON-safe with mode="json"

Records make tagged unions, and match (3.10+) is how you consume one — the checker narrows each arm, and assert_never turns “forgot a variant” into a type error instead of a production bug:

# dispatch on a tagged union: match narrows, assert_never proves exhaustiveness
from dataclasses import dataclass
from typing import assert_never

@dataclass
class Created:
    id: int

@dataclass
class Deleted:
    id: int
    reason: str

def apply(ev: Created | Deleted) -> str:
    match ev:
        case Created(id=i):            return f"created {i}"
        case Deleted(id=i, reason=r):  return f"deleted {i}: {r}"
        case _:                        assert_never(ev)  # unreachable -- or the union grew
L1 · Beginner

Stop passing dicts around

  • A dict has no shape — user["nmae"] is a KeyError at 2am; user.nmae is caught by the checker and your editor.
  • @dataclass — write the fields with their types and you get __init__, __repr__ and __eq__ for free.
  • Defaults work as expected — retries: int = 3, and required fields must come before defaulted ones.
  • The repr matters — a dataclass prints as User(id=1, name='ada'), which is most of a debugging session.
  • It is still a normal class — add methods, inherit, use it anywhere.
L2 · Intermediate

The four arguments that matter

  • field(default_factory=list) — the mutable-default trap again; a bare [] as a class-level default is a ValueError from dataclasses, and a shared list everywhere else.
  • frozen=True — assignment raises, and the instance becomes hashable. Good default for anything you pass between threads.
  • slots=True — no per-instance __dict__: less memory, faster attribute access, no typo-attributes.
  • __post_init__ — derived fields and cheap invariants, run after __init__ assigns.
  • NamedTuple — when tuple-ness is the point: unpacking, use as a dict key, returning from a function that used to return a plain tuple.
  • TypedDict — for a JSON shape you do not own. It is a dict at run time; the types exist only for the checker.
L3 · Advanced

Validate at the edge, trust inside

  • Pydantic belongs at the boundary — HTTP body, queue message, config file, third-party response. Parse once, into a typed object.
  • Do not validate in a loop — re-validating an already-parsed model on every internal hop buys nothing and shows up in profiles.
  • v2 does the work in Rust — much faster than v1, but still far more expensive than a dataclass constructor, which does almost nothing.
  • attrs — the library dataclasses came from; still ahead on validators, converters and __slots__ ergonomics.
  • The rule — untrusted data crosses exactly one line in your codebase. After that line it is a typed record, and no function downstream defends itself.
Python · 00

Modules, packages, imports and environments

import orders is a search, an execution and a cache, in that order. Knowing those three steps explains import side effects, why the second import is free, and why a circular import fails with an attribute error rather than a clear message.

L1 · Beginner

One environment per project

  • Module vs package — a module is a .py file; a package is a directory of them, importable as a unit.
  • Import forms — import orders, from orders import Order, import orders as o. Avoid from x import *: the reader cannot tell where a name came from.
  • if __name__ == "__main__": — the guard that makes a file both importable and runnable, and stops multiprocessing re-running your script.
  • A virtual environment per project — python -m venv .venv, or let uv manage it. It is a directory with its own interpreter and its own packages.
  • Never install globally — two projects will eventually want two versions of the same library, and system Python belongs to the system.
L2 · Intermediate

Make the environment reproducible

  • Absolute imports — from myproj.orders import Order reads the same from anywhere. Keep relative imports (from .orders import Order) shallow if you use them at all.
  • sys.modules is the cache — re-importing gives you the same object. Monkeypatching in tests and reload tricks both hang off this.
  • Import side effects — anything at module level runs on import. Keep it to constants and definitions; put work in functions.
  • pyproject.toml — one file for dependencies, build backend, and tool config (ruff, mypy, pytest).
  • Pin and lock — loose ranges for a library you publish, an exact lockfile for an application you deploy.
  • pip vs uv — same package format; uv resolves and installs an order of magnitude faster and manages the venv and lockfile itself.
L3 · Advanced

Break the cycle, watch the clock

  • Three fixes for a circular import — move the shared type to its own module, import inside the function that needs it, or accept the dependency is backwards and invert it.
  • if TYPE_CHECKING: — imports needed only for annotations, skipped at run time. Pairs with from __future__ import annotations.
  • The src layout — putting the package under src/ means tests import the installed package, not the working copy that happens to be on sys.path.
  • Editable installs — pip install -e . puts a link on the path, so edits take effect without reinstalling.
  • Namespace packages — a directory without __init__.py can still be a package split across distributions. Usually a surprise rather than a plan.
  • Import time is start-up cost — python -X importtime -c "import myproj" prints the tree with microseconds per module. A lazily imported heavy dependency is often the whole fix.
Part four

Errors and resources

Python asks forgiveness rather than permission: you attempt the operation and handle the exception. That is idiomatic and it is race-free, but it only works if the handler catches what it can actually deal with — and if the file, socket or transaction is released whichever way control leaves the block.

Python · 00

Exceptions, EAFP, and chaining

Four clauses, four different jobs. else is the part of the body that must not be inside the try; finally is the part that runs whatever happens, including on the way out of a return.

import contextlib

class Transient(Exception): ...    # worth a retry: timeout, 503, connection reset
class Terminal(Exception): ...     # never retry: 400, 403, bad payload

def fetch(url: str) -> bytes:
    try:
        return http.get(url)
    except TimeoutError as err:
        raise Transient(f"timeout: {url}") from err
    except PermissionError as err:
        raise Terminal(f"forbidden: {url}") from err

with contextlib.suppress(FileNotFoundError):
    os.remove(tmp)                 # "already gone is fine" -- not a bare except

# all four clauses, each with a job try/except alone cannot do
def load_batch(path: str) -> list[Row]:
    try:
        fh = open(path)
    except FileNotFoundError:
        return []                  # handled: an empty batch is a valid outcome
    else:
        with fh:                   # only runs if open() did NOT raise; the with
            return parse(fh)       # closes fh even if parse() raises -- next topic
    finally:
        log.info("load_batch done: %s", path)    # always -- even on the return above
L1 · Beginner

Catch what you can handle

  • The hierarchy — everything derives from BaseException; the errors you mean are under Exception. ValueError, KeyError, OSError are the ones you meet daily.
  • Be specific — except ValueError:, not except Exception:. A handler that catches everything hides the bug you have not found yet.
  • Never a bare except: — it catches KeyboardInterrupt and SystemExit too, so Ctrl-C stops working.
  • else — runs only when the try raised nothing; keeps the success path out of the guarded block.
  • finally — runs on every exit path. Cleanup goes here, or better, in a with.
L2 · Intermediate

EAFP, and errors with meaning

  • EAFP beats LBYL — try: open(p) against if os.path.exists(p): the check-then-act version has a race, and does the work twice.
  • Custom exception types — one base class per package, so callers can catch your errors without catching everything.
  • raise NewError(...) from err — translation with the cause attached. The default implicit chaining is fine too; the anti-pattern is from None.
  • contextlib.suppress(FileNotFoundError) — says “I expect this and it is fine” in one line, and cannot accidentally swallow more.
  • Exceptions as control flow — StopIteration ends every for loop, KeyError drives defaultdict. Idiomatic here, unlike most languages.
  • Log with the traceback — logging.exception(...) inside the handler; a logged message without a traceback is half an incident report.
L3 · Advanced

Groups, cost, and taxonomy

  • ExceptionGroup and except* — 3.11+. A TaskGroup where three tasks fail raises all three; except* handles each type and re-raises the rest.
  • Cost on hot paths — setting up a try is nearly free; raising is not. Building a traceback in a per-row loop is measurable, so a sentinel return can win there.
  • Taxonomy drives retries — transient (timeout, 503, deadlock) retries with backoff and jitter; terminal (400, 403, schema error) must not, or you have built a retry storm. The same split as the Go and foundations pages.
  • Do not catch BaseException — that is where KeyboardInterrupt, SystemExit and asyncio.CancelledError live. Catching them breaks shutdown and cancellation.
  • Retries need idempotency — a timeout does not tell you whether the write landed. Retry only what carries an idempotency key.

Context managers and deterministic cleanup

with is syntax for a try/finally that someone else wrote and tested. The release runs on the exception path as well as the happy one, which is the entire reason the statement exists.

import contextlib, logging, time

@contextlib.contextmanager
def timed(label: str):
    start = time.perf_counter()
    try:
        yield                       # the body of the with block runs here
    finally:                        # runs on the exception path too
        ms = (time.perf_counter() - start) * 1000
        logging.info("%s took %.1f ms", label, ms)

with timed("query"), conn.transaction():    # left to right in, right to left out
    rows = conn.fetch_all(sql)
L1 · Beginner

Use with for anything you open

  • with open(path) as f: — the file closes when the block ends, however it ends.
  • Why it matters — if json.load(f) raises halfway, the file still closes; a plain f.close() at the end of the function never runs.
  • Not just files — sockets, locks, database connections and transactions, tempfile, subprocess.Popen.
  • Several at once — with open(a) as src, open(b, "w") as dst: in one statement, entered left to right.
  • The as target — is whatever __enter__ returns, which is not always the manager itself.
L2 · Intermediate

Write your own

  • The protocol — __enter__(self) returns the resource; __exit__(self, exc_type, exc, tb) releases it and returns falsy to let any exception through.
  • @contextlib.contextmanager — one function, one yield. Everything before is setup, everything after is teardown.
  • Wrap the yield in try/finally — without it, an exception in the body skips your teardown entirely. This is the bug in most hand-written generators.
  • ExitStack — for a number of resources known only at run time: stack.enter_context(open(p)) in a loop, all unwound together.
  • closing, suppress, redirect_stdout — contextlib already has the adapters you were about to write.
  • Also a decorator — a ContextDecorator can be applied to a whole function with @timed("x").
L3 · Advanced

Reentrancy, async, and suppression

  • Generator-based managers are single-use — re-entering one raises. If you need reuse, write the class, or use contextlib.nullcontext for the optional case.
  • async with — __aenter__ and __aexit__, built with @asynccontextmanager. A connection pool acquire that awaits needs this; a sync manager holding an await is how you block the loop.
  • AsyncExitStack — the same dynamic unwinding for coroutine resources.
  • Returning True suppresses — legitimate for suppress, wrong almost everywhere else: it silently converts a failure into a success.
  • Cleanup can raise — an exception in __exit__ replaces the one in flight, with the original as its context. Keep teardown boring.
  • Refcounting is not a resource policy — deterministic close is a CPython accident that PyPy does not share, and one stray reference removes it on CPython too.
Part five

Concurrency, and where Python is different

Every other page in this series treats threads as the default unit of parallelism. Python does not, because one lock inside the interpreter decides who executes bytecode. Understand that lock and the rest — threads, processes, asyncio — stops being folklore and becomes a straightforward choice.

Python · 00

The GIL: what actually runs in parallel

One lock per interpreter, held by whichever thread is executing bytecode. Threads still interleave, and they still overlap perfectly while waiting on I/O — but four CPU-bound threads on four cores finish no sooner than one.

L1 · Beginner

One lock, one runner

  • What it is — a mutex inside CPython that a thread must hold to execute bytecode.
  • Threads do not speed up CPU work — four threads summing numbers take as long as one, plus switching overhead.
  • Threads do help I/O — waiting on a socket or a disk releases the lock, so twenty requests can be in flight at once.
  • They are still real OS threads — pre-emptive, so shared state still needs a lock of your own.
  • Measure before choosing — if the profile is dominated by waiting, you have an I/O problem and the GIL is irrelevant.
L2 · Intermediate

Pick the executor by the profile

  • ThreadPoolExecutor — the answer for I/O: HTTP fan-out, S3 uploads, a few dozen database calls.
  • ProcessPoolExecutor — the answer for CPU: image work, parsing, compression, anything numeric without NumPy.
  • Pickling is the process tax — arguments and results are serialised. Sending a 200MB dataframe to each worker can cost more than the work.
  • concurrent.futures — one API for both, so switching is a one-word change. as_completed for results in finishing order.
  • Chunk the work — per-item tasks in a process pool are dominated by round-trip overhead; hand each worker a batch.
  • Never an unbounded pool — the same rule as everywhere else in this series: fix the worker count, and let the queue absorb the burst.
L3 · Advanced

Escaping the lock

  • C extensions release it — NumPy, Pillow, zlib, hashlib, and most database drivers drop the GIL around their heavy call, so threads over those really are parallel.
  • Free-threaded CPython (PEP 703) — builds with no GIL: experimental in 3.13, officially supported since 3.14 (PEP 779). Real thread parallelism, a single-thread cost that has shrunk to a few percent, and an ecosystem of C extensions still being rebuilt and re-audited for thread safety. Watch it seriously; default production stays on the GIL build for now.
  • Subinterpreters (PEP 734) — a per-interpreter GIL in one process: isolation like processes, without the fork cost. In the stdlib as concurrent.interpreters since 3.14; still young in library support.
  • Shared memory — multiprocessing.shared_memory or memory-mapped arrays move large buffers between processes without pickling them.
  • The honest summary — the GIL serialises bytecode, not I/O. Say which of those your workload is made of before you argue about it.
Python · 00

asyncio: one thread, many waits

The event loop runs one task until it awaits something, then runs another. Thousands of sockets on one thread, with no locks — and one synchronous call in the wrong place freezes every task at once.

import asyncio, httpx

async def fetch_all(urls: list[str]) -> list[bytes]:
    sem = asyncio.Semaphore(20)                  # bound the fan-out

    async with httpx.AsyncClient() as client:
        async def one(u: str) -> bytes:
            async with sem:                      # at most 20 in flight
                r = await client.get(u)
                return r.content

        async with asyncio.timeout(30):          # the whole batch, not each call
            return await asyncio.gather(*(one(u) for u in urls))

asyncio.run(fetch_all(urls))
L1 · Beginner

A coroutine is a plan, not a thread

  • async def returns a coroutine — calling it runs nothing. Forgetting the await is a warning and a function that never happened.
  • await yields control — it says “I am waiting; run someone else”, and resumes when the result is ready.
  • asyncio.run(main()) — one entry point per program: it creates the loop, runs the coroutine, and shuts the loop down.
  • Concurrency, not parallelism — one thread the whole time. It wins by never waiting idly, not by using more cores.
  • Async is contagious — only a coroutine can await, so an async call at the bottom pulls async all the way up the stack.
L2 · Intermediate

Run many, bound them, cancel them

  • gather vs TaskGroup — gather collects results; TaskGroup (3.11+) also guarantees that when one task fails the rest are cancelled and awaited. Prefer it for new code.
  • asyncio.timeout(s) — a context manager that cancels whatever is inside. Cleaner than threading a deadline through every call.
  • Cancellation is an exception — CancelledError is raised at the await point, so cleanup belongs in finally, and you must not swallow it.
  • Never block the loop — no time.sleep, no requests, no big json.loads, no synchronous database driver.
  • asyncio.to_thread(fn, *args) — the one-line adapter for a sync library you cannot replace.
  • Semaphore(n) — launching 10,000 coroutines at a service that handles 50 is not concurrency, it is a denial-of-service test. Bound the fan-out, every time.
L3 · Advanced

The sharp edges

  • Coloured functions — sync and async are two ecosystems: requests and httpx, psycopg sync and async. Choosing async is choosing a dependency stack.
  • Keep a reference to your tasks — the loop holds only a weak one, so a bare asyncio.create_task(...) can be garbage collected mid-flight. Store it in a set and discard on completion, or use a TaskGroup.
  • loop.run_in_executor — what to_thread wraps; use it directly to target a process pool for CPU-bound work.
  • Structured concurrency — a TaskGroup block cannot exit with children still running. The same discipline as an errgroup in Go, enforced by the language.
  • Back-pressure — a bounded asyncio.Queue makes the producer wait when consumers fall behind. An unbounded one turns a slow consumer into a memory leak.
  • Debugging — asyncio.run(main(), debug=True) logs coroutines that hold the loop too long. It finds the blocking call in minutes.

Threads, processes, or async: choosing

The decision has one input that matters — what the work is waiting on — and one honest caveat: most services never reach the scale at which the exciting answer beats a pool of ordinary synchronous workers.

Two limits that decide this before you do

Your database connection pool and your downstream rate limits cap real concurrency long before the interpreter does. Twenty thousand coroutines contending for thirty connections is thirty connections' worth of throughput plus a queue you cannot see. Size the pool first, bound the fan-out to match, and only then argue about threads against async — the same lesson as the queue-depth section on the foundations page, in a different costume.
