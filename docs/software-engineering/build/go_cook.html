Five things you will actually be asked to write

A service main(), start to finish

The job: wire up a service so it fails loudly at start-up and quietly on the way down. The shape is always the same — main does nothing but call run and exit, because a function that returns an error is testable and a function that calls os.Exit is not.

func main() {
	if err := run(context.Background()); err != nil {
		slog.Error("fatal", "err", err)
		os.Exit(1)                      // the only Exit in the programme
	}
}

func run(ctx context.Context) error {
	cfg, err := config.Load()               // fails now, not at 3am
	if err != nil {
		return fmt.Errorf("config: %w", err)
	}
	ctx, stop := signal.NotifyContext(ctx, syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	db, err := sql.Open("pgx", cfg.DatabaseURL)
	if err != nil {
		return fmt.Errorf("open db: %w", err)
	}
	defer db.Close()
	db.SetMaxOpenConns(cfg.DBMaxConns)      // default is unlimited
	db.SetConnMaxLifetime(30 * time.Minute) // survives a failover
	if err := db.PingContext(ctx); err != nil {
		return fmt.Errorf("ping db: %w", err)
	}
	srv := &http.Server{
		Addr:              cfg.Addr,
		Handler:           routes(db),
		ReadHeaderTimeout: 5 * time.Second,   // the anti-Slowloris one
		ReadTimeout:       15 * time.Second,
		WriteTimeout:      30 * time.Second,
		IdleTimeout:       60 * time.Second,
	}

	errc := make(chan error, 1)               // buffered: the goroutine never blocks
	go func() { errc <- srv.ListenAndServe() }()

	select {
	case err := <-errc:
		return fmt.Errorf("serve: %w", err)   // could not bind, or a real failure
	case <-ctx.Done():
		slog.Info("signal received, draining")
	}

	grace, cancel := context.WithTimeout(context.Background(), 25*time.Second)
	defer cancel()                            // NOT ctx — that one is cancelled
	return srv.Shutdown(grace)
}
L1 · Beginner

What the code does

  • run returns error; main prints it and exits. Everything else is ordinary code.
  • signal.NotifyContext gives you a context that is cancelled when SIGTERM arrives — no channel plumbing needed.
  • defer db.Close() immediately after a successful open, so there is no path that forgets it.
  • %w wraps: the caller can still match the underlying error with errors.Is.
  • ListenAndServe blocks, so it goes in a goroutine and reports back on a channel.
L2 · Intermediate

Why it is written this way

  • log.Fatal skips every defer. It is os.Exit with a print — connections stay open, buffers stay unflushed, and the function cannot be tested.
  • The shutdown context is a fresh one. Deriving it from the cancelled ctx makes Shutdown return instantly and kills in-flight requests, which is the exact bug this code is avoiding.
  • errc is buffered with capacity one so the serving goroutine can send and exit even after select has already taken the shutdown branch. Unbuffered, it leaks.
  • ReadHeaderTimeout is the one that matters for an exposed service; without it a client can hold a connection open with a slow trickle of header bytes.
  • SetMaxOpenConns defaults to unlimited, which means one traffic spike can exhaust the database’s own connection limit.
L3 · Advanced

What bites in production

  • Shutdown does not touch hijacked or long-lived connections — WebSockets and SSE streams need their own cancellation, usually a context stored per connection.
  • Readiness must flip before the drain starts. Fail the readiness probe, wait one probe interval so the load balancer stops sending traffic, and only then call Shutdown.
  • defer stop() restores default signal handling; a second SIGTERM after that kills the process immediately, which is usually what an impatient operator wants.
  • Background workers need the same treatment. Give them the same ctx and wait for them with an errgroup, or the process exits with work half-done.
  • sql.Open does not connect. Without the explicit PingContext, a bad password becomes a run-time error on the first request rather than a start-up failure.

Bounded fan-out with errgroup

The job: call a service once per item for a few hundred items. Unbounded goroutines are cheap for you and expensive for whoever you are calling — and errgroup gives you the bound, the error and the cancellation in one type.

func enrichAll(ctx context.Context, ids []string) (map[string]Result, error) {
	g, ctx := errgroup.WithContext(ctx)   // shadowing ctx is idiomatic here
	g.SetLimit(20)                        // at most 20 in flight, ever

	var mu sync.Mutex
	out := make(map[string]Result, len(ids))

	for _, id := range ids {              // Go 1.22+: id is per-iteration
		g.Go(func() error {
			r, err := enrich(ctx, id)     // the cancellable ctx, not the outer one
			if err != nil {
				return fmt.Errorf("enrich %s: %w", id, err)
			}
			mu.Lock()
			defer mu.Unlock()
			out[id] = r
			return nil
		})
	}
	return out, g.Wait()                  // blocks until every goroutine is done
}
// when a partial answer is the right answer, collect instead of cancelling:
	var (
		mu   sync.Mutex
		errs []error
	)
	g := new(errgroup.Group)              // no WithContext — no sibling cancellation
	g.SetLimit(20)
	for _, id := range ids {
		g.Go(func() error {
			r, err := enrich(ctx, id)
			mu.Lock()
			defer mu.Unlock()
			if err != nil {
				errs = append(errs, fmt.Errorf("%s: %w", id, err))
				return nil                // nil: do not stop the others
			}
			out[id] = r
			return nil
		})
	}
	_ = g.Wait()
	return out, errors.Join(errs...)      // one error holding all of them
L1 · Beginner

What the code does

  • errgroup.WithContext returns a group and a derived context that the group cancels as soon as any goroutine returns a non-nil error.
  • g.Go(fn) starts a goroutine; g.Wait() blocks until they have all finished and returns the first error.
  • SetLimit(n) makes g.Go itself block once n are running — the backpressure is at the submission point.
  • A mutex around the map because concurrent map writes are a run-time crash in Go, not a race you get away with.
  • errors.Join combines several errors into one that errors.Is can still search.
L2 · Intermediate

Why it is written this way

  • Pass the group’s ctx to the work, not the original. Using the outer context means the cancellation you carefully set up reaches nobody.
  • Two shapes, chosen deliberately: WithContext for “all of it or none”, a bare Group plus errors.Join for “do as much as you can and tell me what failed”.
  • Pre-size the map with make(..., len(ids)) so it does not rehash while twenty goroutines contend for the lock.
  • Wrap with the id. enrich 8fa3: context deadline exceeded is actionable; context deadline exceeded alone is not.
  • The loop-variable capture bug is gone in Go 1.22+ — but on an older module version this exact code silently enriches the last id n times.
L3 · Advanced

What bites in production

  • SetLimit after Go panics, and a limit of zero deadlocks immediately. Set it once, before the loop.
  • Cancellation does not unblock everything. A CPU-bound loop, a call without a context, or a sync.Mutex wait ignores it entirely — Wait then hangs for as long as that call does.
  • The first error wins, the rest are dropped. If several failures are diagnostically different, collect them; the default hides everything after the first.
  • A panic in a g.Go goroutine takes down the process — errgroup does not recover for you. Recover at the top of the closure if the work is untrusted.
  • Bound by the downstream’s capacity divided by your replica count. A limit of 20 on 30 pods is 600 concurrent calls arriving at one service.

An outbound call that cannot hang

The job: call an internal API safely. Go gives you five separate deadlines and two easy ways to leak a connection — and the default http.Client, which has no timeout at all, is the one thing you must never use.

// one client for the process; it is safe for concurrent use by design
var client = &http.Client{
	Timeout: 5 * time.Second,                 // dial + TLS + headers + body
	Transport: &http.Transport{
		DialContext:           (&net.Dialer{Timeout: time.Second}).DialContext,
		TLSHandshakeTimeout:   time.Second,
		ResponseHeaderTimeout: 2 * time.Second,
		MaxIdleConnsPerHost:   32,            // default is 2 — the silent bottleneck
		IdleConnTimeout:       90 * time.Second,
	},
}

var (
	ErrRetryable = errors.New("upstream unavailable")
	ErrRejected  = errors.New("upstream rejected the request")
)
func postEntry(ctx context.Context, e Entry, idem string) (Ref, error) {
	body, err := json.Marshal(e)
	if err != nil {
		return Ref{}, fmt.Errorf("marshal entry: %w", err)
	}
	req, err := http.NewRequestWithContext(ctx, http.MethodPost,
		baseURL+"/entries", bytes.NewReader(body))
	if err != nil {
		return Ref{}, fmt.Errorf("build request: %w", err)
	}
	req.Header.Set("Content-Type", "application/json")
	req.Header.Set("Idempotency-Key", idem)   // same key on every retry

	resp, err := client.Do(req)
	if err != nil {
		return Ref{}, fmt.Errorf("post entry: %w", err)  // wraps ctx deadlines
	}
	defer func() {
		_, _ = io.Copy(io.Discard, resp.Body) // drain, then close, in that order
		_ = resp.Body.Close()
	}()

	switch {
	case resp.StatusCode >= 500:
		return Ref{}, fmt.Errorf("ledger %d: %w", resp.StatusCode, ErrRetryable)
	case resp.StatusCode >= 400:
		return Ref{}, fmt.Errorf("ledger %d: %w", resp.StatusCode, ErrRejected)
	}

	var ref Ref
	if err := json.NewDecoder(resp.Body).Decode(&ref); err != nil {
		return Ref{}, fmt.Errorf("decode ref: %w", err)
	}
	return ref, nil
}
L1 · Beginner

What the code does

  • One package-level client, reused. It holds the connection pool; a new one per call throws that pool away.
  • NewRequestWithContext, never http.Post — the context is how a cancelled request actually stops.
  • defer drain-then-close on the body, immediately after checking err.
  • Sentinel errors wrapped with %w so the caller writes errors.Is(err, ErrRetryable) instead of re-parsing a status code.
  • A non-2xx is not an err from Do. You have to check StatusCode yourself.
L2 · Intermediate

Why it is written this way

  • Timeouts are layered on purpose. client.Timeout is the backstop; the transport’s three let you fail fast on a dead host while still allowing a slow response.
  • The context deadline beats them all, because it also propagates: the callee learns how long the caller is still willing to wait.
  • MaxIdleConnsPerHost defaults to 2. On a service that talks mostly to one host, that is the single most common cause of unexplained latency.
  • Retryable versus rejected is decided here, at the boundary, not by every caller inspecting numbers.
  • Wrapping preserves context.DeadlineExceeded, so a timeout is still matchable several layers up.
L3 · Advanced

What bites in production

  • A leaked body leaks a goroutine and a socket. It shows up as a slow climb in goroutine count — pprof will point straight at net/http.
  • Draining a huge body is worse than dropping it. Cap it: io.CopyN(io.Discard, resp.Body, 64<<10), then close.
  • Retrying is only safe with a body you can rewind. A bytes.Reader can be re-read; an io.Pipe or a file stream cannot, so build the request inside the retry loop.
  • client.Timeout cannot be overridden per request — that is exactly what the request context is for.
  • Sharing a Transport across clients is good; creating a Transport per request is a connection-pool leak with a slow, confusing failure mode.

A repository over database/sql

The job: write two rows in one transaction and read one back. The interesting parts are the exits — a deferred rollback that is a no-op after a successful commit, and sql.ErrNoRows, which is the standard library asking you to decide what “missing” means in your domain.

func (r *Repo) Place(ctx context.Context, o Order) (uuid.UUID, error) {
	tx, err := r.db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
	if err != nil {
		return uuid.Nil, fmt.Errorf("begin: %w", err)
	}
	defer tx.Rollback() //nolint:errcheck // no-op once Commit has run

	var id uuid.UUID
	err = tx.QueryRowContext(ctx,
		`INSERT INTO orders (email, total) VALUES ($1, $2) RETURNING id`,
		o.Email, o.Total,
	).Scan(&id)
	if err != nil {
		return uuid.Nil, fmt.Errorf("insert order: %w", err)
	}

	for _, it := range o.Items {
		if _, err := tx.ExecContext(ctx,
			`INSERT INTO items (order_id, sku, qty) VALUES ($1, $2, $3)`,
			id, it.SKU, it.Qty,
		); err != nil {
			return uuid.Nil, fmt.Errorf("insert item %s: %w", it.SKU, err)
		}
	}
	return id, tx.Commit()
}
func (r *Repo) Get(ctx context.Context, id uuid.UUID) (Order, error) {
	var o Order
	err := r.db.QueryRowContext(ctx,
		`SELECT id, email, total FROM orders WHERE id = $1`, id,
	).Scan(&o.ID, &o.Email, &o.Total)

	switch {
	case errors.Is(err, sql.ErrNoRows):
		return Order{}, ErrNotFound       // a domain error, not a driver one
	case err != nil:
		return Order{}, fmt.Errorf("get order %s: %w", id, err)
	}
	return o, nil
}

// rows.Err() is not optional — a Rows loop that ends early because the
// connection dropped looks exactly like one that ran out of rows:
	for rows.Next() { /* … */ }
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("iterate items: %w", err)
	}
L1 · Beginner

What the code does

  • Every call takes a ctx — QueryContext, ExecContext, BeginTx. The non-context versions exist only for compatibility.
  • Placeholders, always. $1 on Postgres, ? on MySQL — never string concatenation, which is how injection happens.
  • QueryRow(...).Scan(&x) is the one-row shape; it defers the error until Scan.
  • RETURNING id gets the generated key back in the same round trip.
  • sql.ErrNoRows is a normal outcome of a lookup, not a failure of the database.
L2 · Intermediate

Why it is written this way

  • The deferred rollback is written on the line after BeginTx, so no future early return can escape it.
  • Translate ErrNoRows at the repository boundary. The layer above should not import database/sql to know a thing was missing.
  • rows.Err() after every rows.Next() loop — and defer rows.Close(), or the connection never returns to the pool.
  • Wrap with identifying detail: which order, which SKU. The stack trace is not in the error, so the context has to be.
  • Keep transactions short and free of network calls. Every millisecond inside BeginTx is a millisecond of held locks.
L3 · Advanced

What bites in production

  • A Tx pins one connection for its whole life. Long transactions plus a small pool is a deadlock waiting for traffic.
  • Retry on serialisation failure if you use LevelSerializable: Postgres returns 40001 and expects the application to try again, which means the whole function must be safe to re-run.
  • Prepared statements are per-connection. db.Prepare re-prepares on whichever connection it lands on; under a pool that is rarely the win people expect.
  • context cancellation mid-transaction leaves the driver to roll back asynchronously — the row locks can outlive your handler by a moment.
  • SetConnMaxLifetime matters behind a proxy or a failover. Without it, connections pinned to a demoted primary survive the failover and keep failing.

Table-driven tests, fakes and httptest

The job: test the three things above without a network. Go’s answer is unusually consistent — a map of cases, a subtest per case, an interface for the seam, and a real HTTP server when the thing under test is the HTTP client itself.

func TestPlace(t *testing.T) {
	t.Parallel()

	tests := map[string]struct {
		order   Order
		ledger  fakeLedger        // the seam: an interface, not a mock library
		wantErr error
	}{
		"happy path":     {order: valid, ledger: fakeLedger{ref: "led_1"}},
		"ledger down":    {order: valid, ledger: fakeLedger{err: ErrRetryable}, wantErr: ErrRetryable},
		"ledger rejects": {order: valid, ledger: fakeLedger{err: ErrRejected}, wantErr: ErrRejected},
		"empty basket":   {order: Order{}, wantErr: ErrInvalid},
	}

	for name, tc := range tests {
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			_, err := Place(t.Context(), tc.ledger, tc.order)   // 1.24+: t.Context()
			if !errors.Is(err, tc.wantErr) {
				t.Fatalf("Place() error = %v, want %v", err, tc.wantErr)
			}
		})
	}
}
// when the thing under test IS the HTTP client, use a real server
func TestPostEntry(t *testing.T) {
	srv := httptest.NewServer(http.HandlerFunc(
		func(w http.ResponseWriter, r *http.Request) {
			if got := r.Header.Get("Idempotency-Key"); got == "" {
				t.Errorf("missing idempotency key")   // Errorf: this is the server goroutine
			}
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusCreated)
			_, _ = io.WriteString(w, `{"ref":"led_123"}`)
		}))
	t.Cleanup(srv.Close)

	ref, err := postEntry(t.Context(), Entry{Amount: 100}, "idem-1")
	if err != nil {
		t.Fatalf("postEntry() = %v", err)
	}
	if ref.ID != "led_123" {
		t.Errorf("ref.ID = %q, want led_123", ref.ID)   // got, want — in that order
	}
}
L1 · Beginner

What the code does

  • A map from case name to inputs and expectations, then one t.Run per entry — the standard Go test shape.
  • t.Fatalf stops this subtest; t.Errorf records a failure and continues. Use Fatal when the rest of the test cannot run.
  • errors.Is, not ==, because the error you get back is wrapped.
  • httptest.NewServer starts a real HTTP server on a random port and hands you its URL.
  • No assertion library needed — if got != want { t.Errorf(...) } is the convention.
L2 · Intermediate

Why it is written this way

  • A map, not a slice, so cases are named, unordered, and impossible to reference by index.
  • t.Parallel() twice — once for the parent, once inside each subtest. Only then do the cases actually overlap.
  • The fake is a struct implementing your own interface. Go’s implicit interfaces make a five-line fake cheaper than any mocking framework.
  • t.Cleanup over defer in helpers: it runs at the end of the test even when registered several frames down.
  • Message order is got, want. Every Go codebase reads it that way, and reversing it costs a reader real time.
L3 · Advanced

What bites in production

  • t.Fatal from a non-test goroutine does nothing useful — it stops that goroutine, not the test. Inside an httptest handler, always t.Errorf.
  • Run the suite with -race in CI. The detector only reports races it actually observes, so parallel subtests make it meaningfully more likely to see one.
  • Interfaces belong to the consumer. Define the narrow one you need where you use it, not next to the implementation — that is what keeps fakes small.
  • testing/synctest (1.25) fakes time for concurrent code, so a test of a one-minute backoff no longer takes a minute.
  • Golden files plus -update for large outputs, and testcontainers or dockertest when only a real database will do — behind testing.Short() so the fast suite stays fast.
