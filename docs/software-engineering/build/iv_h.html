Part ten

Security

Not a specialist subject any more. Every backend loop now contains at least one question about identity, one about input, and one about secrets — and a design round that never mentions authorisation reads as incomplete. Three topics cover almost all of it: who the caller is, what untrusted input can do, and what cryptography actually promises.

Topic · xx

Authentication and authorisation

Two words that are constantly swapped. Authentication is who are you; authorisation is what may you do. Most real breaches are failures of the second while the first worked perfectly.

Sessions vs tokensA server-side session can be revoked instantly; a signed token cannot be, which is why it must be short-lived.
CookiesHttpOnly, Secure, SameSite, domain and path scope. The four attributes that decide how bad an XSS is.
JWTSigned, not encrypted — anyone can read the claims. Verify the signature, the issuer, the audience, the expiry, and pin the algorithm.
The alg: none trapAccepting the algorithm the token names lets the attacker choose it. Pin it server-side.
Refresh tokensLong-lived and therefore dangerous. Rotate them, detect reuse, and store them somewhere a script cannot read.
OAuth 2.0 and OIDCDelegated authorisation, then identity on top of it. Grant types, scopes, and consent.
SAML and enterprise SSOStill everywhere in business software. Assertions, identity providers, and just-in-time provisioning.
Password storageArgon2 or bcrypt with a per-user salt. Never a fast hash, never encryption, never your own scheme.
Multi-factorTOTP, push, WebAuthn and passkeys. Also account recovery, which is where MFA is usually defeated.
Service-to-servicemTLS, workload identity, short-lived credentials from a metadata service. Not a shared static key.
Authorisation modelsRole-based, attribute-based, relationship-based. Where the check happens, and whether it can be forgotten.
Least privilegePer environment, per service, per table. And the audit that proves it, which is the part that is skipped.
Multi-tenant isolationEvery query filtered by tenant. Enforced in one place, not in three hundred call sites.
Impersonation and support accessHow staff act as a user, and how that is logged. Asked in product-company loops.
Topic · xx

The application attack surface

Every hop between a user and your data has its own family of attacks. You are not expected to be a penetration tester — you are expected to know what class of bug lives where, and the standard defence for each.

# The two lines that answer half of an application-security question.

# 1. Never build a query by concatenation. The parameter is data, forever,
#    no matter what it contains.
cur.execute("SELECT id, email FROM users WHERE tenant_id = %s AND email = %s",
            (tenant_id, email))          # not f"... email = '{email}'"

# 2. Authorise the object, not the route. A logged-in user is not the same
#    thing as this user, and the row is where the truth is.
invoice = repo.get(invoice_id)
if invoice is None or invoice.tenant_id != caller.tenant_id:
    raise NotFound()                     # not Forbidden: do not confirm it exists

Topic · xx

Cryptography, at the level you are expected to use it

Nobody expects you to implement a cipher. They expect you to know which primitive solves which problem, and to never reach for one you have written yourself.

HashingOne way, fixed size. For integrity and lookup — SHA-256. Not for passwords.
Password hashingDeliberately slow and memory-hard: Argon2id, scrypt, bcrypt. With a per-user salt, which the library handles.
MAC and HMACIntegrity plus authenticity with a shared key. The right tool for webhook signatures.
Symmetric encryptionAES-GCM or ChaCha20-Poly1305. Authenticated, so tampering is detected. Never reuse a nonce.
Asymmetric encryptionRSA and elliptic curve. Slow, so used to exchange a symmetric key rather than to encrypt data.
SignaturesProve origin and integrity without a shared secret. What a JWT and a code-signing certificate both rely on.
TLS and PKICertificates, chains, roots, revocation, pinning, and what a certificate actually proves.
Key managementWhere keys live, how they rotate, envelope encryption, and a hardware module for the root.
RandomnessCryptographically secure generators only. A token from Math.random is a predictable token.
Encryption at rest and in transitTwo different threats. Disk encryption does nothing against a compromised application.
Tokenisation and maskingKeeping regulated data out of your systems entirely, which is cheaper than protecting it.
Privacy obligationsData minimisation, retention limits, the right to deletion, and where the data may physically live.
  • How would you store passwords?a slow hash by name, a per-user salt, and the reason a fast hash fails. Mentioning a pepper or a work factor is a bonus, not the point.
  • A user reports seeing another user’s data. What happened?a missing object-level authorisation check, a cache keyed without the tenant, or a connection pool leaking context. All three are worth naming.
  • How do you handle secrets in this design?a secret manager, short-lived credentials, rotation, and nothing in the repository or the image.
  • What does TLS actually protect against here?the distinction between transport security and everything else. It does not authenticate the user or protect the data once it arrives.
Part eleven

The other loops

Everything up to here is the shared core. A specialist loop keeps most of it and swaps one or two rounds for something domain-specific. This part says what each track adds, so that a backend engineer interviewing for a platform role knows what the fourth round is going to be.

Topic · xx

Which rounds each track actually runs

The mix changes more than the subject. A frontend loop keeps the coding round but is likely to make it a component; an infrastructure loop replaces low-level design with a practical exercise on a broken machine.

Topic · xx

What each track adds on top

The subjects below are additional to everything in parts two to ten — not a replacement for them. A frontend loop still asks about hash maps.

FrontendThe browser rendering path, reflow and repaint, the critical path, bundle size, code splitting, hydration. State management, reactivity, virtual DOM diffing. Accessibility: semantics, focus order, ARIA, keyboard-only use. Core Web Vitals. CSS layout and specificity. Forms, validation and optimistic updates. Cross-browser and internationalisation.
MobileThe activity or view-controller lifecycle, and the state you lose on rotation or backgrounding. Memory pressure and being killed. Offline-first storage and sync. Background execution limits. Push notifications. Battery and network cost. App size, store review, staged rollout and the fact that you cannot force an update.
Data engineeringBatch against streaming, and event time against processing time. Watermarks and late data. Idempotent, replayable pipelines. Partitioning, file formats, compaction and small-file problems. Schema evolution. Orchestration and backfills. Data quality tests, lineage, and the cost of a full reprocess.
Machine learningTraining and serving skew, feature stores, offline and online evaluation, drift. Model deployment, shadow traffic and rollback. Latency and cost per inference, batching, quantisation. For language-model work: context, retrieval, tool use, evaluation harnesses, prompt injection and guardrails.
Infrastructure and SREA terminal and a broken host. Linux internals, networking, DNS and TLS debugging under time pressure. Capacity planning and load testing. Terraform and configuration drift. Kubernetes internals, not just its YAML. On-call practice, error budgets, and the failure injection you have actually run.
Security engineeringThreat modelling a design out loud. Reading code for vulnerabilities. Attack chains rather than isolated bugs. Detection and response, log sources, and what an attacker does after the first foothold. Compliance frameworks as a constraint on architecture.
Test and qualityTest strategy across a system rather than a file. Automation frameworks, page objects, flakiness at scale, test data management, and a considered position on what should never be automated.
Embedded and systemsMemory constraints, interrupts and real-time deadlines, fixed-point arithmetic, hardware interfaces, cross-compilation, and firmware update that cannot brick the device.
Platform and developer toolingBuild systems and caching, monorepo tooling, developer experience as a product, migration of hundreds of teams, and API design where the users are engineers who will not read the documentation.
