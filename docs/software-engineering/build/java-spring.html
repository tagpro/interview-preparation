Part one

The machine you are installing

L1 · Beginner

Java is two artefacts: a compiler that turns source into bytecode once, and a virtual machine that turns bytecode into machine code every time you run. Everything people say about the platform — portable, verbose, slow to start, fast once warm — is a property of that split. Install the toolchain, run one file three different ways, and read the bytecode with your own eyes before part two adds the language on top.

Java · 02

A Java file, dissected down to the bytecode

Every declaration in a Java file is load-bearing: the package is a directory, the public class is the file name, and public static void main(String[] args) is a signature the JVM looks up literally. Then javap shows you what the compiler actually wrote.

Here is the same program grown up: a package, an import, a constant. Read it top to bottom, because each line is a contract with either the compiler or the JVM:

// src/dev/ladder/hello/Greeter.java -- path and package MUST agree
package dev.ladder.hello;

import java.time.LocalTime;      // a compile-time name shorthand -- unlike Python's
                                 // import, it executes nothing at runtime
public class Greeter {

    private static final String FALLBACK = "world";   // a class-level constant

    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : FALLBACK;
        System.out.println("Hello, " + name + " at " + LocalTime.now());
    }
}

Dissect the one line that does something. System is a class in java.lang (the only package imported automatically); out is a static final field on it, of type PrintStream; println is an overloaded method on that stream. So System.out.println is not an incantation — it is field access followed by a method call, and by the end of part two you can read it that way.

Now compile explicitly and look at the result. javac -d out mirrors the package into a directory tree; java -cp out tells the launcher where that tree starts; javap -c disassembles what the compiler wrote.

Run it

Part two

Objects, values, and the type system

L1 · Beginner

Java draws a line Python never drew: a handful of primitive types live directly in the variable, and everything else is a reference into the heap. Hold that line in your head and the classic surprises — == lying about equality, a key vanishing from a HashMap, a boxed 127 behaving differently from a boxed 128 — become predictable consequences instead of folklore.

Java · 03

Primitives, references, and the two meanings of ==

A primitive variable holds the value itself; a reference variable holds a pointer into the heap. == compares whatever is in the slot — which is the value for primitives and the address for objects. That one sentence is the most common beginner bug in the language.

Eight primitive types exist; four carry almost all production code. They are not objects: no methods, no null, no heap allocation — the value sits in the variable, the way a C or Go value would.

TypeSizeLiteralNotes
int32-bit42The default for whole numbers; overflows silently at 231−1
long64-bit10_000_000_000LIDs, timestamps, money-in-cents; note the L
double64-bit0.1IEEE-754 — fine for science, never for money
boolean—trueOnly true/false; no truthy values, unlike Python

byte, short, float and char complete the set; you will meet them in I/O buffers and old APIs. Everything that is not one of the eight — String, arrays, every class you write — is a reference type: the variable holds a pointer, null means the pointer points at nothing, and copying the variable copies the arrow, never the object.

Collections cannot hold primitives, so Integer, Long and friends exist as boxed wrappers and the compiler autoboxes in both directions. The trap: the JVM caches boxes for −128..127, so == on small boxed values compares two pointers to the same cached box and returns true — then your test data grows past 127 and it silently returns false. Strings have the same shape: literals are pooled and shared, so == works right up until a string arrives from a file, a request, or new String(...). Prove all of it to yourself:

public class Surprises {
    public static void main(String[] args) {
        Integer a = 127, b = 127;             // both autoboxed from the cache
        Integer c = 128, d = 128;             // two fresh boxes on the heap
        System.out.println(a == b);           // true  -- same cached object
        System.out.println(c == d);           // false -- different objects, equal values
        System.out.println(c.equals(d));      // true  -- what you nearly always meant

        String s1 = "task";
        String s2 = "task";                   // same pooled literal as s1
        String s3 = new String("task");       // new forces a fresh object
        System.out.println(s1 == s2);         // true  -- pooling, an accident you cannot rely on
        System.out.println(s1 == s3);         // false -- different objects
        System.out.println(s1.equals(s3));    // true

        String t = s1.toUpperCase();          // Strings are immutable: this is a NEW string
        System.out.println(s1 + " " + t);     // task TASK -- s1 untouched

        int[] xs = {1, 2, 3};                 // arrays are fixed-size, forever
        System.out.println(xs.length);        // 3 -- a field, not a method
    }
}

Run it

One file, six lies and truths. If any line surprises you, re-read the figure: every result is “== compared what was in the slot”.

The rule that survives this topic

Compare primitives with ==. Compare objects — every String, every Integer, everything you write — with .equals(), or with Objects.equals(a, b) when either side may be null. An == between two reference types is a code-review flag unless identity is genuinely the question.

Java · 04

Classes the long way, then records

Write one value class by hand — fields, constructor, accessors, equals, hashCode, toString — so you know exactly what a record generates when it replaces all thirty lines with one.

A Money type, the classical way. Note the shape: every field private final (set once, in the constructor, never again), accessors instead of public fields, and the three methods every value type owes the rest of the ecosystem:

import java.util.Objects;

public final class Money {                       // final class: cannot be subclassed
    private final long cents;                    // final field: assigned once, in the constructor
    private final String currency;

    public Money(long cents, String currency) {
        if (cents < 0) throw new IllegalArgumentException("negative amount");
        this.cents = cents;
        this.currency = Objects.requireNonNull(currency);
    }

    public long cents()       { return cents; }
    public String currency()  { return currency; }

    public Money plus(Money other) {             // no mutation: arithmetic returns a NEW Money
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(cents + other.cents, currency);
    }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;
        return cents == m.cents && currency.equals(m.currency);
    }

    @Override public int hashCode() { return Objects.hash(cents, currency); }

    @Override public String toString() { return cents + " " + currency; }
}

Thirty lines, and every one of them mechanical. Since Java 16 the language writes them for you:

public record Money(long cents, String currency) {}   // the same class, generated

A record declares its state in the header, and the compiler generates the final fields, the canonical constructor, accessors named after the components (cents(), not getCents()), and value-based equals, hashCode and toString. You add back only what is genuinely yours — validation goes in a compact constructor, domain logic is an ordinary method:

record Money(long cents, String currency) {
    Money {                                      // compact constructor: validate, then fields assign
        if (cents < 0) throw new IllegalArgumentException("negative amount");
    }
    Money plus(Money other) {
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(cents + other.cents, currency);
    }
}

public class MoneyDemo {
    static final Money FREE = new Money(0, "GBP");    // static: one per class, shared

    public static void main(String[] args) {
        Money a = new Money(12_50, "GBP");            // instance state: one per object
        Money b = new Money(4_99, "GBP");
        System.out.println(a.plus(b));
        System.out.println(a.equals(new Money(12_50, "GBP")));
        System.out.println(new Money(-1, "GBP"));     // validation fires
    }
}

Run it

Both classes sit in one file (only MoneyDemo is public), so the single-file launcher compiles them together. Value equality works with no equals written, and the compact constructor rejects the bad amount.

$ java MoneyDemo.java
Money[cents=1749, currency=GBP]
true
Exception in thread "main" java.lang.IllegalArgumentException: negative amount

static versus instance is the other axis worth fixing now: a static member belongs to the class (one FREE, shared; Math.max, Instant.now()), an instance member to each object (each Money has its own cents). main is static because when the JVM calls it, no object of your class exists yet. And final means “assigned once” for a field or variable, “no subclassing” for a class — it does not make the referenced object immutable.

Real money is BigDecimal or cents, never double

0.1 + 0.2 == 0.30000000000000004 in Java exactly as on the Python page. Hold money as long cents (as Money does) or use new BigDecimal("19.99") — constructed from a String, because new BigDecimal(0.1) faithfully preserves the binary error you were escaping.

Java · 05

Collections, generics, and the equals/hashCode contract

Arrays are fixed; real code uses List, Map and Set, parameterised with the type they hold. The compiler enforces the element type; the collection enforces a contract on you — and HashMap quietly loses data when you break it.

Three interfaces carry the standard library: List<T> (ordered, indexed, duplicates allowed — usually ArrayList), Map<K, V> (key to value — usually HashMap), and Set<T> (no duplicates — usually HashSet). The angle brackets are generics: List<Task> is a list that only accepts and only returns Task, checked at compile time, where Python’s list[Task] is a hint mypy checks and the runtime ignores. The diamond <> on the right-hand side asks the compiler to repeat the type parameter so you do not have to.

import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

record Task(String title, int priority, boolean done) {}

public class TaskListDemo {
    public static void main(String[] args) {
        List<Task> tasks = new ArrayList<>();          // diamond: compiler fills in <Task>
        tasks.add(new Task("write the Flyway migration", 1, false));
        tasks.add(new Task("wire the /tasks endpoint", 2, false));
        tasks.add(new Task("install a JDK", 1, true));

        tasks.sort(Comparator.comparing(Task::priority)   // sort by priority,
                             .thenComparing(Task::title)); // ties broken by title

        for (Task t : tasks) {                             // for-each: no index bookkeeping
            System.out.println((t.done() ? "[x] " : "[ ] ") + t.title());
        }

        Map<Integer, Long> perPriority = new HashMap<>();
        for (Task t : tasks) {
            perPriority.merge(t.priority(), 1L, Long::sum); // count per key, no if-absent dance
        }
        System.out.println(perPriority);

        Set<String> owners = new HashSet<>(List.of("ana", "ben", "ana"));
        System.out.println(owners.size());                 // deduplicated by equals/hashCode
    }
}

Run it

Sorting mutates the list in place; the map counts tasks per priority; the set swallows the duplicate. All three behaviours lean on Task’s record-generated equals and hashCode.

$ java TaskListDemo.java
[x] install a JDK
[ ] write the Flyway migration
[ ] wire the /tasks endpoint
{1=2, 2=1}
2

List.of(...), Map.of(...) and Set.of(...) build compact immutable literals — ideal for constants and test data, with one trap: they reject mutation at runtime, not compile time. The type system cannot see the difference between an ArrayList and an immutable list behind the same List interface:

List<String> tags = List.of("api", "db");   // immutable literal
tags.add("ui");                             // compiles fine...
// Exception in thread "main" java.lang.UnsupportedOperationException

List<String> mutable = new ArrayList<>(List.of("api", "db"));   // the copy that grows

Watch it happen. This key overrides both methods correctly — the bug is purely that it mutates after insertion:

import java.util.HashMap;
import java.util.Map;

class MutableKey {
    int n;
    MutableKey(int n) { this.n = n; }
    @Override public boolean equals(Object o) {
        return o instanceof MutableKey k && k.n == n;
    }
    @Override public int hashCode() { return Integer.hashCode(n); }
}

public class LostEntry {
    public static void main(String[] args) {
        Map<MutableKey, String> m = new HashMap<>();
        MutableKey k = new MutableKey(11);
        m.put(k, "hello");
        k.n = 14;                                       // the key moves AFTER insertion
        System.out.println(m.get(k));                   // null -- looked in the wrong bucket
        System.out.println(m.get(new MutableKey(11)));  // null -- right bucket, equals now fails
        System.out.println(m.size());                   // 1  -- the entry is still in there
    }
}

Run it

Both lookups miss while size() insists the entry exists. Fix is not code — it is policy: keys are immutable, ideally records.

Part three

Contracts, hierarchy, and failure

L1 · Beginner

Interfaces are how Java code stays swappable, and sealed hierarchies are how modern Java makes the compiler check what Go delegates to a linter and Python to mypy. Then the part every service is judged on: what happens when things fail — which exceptions to catch, which to wrap, and which to let fly.

Java · 06

Interfaces, and sealed hierarchies the compiler checks

An interface is a contract with no state: methods a type promises to provide. Program to it and implementations become swappable. Seal it, and the compiler knows the full set of implementations — and starts proving your switch handles every one.

The classic half first. An interface declares what, a class declares how, and implements connects them. Two habits are non-negotiable from day one: declare variables as the interface type, and write @Override on every implementing method so the compiler catches the typo’d signature that would otherwise become a brand-new method:

import java.util.ArrayList;
import java.util.List;

record Task(String title, int priority, boolean done) {}

interface TaskStore {
    void add(Task task);
    List<Task> all();

    default boolean isEmpty() {                // a default method: behaviour ON the contract,
        return all().isEmpty();                // inherited by every implementation for free
    }
}

class InMemoryTaskStore implements TaskStore {
    private final List<Task> tasks = new ArrayList<>();   // composition: HAS a list,
                                                          // does not EXTEND ArrayList
    @Override public void add(Task task) { tasks.add(task); }
    @Override public List<Task> all()    { return List.copyOf(tasks); }
}

public class StoreDemo {
    public static void main(String[] args) {
        TaskStore store = new InMemoryTaskStore();   // the variable is the interface;
        store.add(new Task("learn interfaces", 1, false));   // swap in a JdbcTaskStore later
        System.out.println(store.isEmpty());         // and this line does not change
        List<String> xs = new ArrayList<>();         // the same habit, stdlib edition
        xs.add("program to the interface");
        System.out.println(xs);
    }
}

Run it

The main never mentions InMemoryTaskStore after the new. In part seven the same idea lets a Postgres-backed repository replace the in-memory store, and the calling code does not move.

$ java StoreDemo.java
false
[program to the interface]

InMemoryTaskStore has a list rather than being one — composition over inheritance. Java has single inheritance (extends, one superclass) and it is the most over-used feature in the language’s history: a deep extends chain welds subclasses to a parent’s implementation details, and any hierarchy more than two levels deep is a code-review flag. Interfaces impose no such coupling — a class can implement many — and default methods cover the “shared behaviour” excuse that used to justify base classes.

Now the modern half. By default an interface is open — anyone, anywhere, can implement it. A sealed interface names its complete set of implementations, and that closedness is what turns switch into a proof:

import java.util.List;

sealed interface Payment permits Card, Cash, Transfer {}
record Card(String last4, long cents)    implements Payment {}
record Cash(long cents)                  implements Payment {}
record Transfer(String iban, long cents) implements Payment {}

public class PaymentDemo {
    static String describe(Payment p) {
        return switch (p) {                       // switch as an EXPRESSION: it returns a value
            case Card c     -> "card *" + c.last4() + ", " + c.cents() + " cents";
            case Cash c     -> "cash, " + c.cents() + " cents";
            case Transfer t -> "transfer to " + t.iban();
        };                                        // no default: exhaustiveness is checked
    }

    public static void main(String[] args) {
        List<Payment> day = List.of(
            new Card("4242", 19_99), new Cash(5_00), new Transfer("DE89 3704", 120_00));
        for (Payment p : day) System.out.println(describe(p));
    }
}

Run it

Then do the experiment that matters: add record Voucher(long cents) implements Payment {} to the permits list and rerun — the compile error names the switch that is no longer complete.

cash, 500 cents

Java · 07

Exceptions: the hierarchy, the resources, and Optional

Java splits failure into three families and treats one of them — checked exceptions — as part of a method’s type. Knowing which family you are holding tells you the correct reaction: fix, handle, wrap, or stand clear.

The reactions, family by family. Error means the JVM itself is in trouble — there is no catch block that un-runs-out memory. RuntimeException means your code is wrong: a NullPointerException is fixed by the null check you forgot, not by a catch. Checked exceptions — everything else under Exception — mark environmental failure that a correct program still meets: the file missing, the socket closed. The compiler makes you acknowledge those, and the idiomatic acknowledgement at a boundary is: handle it if you genuinely can, otherwise wrap it in your own unchecked exception with the cause attached and let it fly.

Resource cleanup has one modern answer. Anything AutoCloseable goes in the parentheses of try, and the JVM closes it — on success, on exception, in reverse order for multiple resources. The old try/finally dance, with its own bug where close() throws and eats the real exception, is legacy code you will read but should not write:

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.Optional;

class TaskStoreException extends RuntimeException {      // unchecked: extends RuntimeException
    TaskStoreException(String message, Throwable cause) { super(message, cause); }
}

public class ExceptionsDemo {

    static List<String> loadLines(Path file) {
        try (var reader = Files.newBufferedReader(file)) {   // try-with-resources: closed always,
            return reader.lines().toList();                  // even when an exception flies
        } catch (IOException e) {                            // the checked boundary...
            throw new TaskStoreException("could not read " + file, e);   // ...wrapped WITH cause
        }
    }

    static Optional<String> firstMatching(List<String> lines, String needle) {
        return lines.stream()                                // Optional: "maybe absent", in the
                    .filter(l -> l.contains(needle))         // return type where callers see it
                    .findFirst();
    }

    public static void main(String[] args) {
        List<String> lines = List.of("install jdk", "learn records");
        System.out.println(firstMatching(lines, "rec").orElse("no match"));
        System.out.println(firstMatching(lines, "zzz").orElse("no match"));
        loadLines(Path.of("missing.csv"));                   // watch the Caused by chain
    }
}

Run it

Two clean Optional results, then the wrapped failure. The stack trace is the payoff: your exception on top, the original NoSuchFileException preserved underneath as Caused by — both stacks, nothing lost.

        at ExceptionsDemo.loadLines(ExceptionsDemo.java:16)
        at ExceptionsDemo.main(ExceptionsDemo.java:30)

        ...

Optional<T> deserves its own rules, because it is routinely misused. It exists to make “this might be absent” visible in a return type, so the caller is forced to decide — orElse, orElseThrow, map, ifPresent. That is the whole job. Never make it a field (serialisation and JPA both choke, and it solves nothing there), never a parameter (callers end up writing Optional.of(x) noise — overload instead), and never call bare .get() — that is the old NullPointerException wearing a fancier name.

Do

store.findByTitle("ship it").map(Task::title).orElse("—") — absence handled in one chain, at the call site, visibly.

Do not

opt.get() without isPresent(), Optional fields, Optional parameters, or catch (Exception e) {} — the empty catch block is the same bug as Python’s bare except: pass, and it will cost someone a weekend.

Part four

Lambdas, streams, and the functional layer

L2 · Intermediate

Java bolted a functional layer onto a language of classes, and it shows — in a good way. A lambda is not a new kind of value; it is a terse way to make an instance of an interface you already understand. Once that clicks, streams stop being magic syntax and become what they are: a pull-based pipeline over the collections you built in the earlier parts.

Java · 08

Functional interfaces and lambdas

There is no function type in Java. A lambda is an instance of an interface with exactly one abstract method, and the compiler picks which interface from the position you use it in. Everything else — composition, method references, capture rules — follows from that one fact.

Here is the whole family working over tasks; note the composition methods and, or, negate and andThen, which are just default methods on the interfaces.

// Lambdas.java — one file, runnable directly (single-file launch, Java 11+)
import java.time.Instant;
import java.util.List;
import java.util.UUID;
import java.util.function.*;

record Task(UUID id, String title, boolean done, Instant createdAt) {
    static Task of(String title, boolean done) {
        return new Task(UUID.randomUUID(), title, done, Instant.now());
    }
}

public class Lambdas {
    public static void main(String[] args) {
        var tasks = List.of(
            Task.of("write the docs", false),
            Task.of("ship v2", true),
            Task.of("fix the flaky test", false));

        Predicate<Task> open        = t -> !t.done();
        Function<Task, String> name = Task::title;         // method reference
        Supplier<Task> blank        = () -> Task.of("untitled", false);
        Consumer<String> print      = System.out::println;

        Predicate<Task> openAndUrgent =
            open.and(t -> t.title().contains("fix"));      // composition

        for (var t : tasks) {
            if (openAndUrgent.test(t)) print.accept(name.apply(t));
        }
        print.accept(blank.get().title());
    }
}

A method reference is a lambda the compiler writes for you, and there are exactly four shapes. Read the left column as “the thing before ::”:

Task::title           // instance method, receiver comes later:  t -> t.title()
System.out::println   // instance method on a captured object:   s -> System.out.println(s)
Task::of              // static method:                          (t, d) -> Task.of(t, d)
ArrayList::new        // constructor:                            () -> new ArrayList<>()

Capture is where Java and Python genuinely differ, not just in syntax. A Java lambda may read local variables from the enclosing method, but only if they are effectively final — assigned exactly once. The lambda gets a copy at creation time, so there is nothing to bind late and nothing to race on. The compile error below is the Python late-binding loop trap, refused at build time:

int seen = 0;
Consumer<Task> count = t -> seen++;
// error: local variables referenced from a lambda expression
// must be final or effectively final

var cell = new int[] { 0 };            // the classic dodge: a mutable box
Consumer<Task> c2 = t -> cell[0]++;    // compiles — and is a design smell;
                                       // prefer a collector or a plain loop

// Python, for contrast: fns = [lambda: i for i in range(3)] gives 2, 2, 2
// because the closure reads i when CALLED. Java cannot express that bug:
// each lambda would need its own effectively-final copy of i.

Finally, var. It is local type inference, not dynamic typing: the compiler writes the exact static type in for you, and it never changes. Use it when the type is already visible on the right-hand side; avoid it when the reader would have to open another file to know what you have.

var tasks = new ArrayList<Task>();   // fine: the type is right there
var byId  = new HashMap<UUID, Task>();

var result = service.process(id);    // avoid: what is result? go look it up
var xs = new ArrayList<>();          // trap: infers ArrayList<Object> — the
                                     // diamond has nothing to infer FROM
// var is locals-only: never fields, parameters or return types.

Where Go readers land

If you came via the Go page: a Java functional interface plays the role of a one-method Go interface, and a lambda is the literal that satisfies it. The difference is inference direction — Go infers the interface from the concrete type; Java infers the lambda’s type from the interface expected at that position (the target type). That is why a bare t -> t.done() on its own line does not compile: with no target, there is no type.

Streams: a lazy pipeline over your collections

stream() builds a description of work; nothing touches an element until a terminal operation starts pulling. If you internalised generators on the Python page, you already have the model — the terminal operation is the for-loop that drives the pipeline.

The collectors are where streams earn their keep for service code: grouping, counting and joining are the three you will write weekly once the task-tracker has an API. All three appear here, plus toMap and a primitive stream for the numeric tail:

// Pipeline.java — run with: java Pipeline.java
import java.time.Instant;
import java.util.*;
import java.util.stream.Collectors;

record Task(UUID id, String title, boolean done, Instant createdAt) {
    static Task of(String title, boolean done) {
        return new Task(UUID.randomUUID(), title, done, Instant.now());
    }
}

public class Pipeline {
    public static void main(String[] args) {
        var tasks = List.of(
            Task.of("write the docs", false),
            Task.of("ship v2", true),
            Task.of("fix the flaky test", false),
            Task.of("review PR 41", false),
            Task.of("rotate the API keys", true));

        Map<Boolean, Long> counts = tasks.stream()
            .collect(Collectors.groupingBy(Task::done, Collectors.counting()));

        String open = tasks.stream()
            .filter(t -> !t.done())
            .map(Task::title)
            .sorted()
            .collect(Collectors.joining(", ", "[", "]"));

        Map<UUID, String> titleById = tasks.stream()
            .collect(Collectors.toMap(Task::id, Task::title));
            // duplicate keys throw IllegalStateException — pass a merge fn if possible

        long titleChars = tasks.stream()
            .mapToLong(t -> t.title().length())   // LongStream: no boxing
            .sum();

        System.out.println(counts);
        System.out.println(open);
        System.out.println("title characters: " + titleChars);
    }
}

Run it

The grouping map counts two done and three open tasks; the join sorts the open titles and brackets them; the primitive stream sums character counts without creating five Long objects.

    .map(t -> { System.out.println("map    " + t.title()); return t.title(); });
// nothing printed yet — the pipeline is a plan, not a loop

var first = s.limit(1).toList();
// filter write the docs
// map    write the docs
// — and it stops. The other four tasks are never examined.

When a plain for-loop is clearer

Side effects (writing to a file per element), early exit with a value plus an index, and anything that throws a checked exception — a lambda cannot throw IOException through Function, so people smuggle it out in a RuntimeException wrapper, which is worse than the loop. Streams are for transformation; loops are for procedure. The Go page’s position — just write the loop — is the right default whenever the pipeline stops reading as a sentence.

parallelStream()

It splits the work across the common ForkJoinPool — one pool shared by the whole JVM — so in a web service it steals threads from every other request, and for the list sizes a request handles the coordination costs more than it saves. Reach for it only for CPU-bound work over large in-memory data, measured before and after.

JUnit 5 and AssertJ: tests that read as behaviour

Surefire finds every class ending in Test, and JUnit runs each @Test method on a fresh instance of the class. That one design decision is why JUnit tests cannot leak state through fields the way a careless pytest module can.

Test names are documentation that cannot go stale, so write them as behaviour: summary_of_nothing_says_no_tasks reads as a sentence in the failure report, where testSummary2 reads as homework. Inside each test, keep the three phases visible — arrange, act, assert — and let AssertJ’s assertThat(actual).isEqualTo(expected) carry the assertions: it reads left to right, it cannot get expected and actual backwards, and its failure messages show diffs instead of expected: true but was: false.

// src/test/java/dev/ladder/tasklib/TitlesTest.java
package dev.ladder.tasklib;

import java.util.Collections;
import java.util.List;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

import static org.assertj.core.api.Assertions.assertThat;

class TitlesTest {

    private List<String> titles;

    @BeforeEach
    void freshTitles() {                       // arrange, shared
        titles = List.of("write the docs", "ship v2");
    }

    @Test
    void summary_counts_and_joins() {
        String s = Titles.summary(titles);     // act
        assertThat(s).isEqualTo("2 tasks: write the docs, ship v2");  // assert
    }

    @Test
    void summary_of_nothing_says_no_tasks() {
        assertThat(Titles.summary(List.of())).isEqualTo("no tasks");
    }

    @ParameterizedTest                         // one method, many cases —
    @CsvSource({                               // each row is its own test
        "1, 1 tasks",
        "3, 3 tasks",
        "9, 9 tasks",
    })
    void summary_starts_with_the_count(int n, String prefix) {
        var many = Collections.nCopies(n, "x");
        assertThat(Titles.summary(many)).startsWith(prefix);
    }
}

The container: why Spring exists at all

Dependency injection is a compile-visible discipline, not magic: every class declares what it needs as constructor parameters, and exactly one piece of the system — the container — decides what gets constructed, in what order, once.

First the disease, then the cure. Without a container, every class constructs its own dependencies, which welds the object graph shut:

// Without a container: each class builds its own world
class TaskController {
    private final TaskService service = new TaskService(new InMemoryStore());
    // - a test cannot hand in a fake TaskService or a fake store
    // - every change to TaskService's constructor edits every class that news it
    // - two controllers construct two stores: two copies of the truth
}

Inversion of control flips the arrow: TaskController says “I need a TaskService” and stops caring where it comes from. The container scans your package for stereotyped classes, works out the dependency graph from constructor signatures, and instantiates each bean exactly once, in dependency order.

@Service                                  // stereotype: "scan me in" — @Component
public class TaskService {                // with a role name; @Repository is the third
    private final Clock clock;            // one final field per dependency

    public TaskService(Clock clock) {     // single constructor: no @Autowired needed,
        this.clock = clock;               // Spring uses it automatically
    }
}

@Configuration
class TimeConfig {
    @Bean                                 // @Bean: for types you don't own and can't
    Clock clock() {                       // annotate — the method body is the recipe
        return Clock.systemUTC();
    }
}

The review flag, spelled out

@Autowired private TaskService service; on a field means: the field cannot be final, the class can be constructed in an invalid half-empty state, and a plain unit test needs reflection to install a fake. Constructor injection costs four lines and removes all three problems. If a constructor grows past four or five parameters, that is the design talking — split the class, do not reach for field injection to hide the count.

If you came from the Go or Python pages: this is the same “accept interfaces at the edges, wire in main” discipline you already know — FastAPI’s Depends plays the same role — except the wiring code you wrote by hand in Go’s main() is derived from constructor signatures here. The trade: you write less plumbing, and in exchange the construction order lives in a framework you must trust and occasionally debug.

The Task API: records in, records out

A controller is a thin translation layer: HTTP in, domain call, HTTP out. Records make both edges honest — the request record says exactly what a client may send, the response record exactly what it will get back, and validation runs before your method is even called.

Four small files, all in dev.ladder.tasks. The domain record and the two API records first:

// Task.java — the domain record: immutable, equality by value
package dev.ladder.tasks;

import java.time.Instant;
import java.util.UUID;

public record Task(UUID id, String title, boolean done, Instant createdAt) {}

// CreateTaskRequest.java — what a client MAY send
package dev.ladder.tasks;

import jakarta.validation.constraints.NotBlank;

public record CreateTaskRequest(@NotBlank String title) {}

// TaskResponse.java — what a client WILL receive
package dev.ladder.tasks;

import java.time.Instant;
import java.util.UUID;

public record TaskResponse(UUID id, String title, boolean done, Instant createdAt) {
    static TaskResponse from(Task t) {
        return new TaskResponse(t.id(), t.title(), t.done(), t.createdAt());
    }
}

The service owns the store — a ConcurrentHashMap for now; part seven of the series swaps it for Postgres behind the same method signatures, which is the whole reason the controller never touches the map directly. Note markDone replaces the record rather than mutating it: records have no setters, so “update” means “new value, same key”, and computeIfPresent makes the read-modify-write atomic:

// TaskService.java
package dev.ladder.tasks;

import java.time.Instant;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.stereotype.Service;

@Service
public class TaskService {
    private final Map<UUID, Task> store = new ConcurrentHashMap<>();

    public Task create(String title) {
        var task = new Task(UUID.randomUUID(), title, false, Instant.now());
        store.put(task.id(), task);
        return task;
    }

    public List<Task> all() {
        return store.values().stream()
            .sorted(Comparator.comparing(Task::createdAt))   // part two, earning rent
            .toList();
    }

    public Optional<Task> byId(UUID id) {
        return Optional.ofNullable(store.get(id));
    }

    public Optional<Task> markDone(UUID id) {
        return Optional.ofNullable(store.computeIfPresent(id,
            (k, t) -> new Task(t.id(), t.title(), true, t.createdAt())));
    }
}

The controller maps the four endpoints. Where the happy path is the only path (GET /tasks), return the value and let Spring produce the 200; where the status code carries meaning — 201 with a Location, 404 for a missing id — return ResponseEntity and say so explicitly:

// TaskController.java
package dev.ladder.tasks;

import jakarta.validation.Valid;
import java.net.URI;
import java.util.List;
import java.util.UUID;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController                      // @Controller + @ResponseBody: returns become JSON
@RequestMapping("/tasks")
public class TaskController {
    private final TaskService service;

    public TaskController(TaskService service) {   // constructor injection, again
        this.service = service;
    }

    @PostMapping
    ResponseEntity<TaskResponse> create(@Valid @RequestBody CreateTaskRequest req) {
        var task = service.create(req.title());
        return ResponseEntity
            .created(URI.create("/tasks/" + task.id()))   // 201 + Location header
            .body(TaskResponse.from(task));
    }

    @GetMapping
    List<TaskResponse> all() {
        return service.all().stream().map(TaskResponse::from).toList();
    }

    @GetMapping("/{id}")
    ResponseEntity<TaskResponse> byId(@PathVariable UUID id) {
        return service.byId(id)
            .map(TaskResponse::from)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());   // empty Optional → 404
    }

    @PatchMapping("/{id}/done")
    ResponseEntity<TaskResponse> done(@PathVariable UUID id) {
        return service.markDone(id)
            .map(TaskResponse::from)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }
}

// TasksProperties.java — kebab-case keys bind to camelCase components
package dev.ladder.tasks;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "tasks")
public record TasksProperties(int maxOpen, String banner) {}

// TasksApplication.java — register it (or use @ConfigurationPropertiesScan)
@SpringBootApplication
@EnableConfigurationProperties(TasksProperties.class)
public class TasksApplication { ... }

// TaskService.java — configuration arrives by constructor, like everything else
@Service
public class TaskService {
    private final Map<UUID, Task> store = new ConcurrentHashMap<>();
    private final TasksProperties props;

    public TaskService(TasksProperties props) {
        this.props = props;
    }

    public Task create(String title) {
        long open = store.values().stream().filter(t -> !t.done()).count();
        if (open >= props.maxOpen()) {
            throw new IllegalStateException("open-task limit reached: " + props.maxOpen());
        }
        var task = new Task(UUID.randomUUID(), title, false, Instant.now());
        store.put(task.id(), task);
        return task;
    }

Never ddl-auto: update outside a demo

@Transactional is a proxy, and N+1 is a lazy list

The container does not change your method; it wraps your bean in a generated subclass that opens a transaction before the call and commits after. Everything surprising about @Transactional — and about lazy loading — follows from where that wrapper does and does not sit.

The working rules, applied to the service. Reads get readOnly = true — it lets Hibernate skip dirty-checking snapshots and hints the driver. Writes get the default. And note markDone no longer calls save: inside a transaction the loaded entity is managed, so mutating it is enough — the flush at commit writes the UPDATE.

@Service
public class TaskService {
  // ... constructor as before ...

  @Transactional(readOnly = true)
  public List<Task> open() {
    return repo.findByDoneFalse().stream().map(TaskEntity::toTask).toList();
  }

  @Transactional
  public Task markDone(UUID id) {
    var e = repo.findById(id).orElseThrow(() -> new TaskNotFoundException(id));
    e.markDone();          // managed entity: the commit flushes the UPDATE
    return e.toTask();     // no save() needed inside a transaction
  }
}

Three rules that are not visible in that code. Rollback happens for unchecked exceptions only — a checked exception commits unless you say @Transactional(rollbackFor = Exception.class). A transaction holds a pooled connection from first query to commit, so keep it short: with Hikari’s default pool of 10, one HTTP call made inside a transaction means ten slow requests can hold every connection while they wait on someone else’s API. And the classic silent failure:

@Service
public class SweepService {

  public void nightly() {
    this.sweep();          // same object, plain call: the proxy never sees it
  }                        // sweep() runs with NO transaction, silently

  @Transactional
  public void sweep() { /* delete old done tasks */ }
}

public record TaskSummary(UUID id, String title) { }

open-in-view: the default that hides all of this

Boot’s default (true, with a warning at startup) keeps the Hibernate session open while the JSON response is serialised, so a lazy collection touched by Jackson quietly loads mid-response. That makes N+1 invisible in development, moves query errors into the middle of a half-written response, and holds a pooled connection for the whole request. You already set open-in-view: false in the datasource YAML of the previous topic; with it, touching an unfetched lazy relation outside the service throws LazyInitializationException — loud, early, and exactly what you want.

Executors, shared state, and virtual threads

You never create threads by hand in a service; you hand tasks to an executor that owns a bounded pool. Java 21 then quietly removed the reason the pool had to be small.

First the classic toolkit, because most codebases still run on it. An ExecutorService owns the threads; you submit work and hold a Future. CompletableFuture adds composition — run two things, combine the results — and every blocking wait gets a timeout, the same reflex the Go page drilled with contexts.

ExecutorService pool = Executors.newFixedThreadPool(8);  // bounded, always

// submit + Future: fine for one-off background work
Future<Long> open = pool.submit(() -> repo.countByDone(false));
long n = open.get(2, TimeUnit.SECONDS);        // never get() without a timeout

// CompletableFuture: run both counts in parallel, combine, bound the whole thing
var openF = CompletableFuture.supplyAsync(() -> repo.countByDone(false), pool);
var doneF = CompletableFuture.supplyAsync(() -> repo.countByDone(true),  pool);

long total = openF.thenCombine(doneF, Long::sum)
                  .orTimeout(2, TimeUnit.SECONDS)
                  .join();

pool.shutdown();   // in Spring: expose the pool as a @Bean so the container closes it

Shared state, in one pass. The demo below is the whole problem: counter++ is a read, an add and a write, and two threads interleaving those three steps overwrite each other’s updates. No exception, no warning — just a wrong number.

// Race.java -- run it, the count is wrong, and differently wrong each time
public class Race {
  static long counter = 0;                      // plain shared field

  public static void main(String[] args) throws InterruptedException {
    Runnable inc = () -> { for (int i = 0; i < 1_000_000; i++) counter++; };
    Thread a = new Thread(inc);
    Thread b = new Thread(inc);
    a.start(); b.start();
    a.join();  b.join();
    System.out.println(counter);                // almost never 2000000
  }
}
// the fixes, smallest hammer first
static final AtomicLong counter = new AtomicLong();
counter.incrementAndGet();                       // lock-free read-modify-write

// per-key atomic updates on a shared map -- no lock around the whole map
ConcurrentHashMap<String, Long> hits = new ConcurrentHashMap<>();
hits.compute("tasks", (k, v) -> v == null ? 1 : v + 1);

// synchronized: mutual exclusion AND visibility, for multi-field invariants
synchronized (lock) { balance -= amount; ledger.add(entry); }

// volatile: visibility only -- a flag one thread writes, others read.
// It does NOT make ++ atomic; that mistake is the race above with extra steps.
volatile boolean shuttingDown = false;

Now the Java 21 headline. A virtual thread is a thread whose stack lives on the heap; the JVM mounts it on a carrier (an OS thread) only while it is actually running, and unmounts it the moment it blocks. Creating one is cheap enough that pooling them is an anti-pattern — you create one per task and throw it away.

Thread.ofVirtual().name("enrich-", 0).start(() -> enrich(taskId));

// one virtual thread per task; close() waits for all of them
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
  for (UUID id : ids) {
    exec.submit(() -> enrich(id));     // 10,000 submissions: fine
  }
}

# and in Spring Boot -- one line in application.yml:
spring:
  threads:
    virtual:
      enabled: true   # Tomcat serves each request on a virtual thread

With that property on, the blocking repository calls this page just wrote stop costing platform threads while they wait on Postgres — the thread-pool ceiling on concurrent requests effectively disappears, and the next limit is the database pool, which is where you want it.

The pinning caveat

On Java 21, a virtual thread that blocks inside a synchronized block pins its carrier — the OS thread waits after all. Old drivers and libraries that guard I/O with synchronized can quietly re-create the platform-thread ceiling. Prefer ReentrantLock around blocking calls, and run with -Djdk.tracePinnedThreads=short to see pinning happen. (JDK 24 removed this limitation; on 21 it is real.)

Java · 18

The heap, the collector, and the container limit

Allocation in Java is a pointer bump — nearly free. The bill arrives as garbage-collection pauses, and in containers, as the gap between what you told the JVM (-Xmx) and what you told Kubernetes (the memory limit). Those are two different numbers and the kernel enforces the second.

What the collector is doing with that heap: nearly all objects die young, so the heap is split into a young generation — collected often and cheaply, because collecting means copying the few survivors — and an old generation for whatever survives repeatedly, collected rarely and more expensively. Allocation itself is a thread-local pointer bump, which is why idiomatic Java allocates freely and why the cost model is the opposite of C’s: creating garbage is cheap, keeping objects alive is what costs.

G1, the default collector, does this region by region against a pause target (200 ms by default) and is the right answer until measured otherwise. ZGC (-XX:+UseZGC) trades some throughput for sub-millisecond pauses on heaps up to terabytes — one flag, when p99 latency says so.

# the flags that matter, and the ones to stop using
java -Xms256m -Xmx256m -jar app.jar        # fixed heap: fine on a VM you own

# in a container, size from the cgroup limit instead of hard-coding:
java -XX:MaxRAMPercentage=75 \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/tmp/heap.hprof \
     -jar app.jar

# flight recording: always-on production profiling, ~1% overhead
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr -jar app.jar
jfr print --events jdk.GCPhasePause rec.jfr   # or open rec.jfr in JDK Mission Control

When the heap does run out you get java.lang.OutOfMemoryError — an Error, not an Exception, and not one to catch: the useful move is the flag above, which writes a heap dump on the way down so you can see what filled the heap rather than guessing. And for a JVM that is alive but suspicious, jcmd asks it questions directly — no restart, no agent, nothing installed.

One error shape: @RestControllerAdvice and ProblemDetail

Controllers never catch anything. The service throws domain exceptions; one advice class catches everything that escapes and translates it into RFC 9457 application/problem+json — the same three-case split every API ends up needing.

Recall from part six that CreateTaskRequest carries @NotBlank String title and the controller takes @Valid @RequestBody CreateTaskRequest req — that is what raises the validation exception in lane two. The domain exception in lane one is TaskNotFoundException, the two-line class you wrote in part seven. The whole advice class, complete:

// src/main/java/dev/ladder/tasks/ApiExceptionHandler.java
package dev.ladder.tasks;

import java.util.Map;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
class ApiExceptionHandler {

  private static final Logger log = LoggerFactory.getLogger(ApiExceptionHandler.class);

  @ExceptionHandler(TaskNotFoundException.class)
  ProblemDetail notFound(TaskNotFoundException ex) {
    var p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    p.setTitle("Task not found");
    return p;                          // Spring serialises it as problem+json
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  ProblemDetail invalid(MethodArgumentNotValidException ex) {
    var p = ProblemDetail.forStatusAndDetail(
        HttpStatus.BAD_REQUEST, "Request body failed validation");
    p.setTitle("Validation failed");
    p.setProperty("errors", ex.getFieldErrors().stream()
        .map(f -> Map.of("field", f.getField(),
                         "message", String.valueOf(f.getDefaultMessage())))
        .toList());                    // extra members are allowed by RFC 9457
    return p;
  }

  @ExceptionHandler(Exception.class)   // the safety net -- keep it LAST in your head
  ProblemDetail internal(Exception ex) {
    log.error("unhandled exception", ex);          // full trace -> the log
    var p = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
    p.setTitle("Internal error");                  // nothing else -> the client
    return p;
  }
}

Calling another service: RestClient, built once

The rules are the ones every sibling page drilled: every call has a timeout, 4xx and 5xx are different kinds of failure, and you retry only what is safe to repeat. The Java-specific part is where those rules live — in one @Bean, not sprinkled across call sites.

// src/main/java/dev/ladder/tasks/HttpClients.java
package dev.ladder.tasks;

import java.time.Duration;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.http.client.ClientHttpRequestFactoryBuilder;
import org.springframework.boot.http.client.ClientHttpRequestFactorySettings;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpStatusCode;
import org.springframework.web.client.RestClient;

@Configuration
class HttpClients {

  @Bean
  RestClient auditClient(RestClient.Builder builder,
                         @Value("${audit.base-url}") String baseUrl) {
    var settings = ClientHttpRequestFactorySettings.defaults()
        .withConnectTimeout(Duration.ofSeconds(2))    // reaching the host
        .withReadTimeout(Duration.ofSeconds(3));      // waiting for bytes

    return builder
        .baseUrl(baseUrl)
        .requestFactory(ClientHttpRequestFactoryBuilder.detect().build(settings))
        .defaultStatusHandler(HttpStatusCode::is5xxServerError, (req, res) -> {
          throw new AuditUnavailable(res.getStatusCode().value());   // transient
        })
        .defaultStatusHandler(HttpStatusCode::is4xxClientError, (req, res) -> {
          throw new AuditRejected(res.getStatusCode().value());      // terminal
        })
        .build();
  }
}

class AuditUnavailable extends RuntimeException {   // their problem: 5xx, timeouts
  AuditUnavailable(int status) { super("audit unavailable: " + status); }
}
class AuditRejected extends RuntimeException {      // our problem: 4xx
  AuditRejected(int status) { super("audit rejected the request: " + status); }
}

Using it is deliberately boring — and note the idempotency thinking baked into the payload: the event carries the task id and type, so if a retry does happen after an ambiguous timeout, the audit service can deduplicate. The same reasoning as idempotency keys on the backend-foundations page, spelled in Java.

@Service
public class AuditService {

  private final RestClient client;

  AuditService(RestClient auditClient) { this.client = auditClient; }

  public void recordDone(Task task) {
    client.post()
        .uri("/events")
        .contentType(MediaType.APPLICATION_JSON)
        .body(new AuditEvent("task.done", task.id(), Instant.now()))
        .retrieve()
        .toBodilessEntity();     // throws AuditUnavailable / AuditRejected on error
  }
}

record AuditEvent(String type, UUID taskId, Instant at) { }

Wire it in with one field and one line — TaskService takes an AuditService through its constructor next to the repository, and markDone reports the event after the save:

// TaskService.java -- markDone, after wiring in the audit client
public Task markDone(UUID id) {
    var e = repo.findById(id).orElseThrow(() -> new TaskNotFoundException(id));
    e.markDone();
    var task = repo.save(e).toTask();
    audit.recordDone(task);     // audit is the constructor-injected AuditService
    return task;
}

The three HTTP clients, one line each

RestClient (Boot 3.2+) is the default choice: fluent, synchronous, plays perfectly with virtual threads. WebClient is the reactive one — you take it when you are already in WebFlux, not for a timeout. RestTemplate is the legacy one: maintained, not evolving, fine to leave in old code and wrong to start new code with.

Run it

No audit service exists, which is exactly the test. Point audit.base-url at the JDK’s built-in static server — it answers POST with 501 — then restart it aimed at a non-routable address. One exercises the 5xx handler, the other the connect timeout; neither hangs. (A dead local port would not do: the kernel refuses instantly, and no timeout ever fires.)

$ jwebserver -p 9090 &
$ ./mvnw spring-boot:run -Dspring-boot.run.arguments=--audit.base-url=http://localhost:9090
$ curl -s -X PATCH localhost:8080/tasks/<id>/done
... AuditUnavailable: audit unavailable: 501    ← the 5xx handler fired
$ kill %1                         # done with the static server; Ctrl-C the app too
$ ./mvnw spring-boot:run -Dspring-boot.run.arguments=--audit.base-url=http://10.255.255.1:9090
$ time curl -s -X PATCH localhost:8080/tasks/<id>/done
real  0m2.1s    ← packets into a black hole: the 2s connect timeout, not an infinite hang

// rung 3 -- the full path, against the same postgres:16 production runs
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class TasksEndToEndTest {

  @Container
  @ServiceConnection                     // injects url/user/password automatically
  static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");

  @Autowired TestRestTemplate http;

  @Test
  void createThenFetchAgainstRealPostgres() {

Packaging, probes, and dying politely

The fat jar is self-contained but a Docker image built from it re-ships 40 MB of unchanged dependencies on every one-line fix. Boot’s layered extraction fixes the caching; graceful shutdown and the actuator probes fix everything the cloud page said about pods being killed mid-request.

First the production settings, then the image. The probes property gives the health endpoint two sub-paths that mean exactly what the cloud page’s liveness and readiness probes need them to mean — and Boot flips readiness during startup and shutdown automatically.

# application.yml -- the production additions
server:
  shutdown: graceful              # drain in-flight requests on SIGTERM
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s   # stay under the pod’s 30s grace period
management:
  endpoint:
    health:
      probes:
        enabled: true             # exposes /liveness and /readiness
  endpoints:
    web:
      exposure:
        include: health           # and nothing else, on purpose

# and in the Deployment, from the cloud page:
#   livenessProbe:  httpGet /actuator/health/liveness  :8080
#   readinessProbe: httpGet /actuator/health/readiness :8080

(That block assumes spring-boot-starter-actuator is in the pom — one dependency, no version.) Now the Dockerfile. ./mvnw package produces one fat jar, and the trick is to not copy it into the image as one blob: jarmode=tools extracts it into layers so the 40 MB of dependencies — which change rarely — sit in a different image layer from your classes, which change every commit. Rebuilds and pulls then move kilobytes, not the world.

# Dockerfile
FROM eclipse-temurin:21-jre AS extract
WORKDIR /app
COPY target/tasks-0.0.1-SNAPSHOT.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd --system app
USER app                                  # never root; nothing here needs it

# rarely-changing layers first: cache hits on every rebuild
COPY --from=extract /app/extracted/dependencies/          ./
COPY --from=extract /app/extracted/spring-boot-loader/    ./
COPY --from=extract /app/extracted/snapshot-dependencies/ ./
COPY --from=extract /app/extracted/application/           ./

# the memory lesson from the JVM part, applied
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

ExitOnOutOfMemoryError deserves its one sentence: a JVM that has thrown OutOfMemoryError on some thread is a zombie that still answers liveness probes, and it is better to die and be restarted by the kubelet than to limp.

Run it

Build, run against the compose network, and curl the probes. Then touch a source file, rebuild, and read the build output: every layer above application/ reports CACHED.

$ docker build -t tasks:1 .
$ docker run --rm --network host --memory 512m tasks:1
$ curl -s localhost:8080/actuator/health/readiness
{"status":"UP"}                              ← K8s would route traffic now
$ curl -s localhost:8080/actuator/health/liveness
{"status":"UP"}

What “idiomatic” means in a Java review

Idiom in Java is mostly about narrowing what code is allowed to do: make it immutable, make it final, make the type say it. Each rewrite below deletes a state the wrong version could reach — the same argument the Python and Go pages made, wearing a suit.

Field injection (@Autowired on a field)Untestable without the container; hides the dependency countOne constructor, final fields — Spring wires it with no annotation

Returning null for “not found”The caller’s NPE fires far from the causeOptional<T> as the return type; orElseThrow at the edge

The toolchain that argues for you

Spotless with google-java-format ends formatting debate the way black did for Python. Error Prone runs inside javac and catches real bug patterns (a missing @Override, a self-assignment, an ignored return). SpotBugs reads the bytecode for null-flow and resource leaks. JaCoCo measures coverage in mvn verify. Wire all four into the build and a class of review comments disappears.

Idioms that have quietly expired

new Date() → java.time.Instant. Getters/setters on a data holder → a record. synchronized collections → ConcurrentHashMap or immutability. XML config and web.xml → annotations and application.yml. RestTemplate → RestClient. Application servers → the embedded server in the jar. If a tutorial shows any of the left column, check its date.

Run it

Add Spotless to the tasks project’s pom.xml plugins block, then let it rewrite your formatting and fail the build when someone skips it.

[INFO] Spotless check succeeded.
