Part three

The machine underneath

Hardware, the operating system, concurrency and the network. These four turn up in three disguises: as fundamentals questions in their own right, as the reason a system-design answer is wrong, and as the explanation for a bug in a debugging round. A candidate who can say why a thing is slow is scored a level above one who knows that it is.

Topic · xx

The processor, memory and the cost of a cache miss

Every performance question eventually reduces to one number: how far away the data is. Knowing the ladder by heart is the cheapest possible preparation and it pays out in coding rounds, design rounds and debugging rounds alike.

Cache line64 bytes, the unit of transfer. Reading one byte fetches all 64 — which is why sequential access is nearly free.
LocalityTemporal and spatial. Almost every “make it faster” answer is one of these two in disguise.
False sharingTwo cores writing different variables in the same line, invalidating each other. Fix by padding.
Branch predictionA mispredict costs ~15 cycles. Sorted input can make identical code twice as fast.
Pipelining, superscalar, SIMDWhy loop count is a bad proxy for time, and why branchless code sometimes wins.
Virtual memoryPages, the page table, the TLB, a page fault. Explains a mysterious first-request latency.
NUMAMemory attached to one socket is slower from the other. Turns up in database and JVM tuning questions.
Endianness and alignmentWire formats, struct padding, and why a field order change shrinks a struct.
Word size and overflow32 vs 64 bit, signed overflow, floating-point representation and why 0.1 + 0.2 is not 0.3.
Memory hierarchy cost modelRegisters, caches, RAM, disk, network — the five rungs above, in order, with numbers.

The operating system your service is a guest of

Processes, threads, scheduling, memory and files. Asked directly in systems-heavy loops, and indirectly everywhere else — “why did the container get killed?” is an operating-system question wearing a cloud costume.

Process vs threadSeparate address space vs shared. Everything hard about concurrency follows from the word “shared”.
The schedulerTime slices, priorities, preemption, run queues. Why a busy machine adds latency without adding work.
Context switchA few microseconds plus a cold cache. The reason a thread per request stops scaling.
System callsThe user/kernel boundary, and why a syscall per byte is the bug. strace is the tool they hope you name.
Virtual address spaceStack, heap, text, mapped files. Where a segmentation fault comes from and what a stack overflow is.
Paging and swapPage faults, minor vs major, thrashing, and the OOM killer that ended your pod.
The page cacheWhy a second read of the same file is free, and why “the database has 8 GB of RAM” understates its cache.
File descriptorsA finite per-process table. Leaks show up as EMFILE under load and never in testing.
Blocking vs non-blocking I/OAnd the four models: blocking, non-blocking polling, readiness (epoll/kqueue), completion (io_uring, IOCP).
SignalsSIGTERM then SIGKILL — the contract behind graceful shutdown in every orchestrator.
Pipes, sockets, shared memoryThe inter-process channels, and which one a question is really describing.
fsync and durabilityA write returns before it is durable. This one fact underlies write-ahead logs and half of all database questions.
Permissions and usersUID/GID, file modes, why the container runs as root and why it should not.
cgroups and namespacesWhat a container actually is: limits plus a private view. Memory limits kill; CPU limits throttle.
  • What happens between typing a command and the program running?fork, exec, the loader, dynamic linking, the entry point — and whether you can stop at the right depth for the role.
  • Your service is at 100% CPU but doing no work. What now?a method: is it user or system time, a spin loop, GC, a lock convoy? Naming top, perf and a flame graph is the expected answer.
  • Why was the container killed with exit code 137?128 + 9, so SIGKILL, so the memory cgroup limit — and the follow-up about heap versus RSS.
  • How does a thread pool of 200 threads behave differently from 20?context switching, memory per stack, and Little’s law: more threads do not create more capacity, they only lengthen the queue.
Topic · xx

Concurrency: races, locks and the memory model

The most reliably mishandled subject in the whole loop. Almost everyone can define a race condition; far fewer can say why a correctly locked program can still read stale data on another core.

// race.go — go build -race is the only honest way to find these.
var counter int                       // shared, unprotected

func worker(wg *sync.WaitGroup) {
    defer wg.Done()
    for i := 0; i < 1000; i++ {
        counter++                     // read, add, write: three steps
    }
}

// Three fixes, in increasing order of how much they let you do:

var mu sync.Mutex                     // 1. protects any amount of state
mu.Lock(); counter++; mu.Unlock()

var n atomic.Int64                    // 2. one word, no lock, no waiting
n.Add(1)

for {                                 // 3. read-modify-write on your own terms
    old := n.Load()
    if n.CompareAndSwap(old, old*2) { // fails if anyone else moved it
        break
    }
}
Race conditionThe result depends on timing. A data race is the narrower case: unsynchronised access where one side writes.
Critical sectionThe code that must not interleave. Keep it small; a lock held across I/O is a design bug.
Mutex, RWMutex, spinlockAnd when a reader–writer lock is slower than a plain one, which is more often than people expect.
SemaphoreA permit count. The right primitive for “at most N concurrent”, which is most rate-limiting questions.
Condition variableWait until a predicate holds. Always in a loop — spurious wakeups are real.
DeadlockFour conditions; break any one. Consistent lock ordering is the answer they want.
Livelock and starvationProgress without work, and progress for everyone but you. Backoff and fairness are the fixes.
Atomics and CASLock-free algorithms, and the ABA problem that makes naive pointer CAS unsound.
Memory modelHappens-before, sequential consistency, acquire/release, barriers. Why volatile in Java is not volatile in C.
Thread poolsBounded queues, rejection policies, and why an unbounded queue converts a latency problem into an outage.
Async and event loopsSingle-threaded concurrency: callbacks, promises, async/await, and the blocking call that stalls everything.
CSP and actorsChannels and message passing — share memory by communicating instead of the other way round.
ImmutabilityThe cheapest concurrency strategy: nothing to protect. Persistent structures and copy-on-write.
Producer–consumerThe archetypal exercise, and where backpressure enters the conversation.
Thread safety of your own types“Is HashMap safe?” is really “what does your language guarantee, and at what cost?”
Parallel vs concurrentDoing many things at once vs dealing with many things at once. Interviewers do ask for the distinction.
Topic · xx

The network, from the frame to the request

“What happens when you type a URL and press enter” is still asked because it is unboundedly deep: you can answer it in thirty seconds or forty minutes, and where you stop tells the interviewer your level.

The layersLink, network, transport, application. Enough of the OSI model to place a problem, not to recite seven names.
IP addressingIPv4, IPv6, CIDR, subnets, private ranges, NAT, and reading a routing table.
DNSRecursive resolution, record types, TTL, and why a deploy that changed a record is still broken for some users.
TCPThree-way handshake, sequence numbers, retransmit, sliding window, slow start, Nagle, TIME_WAIT.
UDP and QUICNo ordering, no delivery guarantee — and why HTTP/3 rebuilt those on top of it anyway.
TLSHandshake, certificate chain, SNI, ALPN, mTLS, and where termination happens in your architecture.
HTTP versions1.1 keep-alive and pipelining, 2 multiplexing and HPACK, 3 over QUIC. Head-of-line blocking at each.
HTTP semanticsMethods, safe and idempotent, status codes, caching headers, cookies, CORS, content negotiation.
Socketsbind, listen, accept, the backlog queue, and what a connection actually is to the kernel.
Load balancingL4 vs L7, round robin, least connections, consistent hashing, health checks, connection draining.
ProxiesForward, reverse, sidecar. Where TLS ends, where retries happen, and who sees the real client IP.
WebSockets and SSELong-lived connections, and what they cost a load balancer that assumed short ones.
gRPC and HTTP/2 streamsMultiplexing, flow control, deadlines propagated across hops.
Bandwidth, latency, jitter, lossFour different problems that all present as “the network is slow”.
The toolsdig, curl -v, ss, tcpdump, traceroute, mtr. Naming the right one is half the answer.
  • What happens when you type a URL and press enter?whether you can walk the whole path — cache, DNS, ARP, route, handshake, TLS, request, render — and stop at the depth the role needs.
  • The service is fine but users say it is slow. Where do you look?splitting client, network and server time; the words TTFB, round trip and percentile.
  • Why would a request succeed from your laptop and fail from the pod?DNS, egress rules, security groups, proxies, certificate trust stores, IPv6 — a list, then a way to bisect it.
  • TCP or UDP for this?whether you reason from the requirement (ordering, loss tolerance, latency) rather than from a memorised table.
