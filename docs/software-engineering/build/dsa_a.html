Part one

What a cost actually costs

Before any structure or any algorithm: three ideas that decide whether the rest of this page helps you or misleads you. What the notation promises and what it quietly refuses to promise. Why two O(n) loops can differ by two orders of magnitude. And why the memory an algorithm uses is usually the constraint that bites first.

DSA · xx

What the notation is hiding

Big-O is a statement about the shape of the curve as the input grows without bound. It is not a statement about speed, it deliberately discards the constant factor, and it says nothing at all about the size of input you actually have. Every one of those omissions is load-bearing.

NotationWhat it claimsWhat people wrongly assume
O(f) upper boundBeyond some n, the cost is at most c·f(n) for some constant cThat it is tight. O(n²) is a true statement about binary search. Useless, but true.
Θ(f) tight boundThe cost is squeezed between two constant multiples of f(n)This is what people usually mean when they say “O”, and it is the honest thing to state.
Ω(f) lower boundThe cost is at least c·f(n)That it describes an algorithm. Its best use is describing a problem: comparison sorting is Ω(n log n) no matter who writes it.
AmortisedAveraged over a sequence, with no probability involvedThat it is the average case. It is a worst-case guarantee about totals: any n appends to a doubling array cost O(n) between them, always.
Average caseExpected cost over a distribution of inputsThat the distribution is the one you have. Quicksort’s O(n log n) average assumes random pivots; sorted input with a naive pivot gives O(n²).
Worst caseThe cost when an adversary picks the inputThat it is paranoid. If the input comes over HTTP, the adversary is real: hash flooding was a live denial-of-service class for years.
L1 · Beginner

Read the loops

  • Count nested iterations. Two loops over the same n, one inside the other, is O(n²). Sequential loops add, so they stay O(n).
  • Halving is a logarithm. Anything that discards half the remaining work each step is O(log n).
  • Drop constants and lower terms. 3n + 200 is O(n); n² + n is O(n²).
  • Know the ladder by heart: constant, log, linear, n log n, quadratic, exponential.
L2 · Intermediate

Analyse what is actually there

  • The hidden cost of a line. s = s + x in a loop is quadratic in most languages; list.insert(0, x) is O(n) each time; slicing copies.
  • Amortised vs worst case. A hash insert is O(1) amortised, but the one that triggers the resize is O(n). If you have a latency budget, that tail is your problem.
  • Recursion by the recurrence. T(n) = 2T(n/2) + O(n) is n log n — that single line explains merge sort, quicksort and most divide-and-conquer.
  • Two variables mean two symbols: graph work is O(V + E), not “O(n)”.
L3 · Advanced

Know when the model breaks

  • The constant wins below a threshold. Every industrial sort falls back to insertion sort under about 12–32 elements, because n² with a tiny constant beats n log n with a large one.
  • The model assumes uniform memory. It is wrong by two orders of magnitude, which the next section is about.
  • Adversarial inputs change the class. Randomised pivots and seeded hashes are not paranoia; they are what makes the average case an honest claim.
  • Measure before and after. An analysis tells you which line to be on; only a benchmark tells you where you are on it.

Snippets in Go, Python and Java — switch in the bar, or press g / p / j.

// bench_test.go — the only honest way to compare two implementations.
// Run: go test -bench=. -benchmem -count=6 ./... | tee new.txt
//      benchstat old.txt new.txt   # tells you whether the difference is real
func BenchmarkContains(b *testing.B) {
    for _, n := range []int{16, 256, 4096, 65536} {
        haystack := rand.Perm(n)
        set := make(map[int]struct{}, n)
        for _, v := range haystack {
            set[v] = struct{}{}
        }
        needle := n - 1                          // worst case for the scan

        b.Run(fmt.Sprintf("slice/%d", n), func(b *testing.B) {
            for b.Loop() {                       // Go 1.24+; b.N loop before that
                _ = slices.Contains(haystack, needle)
            }
        })
        b.Run(fmt.Sprintf("map/%d", n), func(b *testing.B) {
            for b.Loop() {
                _, _ = set[needle]
            }
        })
    }
}

// slice/16      6.1 ns    map/16      5.4 ns   <-- no difference worth having
// slice/65536  21400 ns   map/65536   5.6 ns   <-- three orders of magnitude
// The crossover, not the asymptote, is what decides your design.
# bench.py — timeit, because a stopwatch around one call measures the clock.
import random
import timeit

def compare(n: int) -> None:
    haystack = random.sample(range(n * 4), n)
    hay_set = set(haystack)
    needle = haystack[-1]                        # worst case for the scan

    # number= is chosen so each variant runs for a measurable stretch;
    # repeat() then takes the *minimum*, which is the least noisy statistic.
    seq = min(timeit.repeat(lambda: needle in haystack, number=1000, repeat=7))
    hsh = min(timeit.repeat(lambda: needle in hay_set, number=1000, repeat=7))
    print(f"n={n:>6}  list {seq * 1e6:7.1f} us   set {hsh * 1e6:6.1f} us   "
          f"ratio {seq / hsh:6.1f}x")

for n in (16, 256, 4096, 65536):
    compare(n)

# n=    16  list     6.9 us   set    3.4 us   ratio    2.0x
# n= 65536  list 21500.0 us   set    3.5 us   ratio 6100.0x
#
# `in` on a list is O(n) and `in` on a set is O(1). Identical syntax,
# different curve. This is the single most common accidental O(n^2)
# in Python: a membership test on a list inside a loop over another list.
// ContainsBench.java — JMH, because the JIT will happily delete a loop
// whose result nobody uses, and then you benchmark nothing at all.
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Benchmark)
@Fork(value = 2, warmups = 1)
@Warmup(iterations = 5)                          // let C2 compile and settle
@Measurement(iterations = 8)
public class ContainsBench {

    @Param({"16", "256", "4096", "65536"})
    public int n;

    private List<Integer> list;
    private Set<Integer> set;
    private Integer needle;

    @Setup
    public void setUp() {
        list = ThreadLocalRandom.current().ints(n, 0, n * 4).boxed().toList();
        set = new HashSet<>(list);
        needle = list.get(n - 1);                 // worst case for the scan
    }

    // Returning the value hands it to the Blackhole, so it cannot be
    // optimised away. This is the whole reason to use JMH over a loop and
    // System.nanoTime().
    @Benchmark public boolean listContains() { return list.contains(needle); }
    @Benchmark public boolean setContains()  { return set.contains(needle); }
}

The threshold matters more than the exponent

All three benchmarks above tell the same story, and it is not “hash sets are faster”. At sixteen elements a linear scan of a contiguous array beats a hash lookup, because it is one cache line and no hashing. At sixty-five thousand it loses by three orders of magnitude. The asymptotic argument tells you these lines must cross; only measurement tells you where, and the answer for your data on your hardware is the number your design should turn on. Knowing that slices.Contains is O(n) is the beginning of the analysis, not the end of it.

The machine the analysis ignores

Complexity analysis counts operations and charges the same price for each. Real hardware charges by where the data is, and the spread between the cheapest and the dearest answer is roughly a factor of a hundred. Two structures with identical O(n) traversals can differ by that much, and nothing in the notation will warn you.

Cache line64 bytes. The smallest unit memory will move. Reading one byte costs the same as reading all sixty-four, so layout decides how much of that you waste.
PrefetcherPredicts strides. Sequential and fixed-stride access are effectively free after the first miss. Pointer chasing defeats it completely.
Branch predictor~95% accurate, ~15 cycles to be wrong. A comparison sort over random data mispredicts constantly, which is why branchless partitioning is a real optimisation.
AllocationNot free, and not counted. One node per element means one allocation, one header and one pointer of overhead each — before the cache misses.
// layout.go — identical asymptotics, very different machines.

type Node struct {                               // 24 bytes of payload,
    Value int64                                  // plus an 8-byte pointer,
    Next  *Node                                  // plus allocator overhead,
}                                                // scattered across the heap

func SumList(head *Node) int64 {
    var total int64
    for n := head; n != nil; n = n.Next {        // one cache miss per hop
        total += n.Value
    }
    return total
}

func SumSlice(xs []int64) int64 {
    var total int64
    for _, v := range xs {                       // 8 values per cache line,
        total += v                               // and the next line is already
    }                                            // on its way
    return total
}

// n = 10,000,000 on a warm machine:
//   SumSlice   6.8 ms      SumList   402 ms      59x, same O(n)
//
// A []Node (values, not pointers) recovers most of the gap. Prefer
// slices of structs to slices of pointers unless you need identity or
// the elements are genuinely large.
# layout.py — in Python every int in a list is already a pointer, so the
# question is not "list or linked list" but "objects or a buffer".
import array
import sys

xs = list(range(1_000_000))                      # 8 MB of pointers ...
buf = array.array("q", range(1_000_000))         # ... plus ~28 bytes per int

print(sys.getsizeof(xs) / 1e6, "MB of pointers")         # 8.06
print(sys.getsizeof(buf) / 1e6, "MB, values inline")     # 8.00, and that is all

# sum(xs)  ~4.5 ms   -- dereference, unbox, add, per element
# sum(buf) ~9.0 ms   -- array.array re-boxes on the way out, so this is
#                       *slower* despite the better layout: the win is
#                       memory, not speed
#
# numpy is the version that gets both, because the loop moves into C:
#   np.arange(1_000_000).sum()   ~0.4 ms, 8 MB, one pass, no boxing.
#
# The lesson is not "use numpy". It is that CPython's data model puts a
# pointer hop between you and every value, so the constant factor on a
# pure-Python O(n) loop is ~100x a compiled one. Choose the algorithm
# first; then choose whether the loop should run in Python at all.
// Layout.java — the difference between a value and a reference to one.

// Every element here is a pointer to a boxed Integer somewhere on the
// heap: 16 bytes of header plus 4 of payload, scattered by the allocator.
List<Integer> boxed = IntStream.range(0, 10_000_000).boxed().toList();

// Here the values are the array. One allocation, 40 MB, perfectly linear.
int[] flat = IntStream.range(0, 10_000_000).toArray();

long sumBoxed(List<Integer> xs) {
    long total = 0;
    for (Integer x : xs) total += x;             // deref + unbox per element
    return total;
}

long sumFlat(int[] xs) {
    long total = 0;
    for (int x : xs) total += x;                 // 16 ints per cache line
    return total;
}

// sumFlat    ~7 ms       sumBoxed   ~95 ms      13x, same O(n)
//
// Integer caches -128..127, so small-value benchmarks look far better
// than production. Use int[], long[] and double[] on hot paths, and
// reach for the primitive streams (IntStream, LongStream) rather than
// Stream<Integer>.

Space, and the stack nobody counted

Every algorithm has a space complexity as well as a time complexity, and in production it is usually the one that fails first — because running out of memory is an incident, while being slow is a ticket. Recursion depth is space. It is the space most often left out of the analysis.

AlgorithmExtra spaceWhat that means in practice
Insertion / selection sortO(1)Truly in place. This is one reason they survive as the base case of better sorts.
HeapsortO(1)In place and O(n log n) worst case — the only common sort that is both. It loses on cache behaviour, which is why it is rarely the default.
QuicksortO(log n)Stack, not heap — but only if you recurse into the smaller side and loop on the larger. Recurse naively and the worst case is O(n) stack frames.
Merge sortO(n)The buffer is the price of stability and of predictable worst-case time. On linked lists it drops to O(log n), because merging needs no buffer.
BFS on a graphO(V)The frontier can be the whole width of the graph. On a wide, shallow graph BFS is the memory hog and DFS is cheap; on a deep one it is the reverse.
Recursive DFSO(depth)A stack frame per level. A million-node path graph will overflow the stack in every language on this page unless you make the traversal iterative.
Memoised DPO(states)The table is the algorithm. When the table does not fit, the fix is usually to keep only the rows the recurrence still needs.
 
// stack.go — Go grows goroutine stacks on demand (2 KB start, up to
// 1 GB by default), so deep recursion usually *works* and then abruptly
// does not, with "goroutine stack exceeds limit" and no recovery.

func SumRec(n *Node) int64 {                     // O(depth) stack
    if n == nil {
        return 0
    }
    return n.Value + SumRec(n.Next)              // not a tail call: Go has none
}

// The iterative form is the same algorithm with the frames deleted.
func SumIter(n *Node) int64 {                    // O(1) stack
    var total int64
    for ; n != nil; n = n.Next {
        total += n.Value
    }
    return total
}

// For trees, where iteration is genuinely less clear, carry your own
// stack. It is a slice, it costs one allocation, and it cannot overflow
// before the heap does.
func InOrder(root *TreeNode, visit func(int)) {
    stack := make([]*TreeNode, 0, 32)
    for cur := root; cur != nil || len(stack) > 0; {
        for ; cur != nil; cur = cur.Left {
            stack = append(stack, cur)           // walk left, remembering
        }
        cur = stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        visit(cur.Val)
        cur = cur.Right
    }
}
# stack.py — CPython's limit is a *guard*, not the real stack size.
import sys

sys.getrecursionlimit()                          # 1000 by default

# Raising it does not give you more C stack; it removes the check that
# was protecting you from a hard segfault. Since 3.12 pure-Python frames
# no longer consume C stack, which helps -- but the ceiling is still
# finite and the failure below it is much less friendly.
sys.setrecursionlimit(20_000)                    # a smell, not a fix

def in_order_recursive(node, out):               # O(depth) frames
    if node is None:
        return
    in_order_recursive(node.left, out)
    out.append(node.val)
    in_order_recursive(node.right, out)

def in_order(root):                              # O(depth) list, no frames
    out, stack, cur = [], [], root
    while cur is not None or stack:
        while cur is not None:                   # walk left, remembering
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        out.append(cur.val)
        cur = cur.right
    return out

# A balanced tree of a million nodes is 20 deep and recursion is fine.
# A million-node tree built by inserting sorted keys is a linked list
# 1,000,000 deep, and only the iterative version survives it. Which one
# you have depends on data you do not control.
// Stack.java — the JVM gives each thread a fixed stack, default about
// 512 KB to 1 MB. Deep recursion throws StackOverflowError, which is an
// Error, not an Exception: do not catch it and carry on.

// -Xss4m raises it per thread. That is a workaround with a cost:
// thousands of threads at 4 MB of reserved stack each adds up fast.

void inOrderRecursive(TreeNode node, List<Integer> out) {   // O(depth) frames
    if (node == null) return;
    inOrderRecursive(node.left, out);
    out.add(node.val);
    inOrderRecursive(node.right, out);
}

List<Integer> inOrder(TreeNode root) {                      // O(depth) heap
    List<Integer> out = new ArrayList<>();
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !stack.isEmpty()) {
        while (cur != null) {                                // walk left, remembering
            stack.push(cur);
            cur = cur.left;
        }
        cur = stack.pop();
        out.add(cur.val);
        cur = cur.right;
    }
    return out;
}

// Use ArrayDeque, never java.util.Stack: Stack extends Vector, so every
// push and pop is synchronised and it exposes indexed access into the
// middle of a stack, which is not a thing a stack should have.

Depth is data-dependent, and data is adversarial

A recursive traversal that is 20 frames deep on your test tree is 1,000,000 frames deep on a degenerate one, and the shape of the tree is often decided by whoever supplies the input — sorted identifiers, a chain of replies, a JSON document nested by a script. Any recursion whose depth is bounded by input size rather than by log n should either be iterative or have an explicit depth limit that returns an error. This is the same class of bug as unbounded memory, and it is exploited the same way.
