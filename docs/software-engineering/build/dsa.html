Part one

What a cost actually costs

Before any structure or any algorithm: three ideas that decide whether the rest of this page helps you or misleads you. What the notation promises and what it quietly refuses to promise. Why two O(n) loops can differ by two orders of magnitude. And why the memory an algorithm uses is usually the constraint that bites first.

DSA · 01

What the notation is hiding

Big-O is a statement about the shape of the curve as the input grows without bound. It is not a statement about speed, it deliberately discards the constant factor, and it says nothing at all about the size of input you actually have. Every one of those omissions is load-bearing.

NotationWhat it claimsWhat people wrongly assume
O(f) upper boundBeyond some n, the cost is at most c·f(n) for some constant cThat it is tight. O(n²) is a true statement about binary search. Useless, but true.
Θ(f) tight boundThe cost is squeezed between two constant multiples of f(n)This is what people usually mean when they say “O”, and it is the honest thing to state.
Ω(f) lower boundThe cost is at least c·f(n)That it describes an algorithm. Its best use is describing a problem: comparison sorting is Ω(n log n) no matter who writes it.
AmortisedAveraged over a sequence, with no probability involvedThat it is the average case. It is a worst-case guarantee about totals: any n appends to a doubling array cost O(n) between them, always.
Average caseExpected cost over a distribution of inputsThat the distribution is the one you have. Quicksort’s O(n log n) average assumes random pivots; sorted input with a naive pivot gives O(n²).
Worst caseThe cost when an adversary picks the inputThat it is paranoid. If the input comes over HTTP, the adversary is real: hash flooding was a live denial-of-service class for years.
L1 · Beginner

Read the loops

  • Count nested iterations. Two loops over the same n, one inside the other, is O(n²). Sequential loops add, so they stay O(n).
  • Halving is a logarithm. Anything that discards half the remaining work each step is O(log n).
  • Drop constants and lower terms. 3n + 200 is O(n); n² + n is O(n²).
  • Know the ladder by heart: constant, log, linear, n log n, quadratic, exponential.
L2 · Intermediate

Analyse what is actually there

  • The hidden cost of a line. s = s + x in a loop is quadratic in most languages; list.insert(0, x) is O(n) each time; slicing copies.
  • Amortised vs worst case. A hash insert is O(1) amortised, but the one that triggers the resize is O(n). If you have a latency budget, that tail is your problem.
  • Recursion by the recurrence. T(n) = 2T(n/2) + O(n) is n log n — that single line explains merge sort, quicksort and most divide-and-conquer.
  • Two variables mean two symbols: graph work is O(V + E), not “O(n)”.
L3 · Advanced

Know when the model breaks

  • The constant wins below a threshold. Every industrial sort falls back to insertion sort under about 12–32 elements, because n² with a tiny constant beats n log n with a large one.
  • The model assumes uniform memory. It is wrong by two orders of magnitude, which the next section is about.
  • Adversarial inputs change the class. Randomised pivots and seeded hashes are not paranoia; they are what makes the average case an honest claim.
  • Measure before and after. An analysis tells you which line to be on; only a benchmark tells you where you are on it.

The threshold matters more than the exponent

All three benchmarks above tell the same story, and it is not “hash sets are faster”. At sixteen elements a linear scan of a contiguous array beats a hash lookup, because it is one cache line and no hashing. At sixty-five thousand it loses by three orders of magnitude. The asymptotic argument tells you these lines must cross; only measurement tells you where, and the answer for your data on your hardware is the number your design should turn on. Knowing that slices.Contains is O(n) is the beginning of the analysis, not the end of it.

DSA · 02

The machine the analysis ignores

Complexity analysis counts operations and charges the same price for each. Real hardware charges by where the data is, and the spread between the cheapest and the dearest answer is roughly a factor of a hundred. Two structures with identical O(n) traversals can differ by that much, and nothing in the notation will warn you.

Cache line64 bytes. The smallest unit memory will move. Reading one byte costs the same as reading all sixty-four, so layout decides how much of that you waste.
PrefetcherPredicts strides. Sequential and fixed-stride access are effectively free after the first miss. Pointer chasing defeats it completely.
Branch predictor~95% accurate, ~15 cycles to be wrong. A comparison sort over random data mispredicts constantly, which is why branchless partitioning is a real optimisation.
AllocationNot free, and not counted. One node per element means one allocation, one header and one pointer of overhead each — before the cache misses.

DSA · 03

Space, and the stack nobody counted

Every algorithm has a space complexity as well as a time complexity, and in production it is usually the one that fails first — because running out of memory is an incident, while being slow is a ticket. Recursion depth is space. It is the space most often left out of the analysis.

AlgorithmExtra spaceWhat that means in practice
Insertion / selection sortO(1)Truly in place. This is one reason they survive as the base case of better sorts.
HeapsortO(1)In place and O(n log n) worst case — the only common sort that is both. It loses on cache behaviour, which is why it is rarely the default.
QuicksortO(log n)Stack, not heap — but only if you recurse into the smaller side and loop on the larger. Recurse naively and the worst case is O(n) stack frames.
Merge sortO(n)The buffer is the price of stability and of predictable worst-case time. On linked lists it drops to O(log n), because merging needs no buffer.
BFS on a graphO(V)The frontier can be the whole width of the graph. On a wide, shallow graph BFS is the memory hog and DFS is cheap; on a deep one it is the reverse.
Recursive DFSO(depth)A stack frame per level. A million-node path graph will overflow the stack in every language on this page unless you make the traversal iterative.
Memoised DPO(states)The table is the algorithm. When the table does not fit, the fix is usually to keep only the rows the recurrence still needs.
 
// stack.go — Go grows goroutine stacks on demand (2 KB start, up to
// 1 GB by default), so deep recursion usually *works* and then abruptly
// does not, with "goroutine stack exceeds limit" and no recovery.

func SumRec(n *Node) int64 {                     // O(depth) stack
    if n == nil {
        return 0
    }
    return n.Value + SumRec(n.Next)              // not a tail call: Go has none
}

// The iterative form is the same algorithm with the frames deleted.
func SumIter(n *Node) int64 {                    // O(1) stack
    var total int64
    for ; n != nil; n = n.Next {
        total += n.Value
    }
    return total
}

// For trees, where iteration is genuinely less clear, carry your own
// stack. It is a slice, it costs one allocation, and it cannot overflow
// before the heap does.
func InOrder(root *TreeNode, visit func(int)) {
    stack := make([]*TreeNode, 0, 32)
    for cur := root; cur != nil || len(stack) > 0; {
        for ; cur != nil; cur = cur.Left {
            stack = append(stack, cur)           // walk left, remembering
        }
        cur = stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        visit(cur.Val)
        cur = cur.Right
    }
}

import sys

sys.getrecursionlimit()                          # 1000 by default

def in_order_recursive(node, out):               # O(depth) frames
    if node is None:
        return
    in_order_recursive(node.left, out)
    out.append(node.val)
    in_order_recursive(node.right, out)

def in_order(root):                              # O(depth) list, no frames
    out, stack, cur = [], [], root
    while cur is not None or stack:
        while cur is not None:                   # walk left, remembering
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        out.append(cur.val)
        cur = cur.right
    return out

// Stack.java — the JVM gives each thread a fixed stack, default about
// 512 KB to 1 MB. Deep recursion throws StackOverflowError, which is an
// Error, not an Exception: do not catch it and carry on.

// -Xss4m raises it per thread. That is a workaround with a cost:
// thousands of threads at 4 MB of reserved stack each adds up fast.

void inOrderRecursive(TreeNode node, List<Integer> out) {   // O(depth) frames
    if (node == null) return;
    inOrderRecursive(node.left, out);
    out.add(node.val);
    inOrderRecursive(node.right, out);
}

List<Integer> inOrder(TreeNode root) {                      // O(depth) heap
    List<Integer> out = new ArrayList<>();
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !stack.isEmpty()) {
        while (cur != null) {                                // walk left, remembering
            stack.push(cur);
            cur = cur.left;
        }
        cur = stack.pop();
        out.add(cur.val);
        cur = cur.right;
    }
    return out;
}

Depth is data-dependent, and data is adversarial

A recursive traversal that is 20 frames deep on your test tree is 1,000,000 frames deep on a degenerate one, and the shape of the tree is often decided by whoever supplies the input — sorted identifiers, a chain of replies, a JSON document nested by a script. Any recursion whose depth is bounded by input size rather than by log n should either be iterative or have an explicit depth limit that returns an error. This is the same class of bug as unbounded memory, and it is exploited the same way.

Part two

The linear structures

Four structures carry the overwhelming majority of production code: the growable array, the linked list, the stack-or-queue, and the hash table. Everything later in this page is built out of them. What matters is not their interfaces — those you know — but what each one is doing to memory when you use it, and the one operation each is quietly bad at.

DSA · 04

The growable array, and why appending is free

A Go slice, a Python list and a Java ArrayList are the same idea: a fixed block of memory, a length, and a capacity. Appending past the capacity allocates a bigger block and copies. The reason that is not a disaster — the reason append is O(1) rather than O(n) — is one of the most useful arguments in the subject.

OperationCostThe reason, and the trap
IndexO(1)One multiply and one add. Nothing else in this page is this cheap.
AppendO(1) amortisedThe individual append that reallocates is O(n). If you have a tail-latency budget, preallocate.
Insert or delete at the frontO(n)Every later element shifts. In a loop this is the classic accidental O(n²) — use a deque, or append and reverse at the end.
Delete in the middle, order keptO(n)Same shift. If order does not matter, swap the last element into the hole: O(1).
Search, unsortedO(n)But with the best constant of any O(n) in existence, so it beats a hash set well past the size you would guess.
Search, sortedO(log n)Binary search. Keeping an array sorted costs O(n) per insert, which is only worth it when reads dominate heavily.
Grow past capacityO(n), rarelyGo doubles under 256 elements then grows by roughly 1.25×; Java’s ArrayList uses 1.5×; CPython uses about 1.125× plus a constant. All multiplicative, all amortised O(1).

The remove-in-a-loop quadratic

Deleting k elements one at a time from an array-backed list costs O(nk), because each delete shifts the tail. Deleting them in a single filtering pass costs O(n). Go has slices.DeleteFunc, Python has a comprehension, Java has removeIf; all three do the same thing, which is to write the survivors forwards over the original in one sweep. Whenever you find yourself removing inside a loop, you are choosing an algorithm, and it is the worse one.

DSA · 05

Linked lists: rarely the answer, always the exam question

A linked list buys O(1) insertion and removal at a position you already hold, and pays with a pointer per element, an allocation per element, and a cache miss per hop. That trade almost never wins in application code. It wins decisively in three specific places, and those are worth knowing precisely.

Where it winsIntrusive lists in allocators and kernels. The node is part of the object, so there is no extra allocation, and O(1) unlink from a pointer you already have is exactly the operation needed.
Where it winsLRU caches. A hash map to nodes plus a doubly linked list gives O(1) lookup and O(1) move-to-front. No array can do the second one.
Where it winsLock-free queues. A single atomic pointer swap publishes a node. Growable arrays cannot be resized without coordination.
Where it losesEverywhere else. Iteration, search, sorting, memory use and cache behaviour are all worse, and “O(1) insert” is a lie if finding the position is O(n).
// list.go — the two techniques worth memorising, both of them pointer
// discipline rather than cleverness.

type Node struct {
    Val  int
    Next *Node
}

// 1. Reverse in place. Three pointers, one pass, no allocation.
func Reverse(head *Node) *Node {
    var prev *Node
    for cur := head; cur != nil; {
        next := cur.Next                         // remember before clobbering
        cur.Next = prev                          // flip
        prev, cur = cur, next                    // advance both
    }
    return prev                                  // prev is the old tail
}

// 2. Floyd's cycle detection. Fast moves two, slow moves one; if there
// is a loop they must meet inside it, in O(n) time and O(1) space.
// Restarting one pointer at the head then advancing both one step at a
// time lands them on the entry to the cycle -- that part is not obvious,
// and it falls out of the arithmetic of where they met.
func CycleStart(head *Node) *Node {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow, fast = slow.Next, fast.Next.Next
        if slow == fast {                        // a cycle exists
            for p := head; p != slow; p, slow = p.Next, slow.Next {
            }
            return slow                          // the node the loop enters at
        }
    }
    return nil
}

// A dummy head node removes every "is this the first element" branch
// from insert and delete. Use one; the code halves in size.
# linked.py — you will almost never write one of these in Python, but
# the two techniques generalise to every sequence you cannot index.
from dataclasses import dataclass
from typing import Optional

@dataclass
class Node:
    val: int
    next: Optional["Node"] = None

def reverse(head: Optional[Node]) -> Optional[Node]:
    prev = None
    while head is not None:
        head.next, prev, head = prev, head, head.next   # one line, one pass
    return prev

def cycle_start(head: Optional[Node]) -> Optional[Node]:
    slow = fast = head

A stack is last-in-first-out, a queue is first-in-first-out, and a deque is both. All three are interfaces, not structures: the good implementations of all of them are arrays. What makes a queue an array rather than a list is one idea — move the head index instead of moving the elements.

// Queue: the naive version leaks. `q = q[1:]` advances the pointer but
// keeps the whole backing array alive, so a long-running queue grows
// without bound even at constant depth.
type Ring[T any] struct {
    buf        []T
    head, tail int
    n          int
}

func NewRing[T any](cap int) *Ring[T] { return &Ring[T]{buf: make([]T, cap)} }

func (r *Ring[T]) Push(v T) bool {
    if r.n == len(r.buf) {
        return false                             // full: caller decides — block,
    }                                            // drop, or grow
    r.buf[r.tail] = v
    r.tail = (r.tail + 1) % len(r.buf)
    r.n++
    return true
}

func (r *Ring[T]) Pop() (T, bool) {
    var zero T
    if r.n == 0 {
        return zero, false
    }
    v := r.buf[r.head]
    r.buf[r.head] = zero                         // release the reference, or the
    r.head = (r.head + 1) % len(r.buf)           // GC keeps the popped object
    r.n--
    return v, true
}

def window_max(nums: list[int], k: int) -> list[int]:
    """Maximum of every window of size k, in O(n) total.

    The deque holds *indices* whose values are strictly decreasing, so
    the front is always the current maximum. Each index enters once and
    leaves once, which is where the linear bound comes from.
    """
    dq: deque[int] = deque()
    out = []
    for i, v in enumerate(nums):
        while dq and dq[0] <= i - k:             # front fell out of the window
            dq.popleft()
        while dq and nums[dq[-1]] <= v:          # everything smaller is dead:
            dq.pop()                             # v is newer AND bigger
        dq.append(i)
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out

int[] windowMax(int[] nums, int k) {             // O(n), monotonic deque
    int[] out = new int[nums.length - k + 1];
    Deque<Integer> dq = new ArrayDeque<>();      // holds indices, values decreasing
    for (int i = 0; i < nums.length; i++) {

        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) dq.pollLast();
        dq.addLast(i);
        if (i >= k - 1) out[i - k + 1] = nums[dq.peekFirst()];
    }
    return out;
}

Binary trees, and the four orders you can walk them in

A binary tree is a node with up to two children. Everything interesting about it comes from the order in which you visit the nodes — and the three recursive orders differ by one line moving, which is the clearest illustration in the subject that an algorithm is a sequence, not a shape.

Pre-orderRoot, left, right. Serialising a tree, copying it, or any task where the parent must be handled before its children — rendering nested UI, applying inherited permissions.
In-orderLeft, root, right. On a binary search tree this yields sorted order, which is the property every sorted map is built on.
Post-orderLeft, right, root. Freeing, computing a value from children (subtree sizes, directory sizes), and evaluating an expression tree.
Level-orderBy depth, using a queue. Finding the shallowest anything, printing a tree by rows, and any “fewest steps” question.

    Val         int
    Left, Right *TreeNode

func Walk(n *TreeNode, visit func(int)) {
    if n == nil {
        return
    }
    // visit(n.Val)          <- pre-order goes here
    Walk(n.Left, visit)
    visit(n.Val)                                 // in-order
    Walk(n.Right, visit)
    // visit(n.Val)          <- post-order goes here

// Level order: a queue, and one loop per level so you know where the
// rows break. That inner "for range len(q)" is the whole trick.
func Levels(root *TreeNode) [][]int {
    if root == nil {
        return nil
    }
    var out [][]int
    q := []*TreeNode{root}
    for len(q) > 0 {
        row := make([]int, 0, len(q))
        next := make([]*TreeNode, 0, len(q)*2)
        for _, n := range q {                    // exactly one level
            row = append(row, n.Val)
            if n.Left != nil {
                next = append(next, n.Left)
            }
            if n.Right != nil {
                next = append(next, n.Right)
            }
        }
        out, q = append(out, row), next
    }
    return out
}

// Height is post-order: you cannot know yours until both children know
// theirs. Almost every "compute something about a subtree" is this shape.
func Height(n *TreeNode) int {
    if n == nil {
        return 0
    }
    return 1 + max(Height(n.Left), Height(n.Right))
}

    if (t instanceof Branch b) {
        inOrder(b.left(), visit);
        visit.accept(b.val());                   // move for pre/post order
        inOrder(b.right(), visit);
    }
}

Why databases use B-trees and not binary trees

A balanced binary tree over a billion keys is thirty levels deep, and if the tree is on disk that is thirty random reads — roughly a millisecond and a half at NVMe latencies, several hundred milliseconds on a spinning disk. A B-tree stores hundreds of keys per node, sized to a page, so the same billion keys are four levels deep and a lookup is four reads. The asymptotics are identical (both are O(log n); only the base of the logarithm changed) and the practical difference is a factor of eight. This is the memory hierarchy from part one deciding a data structure outright, and it is why every database index is a B-tree or an LSM tree.

Heaps: the structure that only answers one question

A binary heap gives you the minimum (or maximum) in O(1) and lets you remove it or add a new element in O(log n). It cannot search, it cannot iterate in order, and it has no notion of position — and by giving all that up it becomes a plain array with no pointers at all.

Top-kKeep a heap of size k holding the best k so far, and push-then-pop for each new element. O(n log k) time and O(k) space, over a stream you cannot store.
Merging sorted runsOne heap entry per run. Pop the smallest, emit it, push that run’s next value. This is how external sorts and LSM compaction work.
Schedulers and timersKeyed by deadline. The next thing to do is always the root, and inserting a new timer is O(log n).
Dijkstra and A*Keyed by distance. The priority queue is what turns the search from “try everything” into “always expand the cheapest frontier node”.

Tries: when the key has structure worth sharing

A hash map treats a key as an opaque blob to be digested. A trie treats it as a path, one edge per character, so that every key sharing a prefix shares the nodes for it. That buys three things a hash cannot offer at any price: prefix search, ordered iteration, and lookup time that depends on the key length rather than on how many keys there are.

// trie.go — autocomplete, routing tables and dictionary lookups.
// A map per node keeps it simple; a [26]*Node array is faster and only
// works for a known alphabet.

type Trie struct {
    kids map[rune]*Trie
    term bool                                    // a word ends here
}

func New() *Trie { return &Trie{kids: map[rune]*Trie{}} }

func (t *Trie) Insert(word string) {             // O(len(word))
    node := t
    for _, r := range word {
        next, ok := node.kids[r]
        if !ok {
            next = New()
            node.kids[r] = next
        }
        node = next
    }
    node.term = true
}

    node := t

// sorted order, in time proportional to the OUTPUT rather than to the
// number of keys stored.

    if start == nil {

// Trie.java — a HashMap per node is the readable version; an array of

final class Trie {
    private final Map<Character, Trie> kids = new TreeMap<>();   // sorted kids
    private boolean terminal;

    void insert(String word) {                   // O(word.length())
        Trie node = this;
        for (char c : word.toCharArray()) {
            node = node.kids.computeIfAbsent(c, k -> new Trie());
        }
        node.terminal = true;
    }

    private Trie descend(String prefix) {
        Trie node = this;
        for (char c : prefix.toCharArray()) {
            node = node.kids.get(c);
            if (node == null) return null;
        }
        return node;
    }

    List<String> withPrefix(String prefix, int limit) {
        Trie start = descend(prefix);
        List<String> out = new ArrayList<>();
        if (start != null) collect(start, new StringBuilder(prefix), out, limit);
        return out;
    }

    private static void collect(Trie n, StringBuilder acc, List<String> out, int limit) {
        if (out.size() >= limit) return;
        if (n.terminal) out.add(acc.toString());
        for (var e : n.kids.entrySet()) {        // TreeMap: sorted
            acc.append(e.getKey());
            collect(e.getValue(), acc, out, limit);
            acc.deleteCharAt(acc.length() - 1);  // backtrack, no copying
        }
    }

Disjoint sets: forty lines that answer “are these connected?”

Union-find maintains a partition of n elements under two operations: merge two groups, and ask which group something is in. With both of its optimisations it runs in near-constant amortised time — and it is the smallest piece of code on this page with a genuinely surprising complexity proof.

// dsu.go — two int slices, twenty lines, and it is used by Kruskal's
// MST, connected components, image segmentation and cycle detection in
// undirected graphs.

type DSU struct {
    parent []int
    size   []int
    groups int
}

func NewDSU(n int) *DSU {
    d := &DSU{parent: make([]int, n), size: make([]int, n), groups: n}
    for i := range d.parent {
        d.parent[i], d.size[i] = i, 1            // everyone is their own root
    }
    return d
}

// Path halving: point every other node at its grandparent. One pass,
// no recursion, and asymptotically as good as full compression.
func (d *DSU) Find(x int) int {
    for d.parent[x] != x {
        d.parent[x] = d.parent[d.parent[x]]
        x = d.parent[x]
    }
    return x
}

// Union by size. Returns false if they were already together, which is
// exactly the cycle test Kruskal needs.
func (d *DSU) Union(a, b int) bool {
    ra, rb := d.Find(a), d.Find(b)
    if ra == rb {
        return false
    }
    if d.size[ra] < d.size[rb] {
        ra, rb = rb, ra                          // smaller hangs under larger
    }
    d.parent[rb] = ra
    d.size[ra] += d.size[rb]
    d.groups--
    return true
}

# dsu.py — the same twenty lines. The classic use is counting connected
# components in one pass over the edges, with no graph built at all.

class DSU:
    def __init__(self, n: int) -> None:
        self.parent = list(range(n))
        self.size = [1] * n
        self.groups = n

    def find(self, x: int) -> int:
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a: int, b: int) -> bool:
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                         # already connected -> a cycle
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        self.groups -= 1
        return True

final class Dsu {
    private final int[] parent;
    private final int[] size;
    private int groups;

    Dsu(int n) {
        parent = new int[n];
        size = new int[n];
        groups = n;
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }
    }

    int find(int x) {                            // iterative: no stack depth
        while (parent[x] != x) {
            parent[x] = parent[parent[x]];       // path halving
            x = parent[x];
        }
        return x;
    }

    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;
        size[ra] += size[rb];
        groups--;
        return true;
    }

    int groups() { return groups; }
    boolean connected(int a, int b) { return find(a) == find(b); }
}

Stability is a correctness property, not a nicety

A stable sort keeps equal elements in their original relative order. That is what lets you sort by one field, then by another, and end up with a result ordered by both — sort by name, then by department, and each department’s names are still alphabetical. With an unstable sort the second pass scrambles the first, and the bug shows up as “the list is mostly right”, which is the hardest kind to notice. Python’s sort is stable, Java’s Collections.sort and Arrays.sort on objects are stable, Go’s sort.Slice and slices.Sort are not — Go makes you ask for slices.SortStableFunc.

// The merge is the algorithm. Note `<=`: taking from the left on a tie
// is exactly what makes the sort stable. `<` would not.
func merge(a, b []int) []int {
    out := make([]int, 0, len(a)+len(b))
    i, j := 0, 0
    for i < len(a) && j < len(b) {
        if a[i] <= b[j] {
            out, i = append(out, a[i]), i+1
        } else {
            out, j = append(out, b[j]), j+1
        }
    }
    return append(append(out, a[i:]...), b[j:]...)
}

// Quicksort's partition, for contrast: no buffer, and the whole cost is
// in choosing the pivot. Median-of-three on the first, middle and last
// element turns "sorted input is O(n^2)" into "you would have to try".
func partition(xs []int, lo, hi int) int {
    mid := lo + (hi-lo)/2
    if xs[mid] < xs[lo] { xs[mid], xs[lo] = xs[lo], xs[mid] }
    if xs[hi] < xs[lo]  { xs[hi], xs[lo] = xs[lo], xs[hi] }
    if xs[hi] < xs[mid] { xs[hi], xs[mid] = xs[mid], xs[hi] }
    pivot := xs[mid]
    i, j := lo, hi
    for i <= j {
        for xs[i] < pivot { i++ }
        for xs[j] > pivot { j-- }
        if i <= j {
            xs[i], xs[j] = xs[j], xs[i]
            i, j = i+1, j-1
        }
    }
    return i
}

def merge_sort(xs: list[int]) -> list[int]:
    if len(xs) < 2:
        return xs
    mid = len(xs) // 2
    left, right = merge_sort(xs[:mid]), merge_sort(xs[mid:])

    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:                  # `<=` is what makes it stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1

    return out

# Three-way (Dutch national flag) partitioning: the fix for quicksort on
# data with many duplicates. Everything equal to the pivot ends up in
# the middle and is never looked at again, so an array of one repeated
# value goes from O(n^2) to O(n).
def quicksort(xs: list[int]) -> list[int]:
    if len(xs) < 2:
        return xs
    pivot = xs[len(xs) // 2]
    lt = [x for x in xs if x < pivot]
    eq = [x for x in xs if x == pivot]
    gt = [x for x in xs if x > pivot]
    return quicksort(lt) + eq + quicksort(gt)

# Counting sort: no comparisons, so the n log n bound simply does not
# apply. O(n + k) for keys in a small known range -- ages, HTTP status
# codes, bucket indices, anything with a few thousand distinct values.
def counting_sort(xs: list[int], k: int) -> list[int]:
    counts = [0] * k
    for x in xs:
        counts[x] += 1
    return [v for v, c in enumerate(counts) for _ in range(c)]

// select.go — quickselect is quicksort that throws away half the work.
// After partitioning, the pivot is in its final position; if that is
// past k, only the left side can contain the answer.

func QuickSelect(xs []int, k int) int {          // the k-th smallest, 0-based
    lo, hi := 0, len(xs)-1
    for lo < hi {
        p := partition(xs, lo, hi)               // same partition as quicksort
        switch {
        case p == k:
            return xs[k]
        case p < k:
            lo = p + 1                           // answer is to the right
        default:
            hi = p - 1                           // answer is to the left
        }
    }
    return xs[k]
}

// Why it is O(n): each pass halves the remaining range on average, so

func TopK(stream iter.Seq[Score], k int) []Score {

            heap.Push(h, s)

    }
    return out
}

def quickselect(xs: list[int], k: int) -> int:
    """k-th smallest, 0-based. Randomised pivot, so sorted input is fine."""
    while True:
        if len(xs) == 1:
            return xs[0]
        pivot = random.choice(xs)                # randomised: no adversarial case
        lt = [x for x in xs if x < pivot]
        eq = [x for x in xs if x == pivot]
        if k < len(lt):
            xs = lt                              # recurse left only
        elif k < len(lt) + len(eq):
            return pivot                         # the pivot IS the answer
        else:
            k -= len(lt) + len(eq)               # recurse right, reindexed
            xs = [x for x in xs if x > pivot]

// Select.java — the bounded-heap version, which is the one you will

static List<Score> topK(Stream<Score> stream, int k) {

            new PriorityQueue<>(k, Comparator.comparingInt(Score::value));

}

The four searches, and how little separates them

Breadth-first, depth-first, Dijkstra and A* are the same loop. Take a node from a collection of frontier nodes, mark it seen, add its unseen neighbours. The only difference is which node the collection hands back — the oldest, the newest, the cheapest, or the cheapest-plus-a-guess — and that single choice changes everything about the search.

SearchFrontierCostWhat it guarantees
Breadth-firstQueue — oldest firstO(V + E)Fewest edges. Correct only when every edge costs the same, which is the case people forget.
Depth-firstStack — newest firstO(V + E)Nothing about distance. It gives you reachability, cycle detection, topological order and articulation points.
DijkstraMin-heap by distanceO((V + E) log V)Cheapest path, for non-negative weights. A negative edge breaks it outright — the “already finalised” assumption fails.
A*Min-heap by distance + heuristicO((V + E) log V)Cheapest path, if the heuristic never overestimates. With a zero heuristic it is Dijkstra.
Bellman–FordNo frontier — V−1 passes over all edgesO(V·E)Handles negative weights, and detects a negative cycle. The currency-arbitrage algorithm.
Floyd–WarshallNone — a V×V matrixO(V³)Every pair at once. Only sane below a few hundred nodes, where its tiny constant beats V runs of Dijkstra.

// algorithm with two frontiers.

// BFS: shortest path in EDGES. The queue is what makes it correct --
// nodes come out in non-decreasing distance order.
func BFS(g *Graph, src int32) []int32 {
    dist := make([]int32, len(g.adj))
    for i := range dist {
        dist[i] = -1
    }
    dist[src] = 0
    q := []int32{src}
    for len(q) > 0 {
        u := q[0]
        q = q[1:]
        for _, v := range g.adj[u] {
            if dist[v] == -1 {                   // mark on ENQUEUE, not on
                dist[v] = dist[u] + 1            // dequeue, or a node can be
                q = append(q, v)                 // queued twice
            }
        }
    }
    return dist
}

// Dijkstra: same shape, heap instead of queue. The "lazy deletion"
// variant pushes duplicates and skips stale ones on the way out, which
// avoids needing decrease-key and is what nearly everyone ships.
func Dijkstra(g [][]Edge, src int32) []int64 {
    const inf = math.MaxInt64
    dist := make([]int64, len(g))
    for i := range dist {
        dist[i] = inf
    }
    dist[src] = 0

    pq := &NodeHeap{{Node: src, Dist: 0}}
    for pq.Len() > 0 {
        cur := heap.Pop(pq).(NodeDist)
        if cur.Dist > dist[cur.Node] {
            continue                             // stale entry: already improved
        }
        for _, e := range g[cur.Node] {
            if nd := cur.Dist + int64(e.Weight); nd < dist[e.To] {
                dist[e.To] = nd
                heap.Push(pq, NodeDist{Node: e.To, Dist: nd})
            }
        }
    }
    return dist
}

import heapq
from collections import deque

def bfs(graph, src):
    """Fewest EDGES from src. Only correct when all edges cost the same."""
    dist = {src: 0}
    q = deque([src])
    while q:
        u = q.popleft()
        for v in graph.get(u, ()):
            if v not in dist:                    # mark on enqueue
                dist[v] = dist[u] + 1
                q.append(v)
    return dist

def dijkstra(graph, src):
    """Cheapest path. Non-negative weights only."""
    dist = {src: 0}
    pq = [(0, src)]                              # (distance, node) -- tuples compare
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist.get(u, float("inf")):
            continue                             # stale duplicate: skip it
        for v, w in graph.get(u, ()):
            nd = d + w
            if nd < dist.get(v, float("inf")):
                dist[v] = nd
                heapq.heappush(pq, (nd, v))
    return dist

Topological order and cycles: the build-system algorithm

Given tasks with dependencies, produce an order in which each task comes after everything it needs. This is what a build system, a migration runner, a package manager and a scheduler all do, and the same algorithm that produces the order also proves that no order exists — because there is a cycle.

// topo.go — Kahn's algorithm, with the cycle report as a first-class
// result rather than a boolean.

func TopoSort(n int, deps [][]int32) ([]int32, error) {
    indeg := make([]int32, n)
    for _, vs := range deps {                    // deps[u] = things that need u
        for _, v := range vs {
            indeg[v]++
        }
    }

    ready := make([]int32, 0, n)
    for i, d := range indeg {
        if d == 0 {
            ready = append(ready, int32(i))
        }
    }

    order := make([]int32, 0, n)
    for len(ready) > 0 {
        // Everything in `ready` right now is independent: a build system
        // runs this whole slice in parallel and then re-fills it.
        u := ready[len(ready)-1]
        ready = ready[:len(ready)-1]
        order = append(order, u)
        for _, v := range deps[u] {
            if indeg[v]--; indeg[v] == 0 {
                ready = append(ready, v)
            }
        }
    }

    if len(order) != n {
        stuck := make([]int32, 0, n-len(order))
        for i, d := range indeg {
            if d > 0 {
                stuck = append(stuck, int32(i))  // in, or downstream of, a cycle
            }
        }
        return nil, fmt.Errorf("dependency cycle involving %v", stuck)
    }
    return order, nil
}

# Cycle detection by hand, when you want the cycle itself. Three
# colours: 0 unvisited, 1 on the current path, 2 finished. An edge to a
# colour-1 node is a back edge, and the stack above it is the cycle.
def find_cycle(graph):
    colour, stack = {}, []

    def visit(u):
        colour[u] = 1
        stack.append(u)
        for v in graph.get(u, ()):
            if colour.get(v) == 1:               # back edge
                return stack[stack.index(v):] + [v]
            if colour.get(v, 0) == 0:
                if (found := visit(v)):
                    return found
        colour[u] = 2
        stack.pop()
        return None

    return next((c for u in graph if colour.get(u, 0) == 0 and (c := visit(u))), None)

static List<List<Integer>> waves(int n, List<List<Integer>> dependents) {
    int[] indeg = new int[n];

        for (int v : vs) indeg[v]++;

    int emitted = 0;

            wave.add(u);

Minimum spanning trees, and where union-find comes back

Connect every node using the least total edge weight. Two algorithms solve it, both greedy, and both correct for the same reason — the cut property, which says that the lightest edge crossing any division of the nodes into two groups must belong to some minimum spanning tree.

KruskalSort all edges, keep any that joins two different components. O(E log E), and the component test is exactly union-find. Best when the graph is sparse or the edges already arrive sorted.
PrimGrow one tree, always taking the cheapest edge leaving it. O(E log V) with a heap — structurally identical to Dijkstra, keyed by edge weight instead of path length. Best when the graph is dense.
Where it is usedNetwork and circuit layout, clustering (cut the k−1 heaviest edges of the MST and you have k clusters), image segmentation, and approximating the travelling salesman within a factor of two.
What it is notNot shortest paths. The MST minimises total weight over the whole tree; the path between two nodes within it can be far worse than their shortest path.

    }

import heapq

def prim(graph: dict[int, list[tuple[int, int]]], start: int = 0):
    """Minimum spanning tree by growing one component.

    Compare with dijkstra() above: the ONLY difference is that the heap
    key is the edge weight `w` rather than the accumulated `d + w`.
    Dijkstra minimises distance from the source; Prim minimises the cost
    of attaching one more node to the tree.
    """
    seen = {start}
    pq = [(w, start, v) for v, w in graph[start]]
    heapq.heapify(pq)
    tree, total = [], 0

    while pq and len(seen) < len(graph):
        w, u, v = heapq.heappop(pq)
        if v in seen:
            continue                             # stale: v joined another way
        seen.add(v)
        tree.append((u, v, w))
        total += w
        for nxt, nw in graph[v]:
            if nxt not in seen:
                heapq.heappush(pq, (nw, v, nxt))

    return tree, total

# Kruskal in Python, using the DSU from part three:
def kruskal(n: int, edges: list[tuple[int, int, int]]):
    dsu = DSU(n)
    tree, total = [], 0
    for u, v, w in sorted(edges, key=lambda e: e[2]):
        if dsu.union(u, v):                      # False means it closes a cycle
            tree.append((u, v, w))
            total += w
    return tree, total

record WEdge(int u, int v, long weight) {}

static List<WEdge> kruskal(int n, List<WEdge> edges) {
    List<WEdge> sorted = new ArrayList<>(edges);
    sorted.sort(Comparator.comparingLong(WEdge::weight));

    Dsu dsu = new Dsu(n);
    List<WEdge> tree = new ArrayList<>(n - 1);
    for (WEdge e : sorted) {
        if (dsu.union(e.u(), e.v())) {           // false: both ends already joined
            tree.add(e);
            if (tree.size() == n - 1) break;
        }
    }
    return tree;                                 // size < n-1 => disconnected graph
}

Part six

Recursion and dynamic programming

Dynamic programming has a reputation for being hard that it does not deserve. It is one idea — a recursive definition whose subproblems repeat, computed once each instead of once per occurrence — and the difficulty is never the technique. It is finding the recurrence, and that is a matter of naming the state precisely enough that the answer for a state depends only on smaller states.

From exponential recursion to a table, in three steps

Every dynamic program starts as an honest recursive definition that is unusably slow, because it recomputes the same subproblem an exponential number of times. Memoising it is a mechanical change that fixes the complexity without touching the logic. Turning it into a loop is a second, also mechanical, change that removes the stack.

// Step 1: the honest recursion. O(2^n), and correct.
func coinsNaive(amount int, coins []int) int {
    if amount == 0 {
        return 0
    }
    best := math.MaxInt
    for _, c := range coins {
        if c <= amount {
            if sub := coinsNaive(amount-c, coins); sub != math.MaxInt {
                best = min(best, sub+1)
            }
        }
    }
    return best
}

// Step 2: memoise. The state is a single int, so the cache is a slice.
// O(amount * len(coins)).
func coinsMemo(amount int, coins []int) int {
    memo := make([]int, amount+1)
    for i := range memo {
        memo[i] = -1                             // -1 = not computed yet
    }
    var solve func(int) int
    solve = func(a int) int {
        if a == 0 {
            return 0
        }
        if memo[a] != -1 {
            return memo[a]
        }
        best := math.MaxInt
        for _, c := range coins {
            if c <= a {
                if sub := solve(a - c); sub != math.MaxInt {
                    best = min(best, sub+1)
                }
            }
        }
        memo[a] = best
        return best
    }
    return solve(amount)
}

// Step 3: bottom-up. Same complexity, no recursion, no stack, and the
// loop order IS the dependency order -- every a-c is smaller than a.
func coins(amount int, cs []int) int {
    dp := make([]int, amount+1)
    for a := 1; a <= amount; a++ {
        dp[a] = math.MaxInt
        for _, c := range cs {
            if c <= a && dp[a-c] != math.MaxInt {
                dp[a] = min(dp[a], dp[a-c]+1)
            }
        }
    }
    return dp[amount]
}

def coins_which(amount: int, cs: list[int]) -> list[int] | None:
    dp = [0] + [None] * amount                   # dp[a] = coin used to reach a
    reach = [0] + [False] * amount
    for a in range(1, amount + 1):
        for c in cs:
            if c <= a and reach[a - c]:
                dp[a], reach[a] = c, True
                break
    if not reach[amount]:
        return None
    out = []
    while amount:                                # walk the choices backwards
        out.append(dp[amount])
        amount -= dp[amount]
    return out

static final int UNSET = -1, IMPOSSIBLE = Integer.MAX_VALUE;

// Step 2: top-down with an explicit cache.
static int coinsMemo(int amount, int[] coins, int[] memo) {
    if (amount == 0) return 0;
    if (memo[amount] != UNSET) return memo[amount];

    int best = IMPOSSIBLE;
    for (int c : coins) {
        if (c <= amount) {
            int sub = coinsMemo(amount - c, coins, memo);
            if (sub != IMPOSSIBLE) best = Math.min(best, sub + 1);
        }
    }
    return memo[amount] = best;
}

// Step 3: bottom-up. Prefer this in Java -- the default stack is around
// 512 KB and a recursion of depth 100,000 will not survive it.
static int coins(int amount, int[] cs) {
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, IMPOSSIBLE);
    dp[0] = 0;
    for (int a = 1; a <= amount; a++)
        for (int c : cs)
            if (c <= a && dp[a - c] != IMPOSSIBLE)
                dp[a] = Math.min(dp[a], dp[a - c] + 1);
    return dp[amount];
}

Two dimensions: the table, and reading the answer back out

// edit.go — the rolling-row version, which is what you ship when you
// only need the distance. Two rows instead of m*n.

func EditDistance(a, b string) int {
    ra, rb := []rune(a), []rune(b)               // runes: "café" is 4, not 5
    if len(ra) < len(rb) {
        ra, rb = rb, ra                          // keep the short side as the row
    }

    prev := make([]int, len(rb)+1)
    curr := make([]int, len(rb)+1)
    for j := range prev {
        prev[j] = j                              // turning "" into b[:j] costs j
    }

    for i := 1; i <= len(ra); i++ {
        curr[0] = i                              // turning a[:i] into "" costs i
        for j := 1; j <= len(rb); j++ {
            sub := prev[j-1]
            if ra[i-1] != rb[j-1] {
                sub++
            }
            curr[j] = min(
                prev[j]+1,                       // delete a[i-1]
                curr[j-1]+1,                     // insert b[j-1]
                sub,                             // substitute, or free on a match
            )
        }
        prev, curr = curr, prev                  // swap, do not allocate
    }
    return prev[len(rb)]
}

// match. That is what `diff` computes, then reads back as the edit script.
# edit.py — the full table, because the backtrace is the interesting
# half and the reason `diff` output looks the way it does.

def edit_table(a: str, b: str) -> list[list[int]]:
    n, m = len(a), len(b)
    dp = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(n + 1):
        dp[i][0] = i                             # delete everything
    for j in range(m + 1):
        dp[0][j] = j                             # insert everything
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            dp[i][j] = min(
                dp[i - 1][j] + 1,                # delete a[i-1]
                dp[i][j - 1] + 1,                # insert b[j-1]
                dp[i - 1][j - 1] + (a[i - 1] != b[j - 1]),   # substitute/match
            )
    return dp

def edit_script(a: str, b: str) -> list[str]:
    """Walk backwards from the corner, taking whichever choice produced it."""
    dp = edit_table(a, b)
    i, j, out = len(a), len(b), []
    while i > 0 or j > 0:
        if i > 0 and dp[i][j] == dp[i - 1][j] + 1:
            out.append(f"-{a[i - 1]}"); i -= 1
        elif j > 0 and dp[i][j] == dp[i][j - 1] + 1:
            out.append(f"+{b[j - 1]}"); j -= 1
        else:
            if a[i - 1] != b[j - 1]:
                out.append(f"~{a[i - 1]}{b[j - 1]}")
            i -= 1; j -= 1
    return out[::-1]

// Kadane: maximum sum of any contiguous run, in one pass. The state is
// "best run ENDING HERE", which either extends the previous run or
// starts fresh -- and that choice is the whole algorithm.
func MaxSubarray(xs []int) (best, lo, hi int) {
    best, cur, start := math.MinInt, 0, 0
    for i, v := range xs {
        if cur <= 0 {
            cur, start = v, i                    // the past is a liability: drop it
        } else {
            cur += v
        }
        if cur > best {
            best, lo, hi = cur, start, i
        }
    }
    return best, lo, hi
}

// Longest increasing subsequence in O(n log n). tails[k] holds the
// smallest possible tail of an increasing subsequence of length k+1;
// it is always sorted, so the position is a binary search.
func LIS(xs []int) int {
    tails := make([]int, 0, len(xs))
    for _, v := range xs {
        i, _ := slices.BinarySearch(tails, v)
        if i == len(tails) {
            tails = append(tails, v)             // v extends the longest run
        } else {
            tails[i] = v                         // v gives length i+1 a better tail
        }
    }
    return len(tails)                            // NOTE: the length, not the run
}

# classics.py — knapsack, and the space optimisation that catches
# people out.

def knapsack(weights: list[int], values: list[int], cap: int) -> int:
    """0/1 knapsack: each item may be taken at most once."""
    dp = [0] * (cap + 1)                         # dp[w] = best value within w
    for wt, val in zip(weights, values):
        # BACKWARDS. Forwards would let this item be picked twice,
        # because dp[w - wt] would already include it. That single
        # reversal is the difference between 0/1 and unbounded knapsack.
        for w in range(cap, wt - 1, -1):
            dp[w] = max(dp[w], dp[w - wt] + val)
    return dp[cap]

def unbounded_knapsack(weights, values, cap) -> int:
    dp = [0] * (cap + 1)
    for wt, val in zip(weights, values):
        for w in range(wt, cap + 1):             # forwards: reuse is allowed
            dp[w] = max(dp[w], dp[w - wt] + val)
    return dp[cap]

def lis_with_run(xs: list[int]) -> list[int]:
    """The actual subsequence, not just its length."""
    import bisect
    tails, tail_idx, prev = [], [], [-1] * len(xs)
    for i, v in enumerate(xs):
        k = bisect.bisect_left(tails, v)
        if k == len(tails):
            tails.append(v); tail_idx.append(i)
        else:
            tails[k], tail_idx[k] = v, i
        prev[i] = tail_idx[k - 1] if k else -1
    out, i = [], tail_idx[-1] if tail_idx else -1
    while i >= 0:
        out.append(xs[i]); i = prev[i]
    return out[::-1]

static boolean wordBreak(String s, Set<String> dict) {
    int n = s.length();
    boolean[] dp = new boolean[n + 1];
    dp[0] = true;                                // the empty prefix is splittable

    int longest = dict.stream().mapToInt(String::length).max().orElse(0);

    for (int i = 1; i <= n; i++) {
        // Only look back as far as the longest word: turns O(n^2) into
        // O(n * longest), which for real dictionaries is linear.
        for (int j = Math.max(0, i - longest); j < i; j++) {
            if (dp[j] && dict.contains(s.substring(j, i))) {
                dp[i] = true;
                break;
            }
        }
    }
    return dp[n];
}

Two pointers and the sliding window

A nested loop over pairs is O(n²) because it reconsiders pairs it has already ruled out. When the data has an order — sorted values, or a window that only ever grows and shrinks in one direction — two indices that each move forward only can rule out whole ranges at once, and the whole sweep becomes O(n).

Opposite endsNeeds sorted input. Two-sum, three-sum, container-with-most-water, palindrome checks. Move whichever end can possibly improve the answer.
Same directionThe sliding window. Longest or shortest run satisfying a condition. Grow the right edge; when the condition breaks, advance the left until it holds again.
Fast and slowCycle detection, middle of a list, k-th from the end. One pointer moves twice as fast, or starts k ahead.
Two sequencesMerging, intersecting sorted sets, and diffing. Advance whichever side is behind — the merge step of merge sort is exactly this.

// window.go — the sliding-window template. Almost every "longest or
// shortest run such that ..." problem is this eight-line shape with a
// different condition.

func LongestUnique(s string) (best, at int) {
    last := make(map[byte]int, 64)               // byte -> last index seen
    lo := 0
    for hi := 0; hi < len(s); hi++ {
        if prev, seen := last[s[hi]]; seen && prev >= lo {
            lo = prev + 1                        // jump past the duplicate; never back
        }
        last[s[hi]] = hi
        if hi-lo+1 > best {
            best, at = hi-lo+1, lo
        }
    }
    return best, at
}

// Opposite ends, on sorted input. Each iteration eliminates one whole
// row or column of the pair matrix, which is why n steps suffice for
// n^2 pairs.
func TwoSum(sorted []int, target int) (int, int, bool) {
    i, j := 0, len(sorted)-1
    for i < j {
        switch sum := sorted[i] + sorted[j]; {
        case sum == target:
            return i, j, true
        case sum < target:
            i++                                  // no pair with sorted[i] can work
        default:
            j--                                  // no pair with sorted[j] can work
        }
    }
    return 0, 0, false
}

from collections import Counter

def longest_unique(s: str) -> str:
    """Longest substring with no repeated character. O(n)."""
    last: dict[str, int] = {}
    lo = best = at = 0
    for hi, ch in enumerate(s):
        if (prev := last.get(ch, -1)) >= lo:

def min_window_covering(s: str, need: str) -> str:
    """Shortest substring containing every character of `need`. O(n).

    The 'shortest' variant grows the right edge until the window is
    valid, then shrinks the left as far as it can while staying valid.
    Both edges still only move forward.
    """
    want = Counter(need)
    missing = len(need)
    lo = best_lo = 0
    best = float("inf")
    for hi, ch in enumerate(s):
        if want[ch] > 0:
            missing -= 1
        want[ch] -= 1
        while missing == 0:                      # valid: try to shrink
            if hi - lo + 1 < best:
                best, best_lo = hi - lo + 1, lo
            want[s[lo]] += 1
            if want[s[lo]] > 0:
                missing += 1
            lo += 1
    return "" if best == float("inf") else s[best_lo:best_lo + best]

def rolling_mean(xs: list[float], k: int) -> list[float]:
    total = sum(xs[:k])
    out = [total / k]
    for i in range(k, len(xs)):
        total += xs[i] - xs[i - k]               # O(1) per step, not O(k)
        out.append(total / k)
    return out

Prefix sums and difference arrays

If you are going to be asked many range questions about an array that is not changing, answer them all at once first. A prefix-sum array turns “the sum from i to j” from an O(n) loop into a single subtraction — and its mirror image, the difference array, turns “add 5 to everything from i to j” into two writes.

// prefix.go — build once in O(n), answer every range query in O(1).

func Prefix(xs []int) []int {
    p := make([]int, len(xs)+1)                  // note the +1: p[0] = 0 removes
    for i, v := range xs {                       // every "if i == 0" branch below
        p[i+1] = p[i] + v
    }
    return p
}

sum := p[j+1] - p[i]                             // inclusive range [i, j], O(1)

// The difference array is the same idea run backwards: to add `delta`
// to every element in [i, j], record it at the two ENDS and integrate
// once at the end. k range updates in O(k + n) instead of O(kn).
func ApplyRanges(n int, updates [][3]int) []int {
    diff := make([]int, n+1)
    for _, u := range updates {
        lo, hi, delta := u[0], u[1], u[2]
        diff[lo] += delta
        diff[hi+1] -= delta                      // the +1 slot is why diff is n+1
    }
    out := make([]int, n)
    running := 0
    for i := range out {
        running += diff[i]
        out[i] = running
    }
    return out
}

// solved: +1 at each start, -1 at each end, then a running maximum of
// the integral. No interval tree required.

# The prefix-sum + hash-map combination, which is the answer to a
# surprising number of questions: "how many subarrays sum to k?"
# A subarray (i, j] sums to k exactly when p[j] - p[i] == k, so for
# each j we need the count of earlier prefixes equal to p[j] - k.
def count_subarrays_summing_to(xs: list[int], k: int) -> int:
    from collections import defaultdict
    seen = defaultdict(int)
    seen[0] = 1                                  # the empty prefix
    running = total = 0
    for v in xs:
        running += v
        total += seen[running - k]               # O(1) per element
        seen[running] += 1
    return total

// Prefix.java — and the Fenwick tree, for when the array changes.

static long[] prefix(int[] xs) {
    long[] p = new long[xs.length + 1];          // long: prefix sums overflow int
    for (int i = 0; i < xs.length; i++) p[i + 1] = p[i] + xs[i];
    return p;
}

// A Fenwick tree: prefix sums that survive updates. Each slot i holds
// the sum of a block whose length is the lowest set bit of i, so both
// operations walk O(log n) slots. Fifteen lines, and it replaces a
// segment tree for anything that only needs sums.
final class Fenwick {
    private final long[] t;

    Fenwick(int n) { t = new long[n + 1]; }      // 1-indexed

    void add(int i, long delta) {                // O(log n)
        for (i++; i < t.length; i += i & -i) t[i] += delta;
    }

    long prefix(int i) {                         // sum of [0, i), O(log n)
        long s = 0;
        for (; i > 0; i -= i & -i) s += t[i];
        return s;
    }

    long range(int lo, int hi) { return prefix(hi) - prefix(lo); }
}

// knowing by name, and the whole reason this structure is so small.
//
// Fenwick handles sums (and anything invertible). For minimum, maximum
// or gcd over a range, you need a segment tree, which is larger but
// handles any associative operation.

Greedy, and how to know it is safe

A greedy algorithm takes the best-looking option at each step and never reconsiders. When it works it is the simplest and fastest thing available; when it does not, it produces a plausible wrong answer with no error. The difference is not intuition — it is a proof, and there are two standard ones.

ProblemGreedy ruleSafe?
Interval scheduling — most non-overlapping meetingsAlways take the one that ends earliestYes. Exchange argument: swapping any optimal solution’s first meeting for the earliest-ending one leaves it valid and no smaller.
Coin change, UK or US coinsTake the largest coin that fitsYes, for those coin systems. No in general: with coins 1, 3, 4 making 6, greedy gives 4+1+1 and the answer is 3+3.
Fractional knapsackTake the highest value-per-weight firstYes. You can take a fraction of the last item, so there is no wasted capacity.
0/1 knapsackSame ruleNo. Indivisibility breaks it, and this is exactly why the DP in part six exists.
Minimum spanning treeTake the lightest edge that joins two componentsYes. The cut property, proved in part five.
Huffman codingRepeatedly merge the two least frequent symbolsYes. Exchange argument on the two deepest leaves.

The two proofs, in one sentence each

The exchange argument: take any optimal solution, show you can swap its first choice for the greedy choice without making it worse, then repeat — so a solution that is greedy all the way down is optimal too. The matroid / cut argument: show that the locally best element is in some optimal solution, and that removing it leaves a problem of the same kind. If you cannot produce one of these two for your rule, assume greedy is wrong and look for a counterexample; they are usually small, and finding one takes less time than the incident does.

// greedy.go — interval scheduling. The whole algorithm is the sort key,
// and choosing the wrong key is the classic error.

type Interval struct{ Start, End int }

// Sort by END time, not by start and not by duration. A meeting that
// finishes early leaves the most room for everything after it, and that
// sentence is the proof.
func MaxNonOverlapping(ivs []Interval) []Interval {
    slices.SortFunc(ivs, func(a, b Interval) int { return cmp.Compare(a.End, b.End) })

    out := make([]Interval, 0, len(ivs))
    lastEnd := math.MinInt
    for _, iv := range ivs {
        if iv.Start >= lastEnd {                 // no overlap with the last kept
            out = append(out, iv)
            lastEnd = iv.End
        }
    }
    return out
}

// Merging overlapping intervals: sort by START, then extend or emit.
// Different question, different key -- and that is the point.
func Merge(ivs []Interval) []Interval {
    slices.SortFunc(ivs, func(a, b Interval) int { return cmp.Compare(a.Start, b.Start) })

    out := ivs[:0]                               // reuse the backing array
    for _, iv := range ivs {
        if n := len(out); n > 0 && iv.Start <= out[n-1].End {
            out[n-1].End = max(out[n-1].End, iv.End)
        } else {
            out = append(out, iv)
        }
    }
    return out
}

# greedy.py — Huffman coding, which is greedy plus a heap and is the
# clearest example of a rule that is provably safe.
import heapq
from collections import Counter
from itertools import count

def huffman(text: str) -> dict[str, str]:
    """Optimal prefix-free codes: frequent symbols get shorter codes."""
    freq = Counter(text)
    if len(freq) < 2:
        return {ch: "0" for ch in freq}

    seq = count()                                # tie-breaker: never compare dicts
    heap = [(n, next(seq), {ch: ""}) for ch, n in freq.items()]
    heapq.heapify(heap)

    while len(heap) > 1:
        # The greedy step: the two least frequent symbols must be the
        # two DEEPEST leaves in some optimal tree, so merging them now
        # cannot cost anything.
        n1, _, a = heapq.heappop(heap)
        n2, _, b = heapq.heappop(heap)
        merged = {ch: "0" + code for ch, code in a.items()}
        merged |= {ch: "1" + code for ch, code in b.items()}
        heapq.heappush(heap, (n1 + n2, next(seq), merged))

    return heap[0][2]

record Interval(int start, int end) {}

// "How many rooms do I need?" is not an interval-scheduling problem: it
// is the maximum overlap, and the neat solution is a heap of end times.
static int roomsNeeded(List<Interval> meetings) {
    List<Interval> sorted = new ArrayList<>(meetings);
    sorted.sort(Comparator.comparingInt(Interval::start));

    // The heap holds the end time of every meeting still running. Its
    // size is the number of rooms in use; its root is the one that
    // frees up first.
    PriorityQueue<Integer> running = new PriorityQueue<>();
    for (Interval m : sorted) {
        if (!running.isEmpty() && running.peek() <= m.start()) {
            running.poll();                      // a room came free: reuse it
        }
        running.add(m.end());
    }
    return running.size();                       // the peak, O(n log n)
}

Backtracking: exhaustive search that stops early

Some problems have no better answer than trying everything. Backtracking makes “everything” tractable by building candidates one decision at a time and abandoning a branch the moment it cannot possibly lead anywhere — so the pruning, not the enumeration, is the algorithm.

// backtrack.go — the template. Choose, recurse, un-choose. That last
// step is what makes it backtracking rather than brute force with
// copies, and it keeps the allocation count at zero.

func Permutations(xs []int) [][]int {
    var out [][]int
    var cur []int
    used := make([]bool, len(xs))

    var walk func()
    walk = func() {
        if len(cur) == len(xs) {
            out = append(out, slices.Clone(cur)) // CLONE: cur keeps mutating
            return
        }
        for i, v := range xs {
            if used[i] {
                continue
            }
            used[i], cur = true, append(cur, v)  // choose
            walk()                               // explore
            used[i], cur = false, cur[:len(cur)-1] // un-choose
        }
    }
    walk()
    return out
}

// N-queens: the same template, with the pruning that makes it possible.
// Three bitmasks track which column and which of the two diagonals are
// already attacked, so "is this square safe" is one AND.
func NQueens(n int) int {
    var count int
    var place func(row, cols, diag, anti int)
    place = func(row, cols, diag, anti int) {
        if row == n {
            count++
            return
        }
        // free = the squares in this row attacked by nothing
        free := ^(cols | diag | anti) & (1<<n - 1)
        for free != 0 {
            bit := free & -free                  // lowest set bit: one square
            free ^= bit
            place(row+1, cols|bit, (diag|bit)<<1, (anti|bit)>>1)
        }
    }
    place(0, 0, 0, 0)
    return count
}

def subsets_summing_to(xs: list[int], target: int) -> list[list[int]]:
    """All subsets with a given sum, pruning branches that cannot reach it."""
    xs = sorted(xs, reverse=True)                # big first: prune sooner
    suffix = [0] * (len(xs) + 1)                 # suffix[i] = sum of xs[i:]
    for i in range(len(xs) - 1, -1, -1):
        suffix[i] = suffix[i + 1] + xs[i]

    out: list[list[int]] = []
    cur: list[int] = []

    def walk(i: int, remaining: int) -> None:
        if remaining == 0:
            out.append(cur.copy())               # copy: cur keeps mutating
            return
        # The two prunes that turn 2^n into something finishable:
        if i == len(xs) or remaining < 0:
            return
        if suffix[i] < remaining:                # everything left is not enough
            return
        cur.append(xs[i])                        # choose
        walk(i + 1, remaining - xs[i])
        cur.pop()                                # un-choose
        walk(i + 1, remaining)                   # skip this element

    walk(0, target)
    return out

static boolean solve(char[][] board) {
    for (int r = 0; r < 9; r++) {
        for (int c = 0; c < 9; c++) {
            if (board[r][c] != '.') continue;
            for (char v = '1'; v <= '9'; v++) {
                if (!isValid(board, r, c, v)) continue;
                board[r][c] = v;                 // choose
                if (solve(board)) return true;   // explore
                board[r][c] = '.';               // un-choose
            }
            return false;                        // no digit fits: this branch is dead
        }
    }
    return true;                                 // no empty cell left: solved
}

    int br = r / 3 * 3, bc = c / 3 * 3;
    for (int i = 0; i < 9; i++)
        if (b[r][i] == v || b[i][c] == v || b[br + i / 3][bc + i % 3] == v)
            return false;
    return true;
}

// Streams: excellent for expressing the pipeline, and worth measuring
// before putting in a hot loop -- a plain for loop over an int[] is
// usually faster than the equivalent stream, sometimes by a lot.
Map<Dept, List<User>> byDept = users.stream()
        .collect(Collectors.groupingBy(User::dept));
Map<Dept, Long> counts = users.stream()
        .collect(Collectors.groupingBy(User::dept, Collectors.counting()));

// The utility that saves the most code, and the one most often missed:
map.merge(key, 1, Integer::sum);                 // count
map.computeIfAbsent(key, k -> new ArrayList<>()).add(v);   // group
map.compute(key, (k, v) -> v == null ? init : update(v));

// Across threads: ConcurrentHashMap, and its atomic compute methods.
// Never Collections.synchronizedMap, which serialises every call and
// still needs external locking for check-then-act.
concurrent.computeIfAbsent(key, k -> expensive(k));   // atomic, per key

The mistakes each language invites

Every runtime has a small set of data-structure errors that its own design makes easy. They are not exotic; they are the ones that reach production, survive review, and are eventually found by a profiler or an incident. Here they are, per language, with the fix.

GoSub-slicing a large buffer and keeping the small resultThe whole backing array stays reachable. A 10-byte slice of a 100 MB read holds 100 MB. Fix: slices.Clone.

The order to think in

When something is slow, work down this list rather than reaching for the clever structure first. One: is there an accidental quadratic — a membership test, a removal, or a string concatenation inside a loop? That is the majority of real cases and the fix is usually one line. Two: is the work being repeated — would a cache, a prefix sum or a memo remove it? Three: is the data laid out badly — boxed values, pointer chasing, a map where an array would do? Four, and only then: is a different algorithm needed? Most performance work never gets past step one, and the engineers who look fastest are usually the ones who recognise it there.
