What “idiomatic” means in a Java review

Idiom in Java is mostly about narrowing what code is allowed to do: make it immutable, make it final, make the type say it. Each rewrite below deletes a state the wrong version could reach — the same argument the Python and Go pages made, wearing a suit.

Review flagWhy it bitesThe idiomatic form
Field injection (@Autowired on a field)Untestable without the container; hides the dependency countOne constructor, final fields — Spring wires it with no annotation
equals without hashCodeThe object silently misbehaves as a map key — part two’s buckets diagramGenerate both together, or use a record and get them for free
Returning null for “not found”The caller’s NPE fires far from the causeOptional<T> as the return type; orElseThrow at the edge
String concatenation in a loopQuadratic — each + copies the whole accumulated stringStringBuilder, or a stream with Collectors.joining
Mutable static stateA hidden global shared by every thread and every testInstance state owned by a bean; constants static final and immutable
Catching Exception broadly mid-stackSwallows bugs and cancellation alikeCatch the specific type you can handle; let the advice map the rest

Business logic in the controllerUntestable without HTTP; unusable from a queue consumerControllers translate; services decide — the same split as every sibling page

The toolchain that argues for you

Spotless with google-java-format ends formatting debate the way black did for Python. Error Prone runs inside javac and catches real bug patterns (a missing @Override, a self-assignment, an ignored return). SpotBugs reads the bytecode for null-flow and resource leaks. JaCoCo measures coverage in mvn verify. Wire all four into the build and a class of review comments disappears.

Idioms that have quietly expired

new Date() → java.time.Instant. Getters/setters on a data holder → a record. synchronized collections → ConcurrentHashMap or immutability. XML config and web.xml → annotations and application.yml. RestTemplate → RestClient. Application servers → the embedded server in the jar. If a tutorial shows any of the left column, check its date.

Run it

Add Spotless to the tasks project’s pom.xml plugins block, then let it rewrite your formatting and fail the build when someone skips it.

$ ./mvnw spotless:check
[ERROR] The following files had format violations: TaskService.java   ← caught
$ ./mvnw spotless:apply && ./mvnw spotless:check
[INFO] Spotless check succeeded.
<!-- pom.xml, inside <build><plugins> -->
<plugin>
  <groupId>com.diffplug.spotless</groupId>
  <artifactId>spotless-maven-plugin</artifactId>
  <version>2.44.0</version>
  <configuration>
    <java><googleJavaFormat/></java>
  </configuration>
  <executions>
    <execution><goals><goal>check</goal></goals></execution>  <!-- fails mvn verify -->
  </executions>
</plugin>

The checklist, and where to go next

Twelve things worth a second look in any Java diff, the sixty seconds of commands before a pull request, and the map of what this page deliberately left for your second month.

Run it

The sixty seconds before you open the pull request — from the tasks project root, with Docker running for the Testcontainers rung.

$ ./mvnw spotless:apply                  # format — never argue about it again
$ ./mvnw verify                          # compiles, unit + slice + container tests, coverage
$ ./mvnw versions:display-dependency-updates | grep -A2 spring-boot
# then read your own diff — these catch what the tools do not:
$ git diff --cached | grep -nE '@Autowired|System\.out|printStackTrace'
$ git diff --cached | grep -nE 'catch \(Exception|\.get\(\)|new Thread\('
$ git diff --cached | grep -nE 'password|secret|apikey' # nothing hard-coded, ever

What this page deliberately left out

Spring Security (authentication filters, JWT resource servers) deserves its own page rather than a cameo. So do messaging (Kafka via spring-kafka, the listener/acknowledgement model), caching (@Cacheable and its invalidation problem — the foundations page’s caching section applies verbatim), GraalVM native images, and the module system. Learn them in that order; each builds on parts you now have.

Where to go next

Effective Java (Bloch) is the review lens of this part, expanded to ninety items — read it after a month of writing, not before. Java Concurrency in Practice is part eight’s missing depth; still correct, virtual threads notwithstanding. For Spring, the reference documentation is genuinely good — read the chapter for each starter you add, and read the auto-configuration classes when behaviour surprises you: they are short, and they are the truth.
